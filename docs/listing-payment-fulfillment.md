# Однократная оплаченная публикация обычного объявления

Локальная реализация L17, не включённая на рабочем сайте. Миграция0022,
trusted-worker store и проверки продолжают неизменные0019–0021. Production
остаётся на0018; ручное внешнее ревью финансовой части отложено владельцем,
не заменено этими тестами. Нет нового HTTP API, задания по расписанию, отправки
платежа, production grants или автоматического apply/deploy.

## Правила исполнения

`PostgresListingPaymentFulfillmentStore.fulfill(id)` принимает только ID уже
сохранённого намерения. Это приватный метод доверенного процесса, а не маршрут
владельца: знание UUID не даёт пользователю права его вызывать. Перед будущим
подключением нужны отдельная аутентификация worker, admission и диагностика.
Конфигурация фиксирует конкретный магазин и TEST/LIVE; несовпадение отклоняется.
Разрешение тестового worker не является разрешением выдавать production-услуги
за TEST-платежи: контур и sandbox E2E допускаются отдельно.

1. Блокировки: пользователь → исходное намерение → заказ → объявление →
   категория/родитель, город, прикреплённые фото → решение модерации. Это
   согласовано с user-first редактором и intent-first финансовой сверкой,
   которая пользователей и объявления не блокирует. Сетевых запросов нет.
2. Канонический intent-reader проверяет исходные байты/хеш и известную связь с
   провайдером. Нужны listing, исходный duration и точная привязка магазина.
3. Если запись исполнения уже есть, возвращаются её прежние даты. Это
   **исторический результат**, не утверждение, что карточка сейчас опубликована.
   Архивирование, блокировка или возврат не вызывают повторной публикации.
4. Для первого исполнения нужны order succeeded и authoritative verification
   succeeded с известным captured_at и тем же provider ID. Hold, отсутствующее
   время либо refunded не публикуют. Финансовая правда сохраняется отдельной
   транзакцией сверки: невозможность публикации не превращает списание в failed.
5. Проверяются действующий подтверждённый незаблокированный владелец,
   неоплаченный draft, исходная точная bigint revision, её approved решение,
   каноническая валидация формы и доступные собственные фото. Текущий тариф
   больше не определяет уже купленную цену/длительность. Неполная форма,
   неактивная категория и устаревшая модерация не обходятся наличием денег.
6. Обновление карточки и INSERT записи исполнения атомарны. Ошибка записи
   откатывает публикацию; PK намерения и блокировка сериализуют конкурентов.
   При неизвестном COMMIT метод не делает автоматический retry и не сообщает
   успех: следующий явный вызов прочитает прежнюю запись либо исполнит один раз.

`not_ready` означает отсутствие пригодного финансового подтверждения; `blocked`
— недоступный аккаунт/версия/одобрение/контент/период. Нарушенная структура формы
или недопустимые фото могут бросить существующую ошибку canonical form store;
ошибки SQL не маскируются. Во всех этих случаях запись исполнения отсутствует,
исходный заказ/платёж не меняются. Будущему worker нужен разбор таких записей,
а не бесконечная очередь или автоматическое второе списание.

## Оплаченный период и точность

Начало — исходное captured_at, конец — оно же плюс исходное число суток по
86400 секунд. Текущее время сверки не используется как начало услуги.
Отсутствующее, истёкшее или будущее время не даёт новый срок. До INSERT
проверяется `created_at <= published_at <= clock_timestamp() < expires_at`.
Публичный reader отдельно проверяет актуальность периода при каждом чтении.

Источник хранит до9 знаков дробной секунды, PostgreSQL — до6. Чистый helper
округляет начало вверх, конец вниз до микросекунд: он не начинает услугу раньше
списания и не продлевает её. Целые секунды и календарь проверяются отдельно,
дробь не проходит через теряющий точность JavaScript Date. Поддерживаются
перенос секунды/суток/года и високосный день. Исходная строка captured_at не
перезаписывается. Фиксированные сутки не зависят от часового пояса/DST
([PostgreSQL18](https://www.postgresql.org/docs/18/functions-datetime.html),
[точность](https://www.postgresql.org/docs/18/datatype-datetime.html)); документация
получена через Context7 до реализации.

## Схема, права и откат

0022 добавляет только `app.payment_fulfillments`: PK/FK намерения в сохранённой
verification, даты услуги и DB-stamped время исполнения. UPDATE/DELETE запрещены
trigger. Исходные контакты, карточные сведения или полный provider payload не
копируются. FK/trigger не доказывают подлинность платежа и не защищают от SQL
owner или скомпрометированного доверенного worker: валидация — его обязанность.

`getBootstrapPlan({includePaymentFulfillment:true})` — только явный библиотечный
opt-in без CLI/startup/deploy hook; прежние default/plan и21 хеш сохранены.
Down выполняется на пустой таблице и отказывается удалять непустую историю.
Операционный откат — прежний код с сохранением финансовых данных, не удаление
оплаченных публикаций и не возврат к Supabase. Fixture-роль существует только
в собственном loopback контейнере. Для production нужны отдельные согласования
DDL и точечных grants; web-runtime по-прежнему не получает финансовую запись.

Это только первое размещение обычного объявления. Не реализованы продления,
бесплатный тариф, остальные типы размещений, выдача отклика после оплаты,
refund request/отзыв услуги и чеки. Active-order hold из0020 не снимается:
нельзя автоматически создать новую оплату вместо неизвестной старой. До
release также остаются dispatch/recovery, webhook, checkout UI/история,
merchant sandbox E2E, наблюдение, retention/export/erasure финансовой истории.
Полный перенос ещё не завершён.

## Проверки

Direct-import тесты периода, regression несовместимой booking-формы и реальные
PostgreSQL18 проверки: opt-in/down/hash/grants, исходный срок при drift тарифа,
публичная читаемость карточки, точная большая revision, фото, owner/account/
модерация/категория, сроки/хронология, конкуренция, NOWAIT блокировок, lost COMMIT,
rollback публикации при сбое записи и отсутствие resurrection после refund/
archive. Данные синтетические; merchant HTTP и production БД не используются.
Инверсия ceil→floor действительно ломает тест точности, затем код восстановлен.

Статический разбор выявил несовпадение content-check с public mapper: у
неарендного объявления могла оставаться booking-форма. Сначала отдельный
regression воспроизвёл пропуск, затем общий content-check стал отклонять такую
комбинацию до модерации, checkout и fulfillment; редактируемый черновик не
переписывается. Code Graph не показал dependents этого helper, но прямой поиск
подтвердил form/public/bookings/client consumers: граф здесь не является полным
доказательством изоляции. Полный suite проверяет эти существующие ветки.

Контрольная точка: native1550/1550, PostgreSQL18 293/293, без пропусков и ошибок;
production build и types завершены с exit0. Whole lint:0errors, прежнее
предупреждение unused targetType в checkout-prerequisites test не подавлялось.
Floor чистый; staged Gitleaks не обнаружил секретов. Это локальное runtime proof,
не merchant E2E, не новый production deploy и не полная готовность к запуску.

Команды: `node --experimental-strip-types --test tests/payment-publication-period.test.mjs
tests/listing-non-rental-booking.test.mjs`,
`node --experimental-strip-types --test tests/bootstrap-postgres-integration.mjs`,
полный native suite, build/types/lint/floor и staged Gitleaks.
