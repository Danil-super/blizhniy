# Удаление аккаунта: локальный этап F04

Реализованы подача запроса, просмотр его состояния и ручное рассмотрение администратором в PostgreSQL. Старые Supabase-компоненты и API сохранены для legacy-режима; primary-страницы выбирают новые компоненты и cookie API. Обращение к отсутствующему Supabase-клиенту больше не требуется.

## Границы доступа

- Владелец может прочитать свой последний запрос и создать один активный запрос. Повтор после неизвестного результата возвращает существующую заявку. Пользователь и сессия блокируются до работы с ресурсом; актуальность сессии повторно проверяется перед COMMIT.
- Подтверждённый по email заблокированный пользователь может войти на странице запроса. Этот вход получает отдельную `__Host-blizhniy_data_subject` cookie с HttpOnly, Secure, SameSite=Lax и абсолютным сроком не более часа. Он не разрешает работу с кабинетом, публикациями или админкой. Общий выход и успешная смена обычного аккаунта отзывают этот ограниченный доступ. Ограниченный выход не завершает обычную сессию.
- Выбор cookie явный: `access=account` или `data-subject`. `expectedOwnerId` / `expectedAdminId` — защита от смены аккаунта во время запроса, а не источник полномочий. Проверки выполняются в транзакции по фактической cookie. Парольный маршрут использует те же IP/email бюджеты входа и серверную CAPTCHA, что и обычный вход.
- Администратор должен иметь действующую обычную сессию, актуальную роль и не быть заблокированным. Рассмотрение и решение используют revision CAS. Решение требует подтверждения ручных действий и номера защищённого дела; внутренний номер не попадает в ответ владельцу.
- Миграция 0033 создаёт таблицы заявок и неизменяемых событий. Даты и revision контролирует триггер. Runtime получает SELECT и точечные INSERT/UPDATE только заявок, без DELETE, изменения владельца/дат/revision и записи событий. Audit trigger — SECURITY DEFINER с пустым search_path и отозванным PUBLIC EXECUTE.

Транзакционная настройка `blizhniy.deletion_actor` выставляется после проверки сессии. Это дополнительная защита от ошибки обработчика, а не изоляция от скомпрометированной runtime-роли: существующий серверный контур доверяет SQL-коду и даёт роли чтение пользователей и сессий.

## Что остаётся открытым

Запись решения не запускает стирание данных. `fulfilled` означает подтверждение оператором уже выполненных ручных действий; UI явно сообщает об этом и требует ссылку на защищённое дело. Нельзя считать F04 полностью закрытым по одному этому статусу.

Для автоматического исполнения необходим отдельный план по аккаунту/профилю, публичным и приватным публикациям, откликам и их снимкам, бронированиям, медиа и аватару, уведомлениям, сессиям, поисковым индексам/кэшам и резервным копиям. Для платёжной и административной истории нужны утверждённые основания и сроки хранения, затем воспроизводимый исполнитель и приёмка. Этот этап не вводит новые сроки хранения и не удаляет финансовую историю. В журнале остаются псевдонимные ID автора/оператора и состояния решения; контакт берётся из аккаунта при чтении и не копируется в события.

## Локальная установка и проверка

Только для собственного Docker-стенда, подтверждённого `local-primary-config.mjs`; production-конфигурация не загружается:

```sh
node --experimental-strip-types scripts/local-deletion-migration.mjs --apply
node --experimental-strip-types scripts/local-deletion-migration.mjs --check
node --test tests/primary-account-deletion.test.mjs tests/account-deletion-http.test.mjs tests/data-subject-browser-logout.test.mjs
node --test tests/deletion-shared-login-budget.test.mjs
node --test tests/account-deletion-postgres-integration.mjs
node --experimental-strip-types scripts/check-local-deletion.mjs
```

Установщик требует точного журнала 0001–0032 или уже установленной точной 0033. Схема, права и запись журнала устанавливаются одной транзакцией. Неизвестный COMMIT не повторяется автоматически; повторный явный запуск сначала читает журнал. Preflight отвергает опасные флаги роли, исходящие memberships и прямые права удаления пользователей, назначения роли, изменения оплаты/платёжного статуса и срока размещения. Это узкая проверка данного этапа, не полный аудит всех ACL.

PG-тест использует отдельный одноразовый PostgreSQL 18.6. Браузерная проверка использует только синтетические аккаунты в собственном стенде и существующего локального администратора; проверяет обычного и заблокированного владельца, ограничение scope, повторное открытие, решение и выход. Созданные тестом аккаунты удаляются по их точным ID и случайному суффиксу email; неизменяемые псевдонимные записи решений сохраняются. Рабочие данные и внешние письма не используются.

Не запускайте build/types и PostgreSQL/browser runner одновременно: они используют общий `.next`. После итоговой сборки нужно перезапустить только подтверждённый собственный процесс стенда, чтобы приложение и локальный proxy использовали новый код.
