# Сверка статуса публикаций по сроку оплаты

Скрипт `supabase/maintenance/reconcile-expired-publications.sql` переводит оплаченные и неоплаченные строки `listings` и `vacancies` из `published` в `expired`, когда их `expires_at` наступило. Он не меняет `is_paid` (история оплаты), `published_at` или `expires_at`. Заархивированные, проданные, отклонённые, ожидающие оплаты, записи с пустым сроком и новые оплаченные публикации остаются без изменений. Публичные выборки независимо фильтруют срок, поэтому запуск скрипта нужен для правильного статуса в кабинете и админке.

Отдельное действие «вернуть вакансию из архива» меняет `published_at` на момент восстановления для порядка выдачи, но сохраняет исходный `expires_at`. Дата возврата не означает новую оплату и не продлевает размещение. Архивную вакансию с истёкшим сроком вернуть этим действием нельзя; новый срок потребует отдельного проверенного сценария оплаты и исполнения.

На 25.09.2026 метаданные живой БД подтвердили наличие срока у объявлений и вакансий, но пока не у `specialist_profiles` и `work_requests`. После добавления сроков для этих двух типов потребуется отдельное расширение скрипта и проверка их сценариев публикации. Для `fair_applications` срок не задан: участия без фиксированной даты окончания скрипт не затрагивает.

## Проверка и ввод в эксплуатацию

1. На отдельном стенде исполнить тест на временных таблицах: `psql -X -v ON_ERROR_STOP=1 -d "$STAGING_DATABASE_URL" -f tests/reconcile-expired-publications.sql`. Он проверяет границу `expires_at = now()`, действующие и архивные строки, сохранность истории оплаты и повторный запуск. Тест заканчивается `ROLLBACK`; в production не запускать его вместо основного скрипта.
2. Снять резервную копию стенда и агрегатно подсчитать будущие изменения: `select count(*) from public.listings where status = 'published' and expires_at <= now();` и аналогично для `public.vacancies`. Проверить, что есть право на оба `UPDATE`, а тип статуса принимает `expired`.
3. На стенде выполнить `psql -X -v ON_ERROR_STOP=1 --single-transaction -d "$STAGING_DATABASE_URL" -f supabase/maintenance/reconcile-expired-publications.sql`. Повторить запросы: оба счётчика должны стать нулём; убедиться в правильном статусе в кабинете, админке, отсутствии в выдаче и в том, что оплата не изменилась. Проверить публикацию новой оплаченной вакансии: действующая запись остаётся `published`.
4. Только после этого планировать production: согласовать время, сделать backup, записать агрегатные счётчики до запуска, исполнить тот же файл с production URL и сверить числа `expired_count`. Не включать таймер до успешного одиночного прогона и проверки сайта.

Для будущего Timeweb VPS можно запускать файл через системный таймер раз в 15 минут: `psql -X -v ON_ERROR_STOP=1 --single-transaction -d "$DATABASE_URL" -f /var/www/blizhniy/supabase/maintenance/reconcile-expired-publications.sql`. Использовать отдельную учётную запись ОС и защищённые параметры подключения PostgreSQL (например, `PGSERVICEFILE`/`.pgpass` с правами 0600), не хранить пароль в unit-файле или командной строке; `psql` должен быть установлен. Таймер разворачивать только после шага 4. Успех контролировать по выводимым двум счётчикам и агрегатному запросу, ошибку `psql` считать сбоем всей операции.
