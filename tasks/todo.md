## 2. Аккаунты и серверные сессии — выполнено локально

Зависит от 1. Файлы: новая identity SQL, серверные password/session модули и их тесты (до 5 файлов на инкремент).

- [x] Хеширование пароля и случайные токены; в БД только хеши токенов с TTL.
- [x] Сессия отзывается; заблокированный пользователь не получает обычный API-доступ, запрос удаления остаётся возможным.
- [x] Проверены таймауты, истечение, повторное использование и конкурентные обращения.

Проверка: unit + isolated SQL на PostgreSQL 18.6; типы/lint/build. Не применяем старую синтетическую `auth.users` как production-Auth.

Контракт этого этапа: встроенный async scrypt (N=131072, r=8, p=1), случайная соль 16 байт, максимум 2 вычисления на процесс без неограниченной очереди. Новый пароль — 15–128 символов, без обрезки/нормализации; старую форму пока не меняем. Сессия — случайный 256-битный токен, в БД SHA-256, абсолютный срок 8 часов и простой 30 минут. Вход только после подтверждения email; блокировка запрещает обычный доступ, но не отдельную проверку для запроса удаления/экспорта. Изменение пароля/почты инвалидирует прежние сессии, включая прямое изменение SQL. Схема/rollback применяются только к собственному локальному тестовому контейнеру; rollback отказывается удалять непустые таблицы.

Инкременты: 2a — криптографические примитивы и unit-тесты (`src/lib/identity.ts`, `tests/identity.test.mjs`); 2b — SQL up/down, серверный identity repository и реальная интеграция (до 5 предметных файлов). Публичный login/registration API, cookies, SMTP, CAPTCHA и production-миграция относятся к последующим задачам.

2a проверен локально: 13 unit-тестов, полный suite 783/783, tsc/lint/build успешны; новых зависимостей нет. Инверсия результата timingSafeEqual воспроизводимо ломает тест верного пароля; исходный код восстановлен. Проверены свежая соль, отсутствие trim, невалидные параметры KDF, лимит параллелизма и токенов, отказ браузерному коду.

Итог задачи 2, 09.10.2026:

- `src/lib/identity.ts` + новая plain-PostgreSQL миграция up/down: аккаунты, credential version, ограниченные сессии, отзыв/очистка; рабочие маршруты их ещё не вызывают.
- Unit: **15/15**. Полный native suite: **785/785**, без пропусков. Отдельный PostgreSQL 18.6: **27 предметных сценариев / 28 node:test результатов**, включая 18 новых identity-сценариев и прежние SQL/TLS-проверки.
- Проверены два владельца, безопасные поля ответа, session hash вместо plaintext, подмена токена хешем, неверный пароль/SQL-looking email, подтверждение email, блокировка, privacy-only scope, срок 8 ч / простой 30 мин, отзыв одной/всех сессий, удаление/очистка, актуальные роли, отсутствие публичного чтения credentials, прямые SQL-изменения пароля/email и конкурентная смена пароля во время входа.
- Up → down → up успешен на пустой схеме. Down с аккаунтами и повторный up отказывают атомарно, данные остаются читаемыми. В тестовой синхронизации учтён transaction snapshot `pg_stat_activity`: мониторинг блокировки выполняется на отдельном autocommit соединении, не по таймеру, обходящему защиту.
- Проверка чувствительности: удаление SQL-проверки session scope воспроизводимо допускает privacy-only токен к обычному guard и ломает тест; условие восстановлено. Финальные SQL/native suites зелёные.
- Types/lint/build успешны; одно прежнее lint warning без ошибок. Production npm audit — 0 уязвимостей; зависимости не добавлялись. Приватные `.pem`/`.key` исключены из Git; пароли/токены не логируются.
- Локальный замер Node.js 22: два параллельных scrypt завершились за 381 мс, peak RSS процесса 358 МиБ. Это измерение dev-машины, не SLA/нагрузочный тест VPS; перед production нужны общий limiter и повторный замер вместе с Next.js.
- [ADR-002](../docs/decisions/0002-server-sessions.md) и [операционная инструкция](../docs/postgresql-backend.md) описывают контракт и ограничения. Тестовый контейнер/ключи удалены; существующие сервисы и Timeweb не изменялись.
