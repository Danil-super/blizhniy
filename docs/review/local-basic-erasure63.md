# Кандидат базового удаления63: только локальное сохранение

## Что предлагается одобрить

Сохранить проверенный кандидат в локальном Git. Никакой установки на постоянный
стенд, новых ролей/GRANT, запуска удаления реальных пользователей, push или
production это решение не разрешает.

Новая0063 добавляет append-only квитанцию с уникальными operation/request/subject,
расширяет отдельный admin journal и ставит fencing-триггеры на users и две таблицы
подготовки оплаты. Старые guard/workflows/тестовые ожидания не меняются.
Новый SQL guard требует человеческого просмотра по [CONSTRAINTS.md:47](../../CONSTRAINTS.md#действующие-механизмы):
«Изменения самого guard/workflows … обязательно проверяются человеком».

## Реальный эффект и цена будущего включения

- Только одноразовый Docker/tmpfs и синтетический UUID@synthetic.invalid аккаунт; у кода нет CLI/HTTP/постоянной capability.
- Удаляет основные данные аккаунта без бизнес-истории; любое доменное совпадение требует ручного плана. Журнал заявки и квитанция остаются псевдонимными данными, completeErasure=false.
- Все операции одной транзакцией, конечная проверка admin-сессии, точная привязка повторного запуска.
- SHARE ROW EXCLUSIVE на users и бизнес-таблицах блокирует конкурирующие записи всего тестового контура. Это offline-ограничение, не приемлемая production-очередь.
- После установки SQL все INSERT users/payment-intent/payment-order и защищённые UPDATE id/owner требуют read committed. Это намеренная совместимость, которую потребуется отдельно проверить до любого включения.
- Из-за новой структуры прежние финансовые guard отклонят этот контур. Для установки нужен отдельный согласованный пакет совместимости, backup/restore и минимальные права. В текущий запрос он не входит.
- Старый backup без актуального журнала всё ещё может вернуть данные; процесс внешнего журнала и очистки до открытия восстановленной БД остаётся работой следующего этапа.
