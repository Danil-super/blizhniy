## Граница и результат

Кандидат допускает только NODE_ENV=test, одноразовый контейнер с проверенными
label/name, закреплённым образом PostgreSQL18, loopback-портом, tmpfs без
постоянных mount/bind, совпавшими SQL fixture-marker и адресом сервера. БД должна
называться blizhniy_erasure_test, роль — postgres. Удаляемый пользователь обязан
иметь адрес вида `<его UUID>@synthetic.invalid`. CLI, HTTP-маршрута, установленной
роли или автоматического задания нет. Администратор подтверждается настоящей
сессией; её истечение в конце откатывает даже уже выполненный DELETE.

В одной транзакции удаляются основные данные простого аккаунта без доменной
истории. Заявка закрывается как partly_retained, сохраняются псевдонимный аудит
и квитанция операции. Ответ явно содержит completeErasure=false. Это не
утверждение об уничтожении всех персональных данных и внешних копий.

| Категория | Поведение кандидата |
|---|---|
| Пользователь, профиль/организация, сессии, email/recovery-токены, Telegram attempt/binding | Удаление через проверенные существующие CASCADE; две сессии перестают действовать |
| Версии принятых документов, личные уведомления и готовая/завершённая почта | Удаление связанных основных записей; уже отправленное письмо во внешнем ящике не отзывается |
| Публикации, анкеты, отклики, брони, платежи любого статуса, возвраты, медиа, внешний аудит | При наличии связанных UUID — отказ и отдельный ручной план; ничего не стирается |
| reserved/sending/unknown почта | Отказ до удаления, проверка под блокировкой строк |
| Заявки/события удаления и новая квитанция | Сохраняются без email/телефона; UUID остаётся псевдонимным идентификатором, а не анонимными данными |
| Файлы, SMTP/внешние получатели, логи, индексы/кеш и backup | Полнота удаления не доказана; постоянное включение до проверки этих контуров не разрешено этим кандидатом |

Таблица описывает технический охват синтетического кандидата, **не утверждает
правовые основания или сроки хранения реальных сведений**. Для аккаунтов с
финансовой/спорной историей требуется отдельная политика по категориям.

## Идемпотентность и конкуренция

Предлагаемая0063 добавляет append-only app_admin.basic_account_erasures с
уникальными operation/request/subject ID. Повтор связан также с исходным
администратором, версиями аккаунта и заявки. Другой пользователь или payload
с тем же номером операции отклоняется; потерянный ответ COMMIT восстанавливается
по исходной квитанции без нового удаления. При отказе транзакция не оставляет
квитанцию или новых событий рассмотрения.

Существующего пользовательского row lock недостаточно: финансовые owner UUID
намеренно не имеют FK, а новый INSERT пользователя может ждать удаления
предыдущей строки. Поэтому **этот ограниченный кандидат** удерживает SHARE ROW
EXCLUSIVE на users и всех бизнес-таблицах до COMMIT. Это сериализует записи всего
контура и может закончиться bounded busy/rollback; такая цена приемлема только
для изолированного испытания, не для фоновой production-очереди.

0063 запрещает новые users/payment-intent/payment-order записи с удалённым
subject ID. Пишущие транзакции этих трёх таблиц обязаны использовать read committed:
иначе старый repeatable-read snapshot мог бы не увидеть новую квитанцию.
Семантика блокировок и снимков сверена с официальной документацией
[PostgreSQL18 locking](https://www.postgresql.org/docs/18/explicit-locking.html) и
[transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html).
Context7 в этой сессии вернул исчерпанную месячную квоту.

До операции сверяются точные main59/admin3 journals и структуры app/app_admin
с кандидатом63, а также отдельный каталог local_primary. Неизвестная таблица
local_primary с текстовым user ID не принимается. Скан UUID намеренно
консервативный: совпадение даже независимого ID отправляет случай на review.

## До установки и завершения аудита

- Human review точного SQL guard/diff; отдельное решение для установки,
  минимальные права и координированная совместимость всех обработчиков.
  Старые финансовые guard намеренно не допущены к новой структуре этим этапом.
- Политика реальных категорий/сроков и отдельный исполнитель сложных аккаунтов.
- Проверенный процесс ответа заявителю до потери доступа к кабинету.
- Внешний защищённый журнал исполненных удалений, его доставка в восстановленный
  контур и повторное очищение **до открытия** после старого backup. Один SQL
  INSERT fence не очищает старую копию без актуального журнала и не доказывает
  достижение RPO/RTO.

R01/R03 и полное исполнение права на удаление пока не закрыты.
