После установки62 подготовлен [обновлённый каталог](account-deletion-primary-inventory62.md).
Числа и ограничения ниже относятся к исходному снимку61; текущий runner проверяет62.

Читает каталоги PostgreSQL, main59/admin1 журналы и определения ограничений;
не читает строки пользователей, значения JSON, фото или пароли. Реально
проверен local app60 + отдельная app_admin/0061.

## Что обнаружено

- 30 прямых FK к app.users:18 CASCADE,5 SET NULL,6 RESTRICT,1 NO ACTION.
Транзитивный граф содержит42 отношения, включая корневое, и64 связи.
- Ссылки RESTRICT: media_objects, application_contact_views,
  application_selection_events, payment_checkout_cancellations,
  payment_refund_recovery_actions и work_owner_actions. Booking cancelled_by
  использует NO ACTION. Прямой DELETE пользователя не является готовым сценарием.
- Часть финансовой истории не связана FK с users: payment_orders.owner_id и
  payment_checkout_intents.owner_id. Их сохранение не означает удаления вложенных
  контактов/receipt из JSON. Отсутствие FK не доказывает отсутствие персональных данных.
- account_deletion_events, booking_events и app_admin.user_changes содержат
  исторические actor UUID без FK; их тексты/причины требуют отдельной retention-категории.
- В отчёт включены все потенциально чувствительные JSON/bytea/contact/email/token
  колонки трёх схем и кандидаты идентификаторов без прямого user FK. Поля target_id
  не трактуются автоматически как user ID: у платежей это ID публикации, у
  user_changes — пользователь. Связи подтверждаются источниками конкретного домена.

Закрытый исходный каталог: `~/.local/state/blizhniy/local-primary-private/deletion-inventory61-YcUE7w/catalog.json`.
Он описывает схему, а не количество персональных записей конкретного человека.

## Порядок следующей реализации

1. Зафиксировать категории: прекращение доступа/публичности, удаление профиля и
   контактов, временно сохраняемые финансовые/спорные сведения и сроки, аудит,
   почта/файлы/backup. Для финансовых исключений нужны решение владельца и
   обоснованная политика хранения; этот документ их не назначает.
2. Подготовить read-only план для одного подтверждённого запроса: точный субъект,
   версии, незавершённые платежи/возвраты/брони/загрузки, прямые и доменные связи,
   перечень сохраняемого с причиной. Поиск только FK недостаточен.
3. Отозвать доступ перед изменениями и остановить новые операции субъекта через
   проверяемую границу. Не менять исходные payment body, receipts и immutable
   журналы и не отключать guards ради удобства удаления.
4. Реализовать идемпотентный оператор на синтетической БД: повтор/потеря ответа,
   конкурентная оплата/возврат/загрузка и две сессии. Пользовательские тексты и
   статусы должны отражать фактический результат, включая законно сохраняемое.
5. Согласовать точный пакет с backup/restore и минимальными правами до установки;
   после восстановления из старой копии повторно применять журнал исполненных
   удалений, чтобы персональные данные не возвращались в обслуживание.

Установленная0033 регистрирует и позволяет рассматривать заявку; решение
«исполнено» остаётся записью ручного оператора. Эти действия не выдаются за
выполненное приложением стирание. Действующий runbook ручной обработки сохранён.
