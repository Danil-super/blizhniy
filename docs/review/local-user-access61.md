# Управление доступом пользователей — единый локальный пакет

Статус: кандидат подготовлен, точный patch и установка ещё не одобрены.
Область: только постоянный синтетический стенд https://127.0.0.1:3045.
Production, GitHub/push, два российских сервера и платежи провайдера не затрагиваются.

## Поведение

Администратор может блокировать/разблокировать пользователя и менять роль.
Обязательны причина, подтверждение и актуальная версия записи. SQL повторно
проверяет действующую подтверждённую admin-сессию; собственный доступ и последнего
активного администратора изменить нельзя. Изменение отзывает прежние сессии
пользователя через auth_version и оставляет неизменяемую запись аудита.

Один UUID связан с исходным действием и администратором. После потери ответа
интерфейс предлагает восстановить результат; повтор не выполняет старое изменение
заново. Inspect/recover обновляют last_seen_at действующей сессии, но не меняют
доступ. Закрытие панели/смена аккаунта отменяют запрос и игнорируют поздний ответ.

## Что предлагается применить

[Точный patch](local-user-access61.patch), [план установки](local-user-access61-plan.json)
и [соответствие файлов кандидатам](user-access61-map.json). Patch SHA256:
`2ba6bbff34c071c115fd7852641f069d245c677f9c66aef69aba61056f035db2`.
`git apply --unidiff-zero --check` прошёл; активные guards пока не изменены.

0061 создаёт отдельную схему app_admin с собственным однострочным журналом,
функцией и аудитом. Основная схема app остаётся60, её журнал —59 записей,
0059 отсутствует. SQL SHA256:
`e69fd3681f2a70db9143e027bb1a23e0d0b3435125bfffa03ea7447230fa36a0`.
Существующие данные, роли и GRANT сохраняются.

Новая blizhniy_user_operator получает CONNECT, USAGE трёх перечисленных схем,
чтение name/sha256 двух журналов и EXECUTE ровно одной функции. SELECT users,
UPDATE ролей, доступ к сессиям/аудиту напрямую, memberships, TEMP и CREATE ей
не выдаются. Новый пароль — только в закрытом привязанном к стенду файле вне Git;
Next его не получает. База проверяется через verify-full TLS.

Для допуска новой роли нужны три изменения самих проверок:

1. `financial-catalog-privileges.mjs`: выделена прежняя проверка системных ACL;
   существующая функция продолжает выполнять прежние проверки в прежнем порядке.
2. `refund-worker-schema.mjs`: namespace по умолчанию app; новый аргумент допускает
   только app или app_admin. Существующие версии/эталоны не расширяются.
3. Floor: одна точная пара SHA256 для `admin-user-access-postgres-integration.mjs`.
   Меняются имена объектов в assertions на app_admin, добавляется равенство прежней
   схемы app; ожидаемые отказы/успехи и лимиты сохраняются. Before:
   `2ea4df91367b5593896e2e8cdac5d3f8e17e04792ad91eb04a3edad4a8bf65b6`, after:
   `63ee2e31d24960984ba19a5be81a448da006a2a23764b0d44750dbddfd35e8e3`.

Новый оператор запускается только с BLIZHNIY_LOCAL_USER_ACCESS=enabled.
Прокси валидирует canonical-origin JSON и передаёт команду по закрытому Unix socket;
прежний запрет Unix соединений для процесса Next не ослабляется. При ошибке запуска
или завершении оператора локальная композиция останавливается и закрывает ресурсы.
Новые ветви проверены на отмену и позднее завершение запуска.

автоматического удаления схемы или восстановления поверх истории нет.

## Открытая приёмка

Браузерное управление недоступно: реальная визуальная/клавиатурная проверка
включённой панели остаётся после установки. Тестовые fixtures её не заменяют.
Насыщение очереди пула нового оператора отдельно не измерялось; ограниченные
тайм-ауты/размеры/число соединений проверены кодом и граничными тестами.
Это локальный пакет, не подтверждение готовности production или LIVE.

Требование просмотра: [CONSTRAINTS.md:47](../../CONSTRAINTS.md#действующие-механизмы),
«Изменения самого guard/workflows … обязательно проверяются человеком».
Согласование предыдущих0060/ZAP не включало эту роль, namespace и новые guard.
