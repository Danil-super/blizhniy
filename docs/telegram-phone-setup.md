# Подтверждение телефона через Telegram Login

Настроено локально 28.10.2026. Владелец создал Login-клиент, сохранил ключи вне Git и сообщил об успешном подтверждении настоящего номера; локальная политика включена. Подпись и отрицательные сценарии проверены синтетическими токенами, возврат с действующей сессией — в браузере. На рабочем сайте эта задача ничего не включает.

## Как работает

В настройках аккаунта — «Подтвердить номер через Telegram». Отдельное окно Telegram запрашивает согласие передать телефон. Затем сайт показывает полученный номер и предлагает явно подтвердить его; для замены отличающегося номера требуется отдельное согласие. Телефон привязывается к текущему аккаунту сайта. Telegram не создаёт новый аккаунт и не заменяет вход по email.

Обязательное подтверждение действует перед новым размещением во всех разделах, созданием оплаты размещения и повторной публикацией. Просмотр и сохранение черновиков доступны без подтверждения. Анкета, которая сразу становится доступной для откликов, также требует подтверждения. Внутренние переписки не добавляются; отклики и внешние контакты не превращаются в чаты.

Форма остаётся открытой при подтверждении в другом окне. После подтверждения сайт перечитывает состояние с сервера и продолжает исходное действие. Несохранённые имя, город и другие поля профиля не заменяются чужими изменениями. При конфликте версии необходимо обновить профиль.

Ручная замена номера не переносит подтверждение на новый номер. Удаление номера или «Отвязать подтверждение» снимает привязку. Номер и Telegram ID уникальны среди аккаунтов; конфликт не раскрывает чужого пользователя. Старые опубликованные записи автоматически не снимаются. Повторное размещение проверяется заново.

Если подтверждение сняли уже во время оплаты, успешный платёж не становится новым списанием: размещение ожидает подтверждения в долговечной очереди. После него первая публикация получает полный приобретённый срок. Повторная обработка платежа, редактирование и восстановление публикации этот срок не продлевают. Возврат, блокировка и несовпадение оплаченной версии по-прежнему препятствуют публикации.

## Два российских сервера

Архитектура сохраняется: приложение и файлы находятся на российском VPS, защищённые привязки/попытки/профили — в отдельной управляемой PostgreSQL Timeweb. Дополнительный сервер, Supabase или посредник авторизации не нужны. Telegram — внешний источник подтверждения, которому при авторизации отправляются только параметры Login, а не профиль сайта.

Client Secret хранится только в процессе backend, вне Git. Браузер не получает его и не может назначать phoneVerified. Привязка зависит от существующей HttpOnly-сессии, подтверждённого email и действующего аккаунта.

## Настройка владельцем в BotFather

Основание — [официальная документация Telegram Login](https://core.telegram.org/bots/telegram-login), новый OIDC-поток с Authorization Code, scope `openid phone`, S256 PKCE, state и nonce. Старый виджет, SMS, Gateway и доступ к сообщениям бота не используются.

1. Открыть официальный `@BotFather`, создать или выбрать своего бота и перейти к настройкам Login / Login Widget.
2. Создать Login-клиент, получить **Client ID** и **Client Secret**. Не отправлять Secret в чат и не добавлять в репозиторий. Обычный токен бота не заменяет Login Client Secret.
3. Зарегистрировать origin и точный callback. Для рабочего сайта будущие значения:
   - origin: `https://xn----9sbphbgks4a4a.xn--p1ai`
   - callback: `https://xn----9sbphbgks4a4a.xn--p1ai/api/account/phone/telegram/callback`
4. Для текущего локального стенда код ожидает:
   - origin: `https://127.0.0.1:3045`
   - callback: `https://127.0.0.1:3045/api/account/phone/telegram/callback`
5. На текущем клиенте loopback-адрес принят, владелец прошёл подтверждение. При настройке другого клиента это нужно проверить заново. Если BotFather отвергает адрес, не подменять callback произвольным URL и не подключать туннель автоматически. Требуется отдельно согласованный HTTPS-стенд в существующем российском контуре. Самоподписанный локальный сертификат также должен быть принят локальным браузером.
6. Использовать RS256 для ID token. Если настройки клиента позволяют выбрать алгоритм, не переключать на другой: сервер принимает только RS256 и проверяет подпись по официальному JWKS, issuer, audience, срок и nonce.

## Локальные настройки и запуск

Нужен Node.js 22. Все команды выполняются из корня текущего проекта. Существующие `.env.local` с внешними ключами не загружаются локальным launcher.

Создать вне Git приватный каталог с правами `0700` и файл `telegram.json` с правами `0600`, принадлежащие текущему пользователю. Файл должен содержать ровно два строковых поля:

```json
{"clientId":"CLIENT_ID_FROM_BOTFATHER","clientSecret":"CLIENT_SECRET_FROM_BOTFATHER"}
```

Это схема файла, не рабочие значения. Не использовать реальные ключи в командной строке. Путь задаётся явно:

```sh
export BLIZHNIY_LOCAL_TELEGRAM_CONFIG=/absolute/private/directory/telegram.json
```

Для новой локальной БД `scripts/local-primary.mjs --prepare` создаёт схему с выключенной политикой. Для существующего работающего контейнера схемы 0030:

```sh
node --experimental-strip-types scripts/apply-local-telegram-phone.mjs --plan
node --experimental-strip-types scripts/apply-local-telegram-phone.mjs --apply-local
```

Оператор сверяет точный собственный контейнер, loopback binding, БД, журнал и хеши всех миграций. Применяет 0031/0032 и права серверной роли одной транзакцией. Рабочий адрес БД не принимает. На текущем локальном стенде эти миграции уже применены. При установке значения по умолчанию — `available=false, required=false`; отдельное включение описано ниже.

После создания реального клиента и проверки разрешённого URL включить только локальную политику:

```sh
node --experimental-strip-types scripts/apply-local-telegram-phone.mjs --enable-local
```

Команда требует корректный приватный файл; это ещё не доказательство успешной авторизации Telegram. Перезапустить свой launcher с тем же путём файла:

```sh
env __NEXT_PROCESSED_ENV=true NEXT_TELEMETRY_DISABLED=1 npm run build
node --experimental-strip-types scripts/local-primary.mjs --background
```

Перед пересборкой/перезапуском остановить только собственный launcher по инструкции в [локальном стенде](local-primary-stand.md). Не запускать две сборки в одном `.next`. Начальная страница — `https://127.0.0.1:3045/__local`; там находятся два синтетических аккаунта. Внешние SMTP и платежи остаются запрещены. Только при явной конфигурации разрешаются HTTPS token/JWKS обращения к `oauth.telegram.org`; callback ingress разрешён только для точного пути, а state и сессия проверяются backend.

## Проверка настоящего Telegram после настройки

- Войти в синтетический аккаунт сайта, открыть настройки, запустить подтверждение. Убедиться в согласии Telegram, верном номере и явном подтверждении на сайте.
- Проверить отмену, закрытие окна, просроченную/повторную ссылку и выход из исходного аккаунта.
- Проверить явную замену отличающегося номера; прежняя привязка сохраняется до успешного подтверждения.
- Проверить конфликт второго аккаунта без раскрытия первого, ручное изменение/удаление номера, сохранение email.
- В заполненной форме размещения продолжить через подтверждение и убедиться, что поля и фото сохранились. Без подтверждения новое размещение и оплата должны быть запрещены также при прямом API-запросе.
- Не считать локальную имитацию оплаты проверкой настоящей ЮKassa.

Локальная проверка возврата: `node --experimental-strip-types scripts/check-local-telegram-return-ui.mjs`.
Она создаёт отдельный синтетический аккаунт и действующую одноразовую попытку,
воспроизводит отмену с внешней страницы, callback и следующий 303 на
страницу подтверждения: браузер сохраняет `Sec-Fetch-Site: cross-site` на обоих
шагах. Включённый локальный режим разрешает только эти два GET-документа при
верхнеуровневой навигации. Другие страницы, iframe, API-запросы и изменения
по-прежнему требуют локальный origin. Проверка не обращается к Telegram и не
подтверждает настоящий номер. Дополнительно проверяется отказ при повторе ссылки.
Локальный ingress передаёт callback тому же backend-обработчику через свой
канонический `Request`: внутренний URL Next (`http://127.0.0.1:3046`) не заменяет
зарегистрированный адрес. Проверки сессии, state и токена не изменяются.

На рабочем ingress Caddy перезаписывает `X-Real-IP`, а Next слушает только
`127.0.0.1:3000`. Для GET точного callback runtime переводит внутренний URL
`https://127.0.0.1:3000` в настроенный публичный origin только при совпадении
Host, `X-Forwarded-Proto: https` и единственном корректном IP. Произвольный
`X-Forwarded-Host` не используется. После этого действуют прежние проверки
сессии, state, PKCE, подписи и nonce. Остальные пути и методы не преобразуются.

## Отключение и хранение данных

```sh
node --experimental-strip-types scripts/apply-local-telegram-phone.mjs --disable-local
```

Команда снимает обязательность и доступность только в собственной локальной БД; ожидающие оплаченные размещения возвращаются в очередь с сохранением приобретённого срока. Затем можно остановить launcher и запустить без `BLIZHNIY_LOCAL_TELEGRAM_CONFIG`. Подтверждённые привязки не уничтожаются; их удаление — отдельное действие владельца данных.

Down-миграции отказываются удалять непустую историю и ожидающие оплаты. Не применять откат с удалением данных автоматически. Перенос на рабочие серверы, production-права и включение обязательности — отдельный этап после настоящего Telegram E2E.

## Воспроизводимые проверки

```sh
npm test
npm run check:fast
node --experimental-strip-types --test tests/telegram-phone-postgres-integration.mjs
node --experimental-strip-types --test tests/bootstrap-postgres-integration.mjs
```

Нативные тесты проверяют реальные синтетические RSA/JWKS подписи и подмены claims, HTTP/CSRF, callback/session, приватный файл и сохранность черновика профиля. Изолированная PostgreSQL проверяет RLS, уникальность при конкуренции, замену/отвязку, rate limit, истечение попыток, запрет публикации/оплаты и ожидание оплаченного размещения с возобновлением. Ни один тест не выдаётся за реальное подтверждение Telegram.
