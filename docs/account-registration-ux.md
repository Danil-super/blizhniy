# Регистрация, подтверждение email и первый вход

## Решение владельца — 16.10.2026

Добавить имя и просмотр пароля, установить минимум 8 символов, сделать регистрацию компактнее и устранить неоднозначный результат отправки. Подтверждение email остаётся обязательным. Модерация и оплата не входят в это изменение.

## Сценарий

1. Имя, email, пароль и повтор, два отдельных подтверждения документов, настоящая серверная CAPTCHA. На широком экране поля пароля стоят рядом; на мобильном — друг под другом. Все основные цели нажатия не ниже 44 px.
2. `202 {status:"accepted"}` переключает форму в отдельный экран «Проверьте почту»: адрес, три следующих шага, вход, повтор письма и исправление адреса. Секреты удаляются из памяти формы только при подтверждённом принятии запроса или явной смене режима, а не при сетевой неопределённости.
3. Ответ не раскрывает существование аккаунта. Повторная регистрация существующего адреса не меняет пароль, имя, отметки документов или старую ссылку; экран объясняет возможность входа/восстановления. Повтор письма — отдельная password-gated операция для неподтверждённого аккаунта, без новых legal/profile данных.
4. Ссылка подтверждения содержит одноразовый токен только во fragment. Открытие ссылки не выполняет подтверждение: нужен явный POST с кнопки, чтобы почтовый сканер не потребил ссылку. После подтверждения есть заметное действие «Перейти к входу»; сессия автоматически не создаётся.
5. Вход использует проверенный email и пароль; существующая серверная cookie/session-граница сохраняется. Подтверждённый вход показывает действие «Личный кабинет», а кабинет — быстрые действия и объяснение черновика/модерации. Старые identity/private data не показываются при смене сессии.
6. Восстановление не подтверждает pending-аккаунт. Смена пароля по одноразовой ссылке отзывает прежние сессии и предлагает новый вход. Изменение роли и автоматическое снятие блокировки отсутствуют.

При потере ответа форма не объявляет регистрацию завершённой, не очищает поля и не повторяет запись автоматически: сначала предлагается проверить почту. Пароли/токены не попадают в browser storage, URL query, журналы или Git. Данные формы не обещаются сохранёнными после ухода со страницы.

## Контракты и хранение

- Общий `account-validation.ts`: 8–128 Unicode code points, не более 256 UTF-16 units, корректный Unicode, без NUL и all-whitespace. Пароль не обрезается, не нормализуется и не ограничивается искусственными правилами состава. Старые длинные пароли продолжают работать.
- Минимум 8 выбран владельцем, а не назван современной рекомендацией для password-only входа. [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) рекомендует минимум 15 без MFA; подсказка предлагает длинную фразу. MFA этим изменением не добавлена. Bounded scrypt N=131072/r=8/p=1, случайная соль, CAPTCHA и shared rate limit не ослаблены.
- Новый UI обязательно отправляет `name`, 1–120 печатных символов после удаления краевых пробелов. API дополнительно принимает старый payload без `name` для уже открытых до обновления форм; переданное пустое/некорректное имя отклоняется, лишние поля/роль запрещены. Это не новое право на изменение существующего профиля.
- Имя относится к уже существующей категории профильных ПД. Начальный `app.cabinet_profiles` создаётся в той же транзакции, что пользователь, legal marks и challenge/outbox; authoritative email/phone-verification в JSON не копируются. Дубликат — no-op. При ошибке профиля вся регистрация откатывается. Схема, grants и расположение российских данных не меняются.
- Прямоугольный `size="normal"` 300×65 — [штатная настройка Turnstile](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/widget-configurations/), не CSS-растягивание. Выбран явно на самостоятельных экранах аккаунта; общий compact default для других мест не изменён. Яндекс CAPTCHA остаётся отложенной.

## Ручной review проверки качества перед публикацией

Владелец сначала разрешил подготовку, затем отдельно одобрил показанный diff и публикацию после проверок16.10.2026. Это разрешение относится только к двум парам ниже, не к будущим изменениям guard.

Предлагаются ровно две пары в `scripts/check-quality-floor.mjs`:

| Файл | Прежняя проверка | Новая проверка |
|---|---|---|
| `tests/local-registration-ui.test.mjs` | HTML `minLength="15"` | HTML `minLength="8"` |
| `tests/production-account-browser.mjs` | Точное множество signup keys без имени | То же множество плюс `name` |

Обе полные строки должны встретиться в diff ровно один раз, в одном указанном файле. Отсутствующая/изменённая/дублированная замена, другой путь, удаление иной проверки, skip/suppression, удаление теста, снижение порогов CONSTRAINTS по-прежнему блокируют. Нет wildcard, CLI bypass, изменения workflows или CONSTRAINTS. Guard остаётся эвристикой, не заменой семантического review; эти пары не дают права на будущие исключения. Для них добавлены отдельные позитивные и негативные regression cases.

## Проверка и откат

RED зафиксирован на прежней production-сборке: нет имени, новых переходов и прямоугольной CAPTCHA. Browser GREEN использует настоящий Next/Chromium, но изолированные API/CAPTCHA transport fixtures, не реальные письма/пользователей. Реальные транзакции, KDF, подтверждение, rollback и чтение имени проверяются отдельно на принадлежащем тесту loopback PostgreSQL 18. Рабочая доставка и живая внешняя CAPTCHA не объявляются повторно проверенными этим browser fixture.

Дополнительная интеграционная проверка воспроизвела перекрытие кнопки fixed-навигацией на320px: при высоте кнопки48px её центр попадал в ссылку нижней панели. Локальный `scroll-mb-28` добавляет112px отступа прокрутки и восстанавливает hit target; глобальный scroll/CSS не меняется. Проверка не ослаблена, весь owned PostgreSQL/HTTPS/browser suite после исправления127/127, без skips/cancels. Итоговые native1323/1323, guard17/17, production-build Chromium34/34 с axe и четырьмя ширинами; build/types/lint без ошибок (прежний targetType warning не скрыт). Намеренная мутация минимума до7 поймана и исходная политика восстановлена. Production-only npm audit0; прежние открытые build/dev риски этим не закрываются. Установка и повторная проверка рабочего сайта фиксируются отдельно.

Нет новых зависимостей, миграций, услуг, SSH-изменений, повышения ролей или операций над рабочими аккаунтами. Откат приложения не требует отката БД: добавленные профильные записи совместимы с прежним читателем. После возвращения старого кода пароли короче 15 символов потребуют повторной установки версии с политикой 8; не понижать scrypt и не сбрасывать пользовательские пароли ради отката. Полная готовность кабинета, платежей и массового запуска этим инкрементом не заявляется.
