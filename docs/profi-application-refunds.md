# Возвраты за отклики: исследование для F02

01.11.2026. Указание владельца: обычные возвраты относятся к размещениям; для платы за отклик изучить подход Профи.ру — отсутствие просмотра5дней либо выбор другого специалиста до просмотра. Это уточнение **не означает** обычный безусловный возврат за отклик и не разрешает реальные операции.

## Что подтверждено внешними источниками

Через Firecrawl прочитаны целиком две официальные статьи, на страницах указана дата13.05.2026:

- [Условия компенсации платы за отклик](https://help.profi.ru/ru/articles/3080495).
- [Описание тарифа «Отклик»](https://help.profi.ru/ru/articles/3590909).

Профи.ру предусматривает автоматическую компенсацию после5дней без просмотра; ожидание не требуется, когда заказчик выбирает иную кандидатуру или отменяет заказ до открытия предложения. Уже просмотренный отклик сам по себе не даёт такого основания, даже после отказа/отмены. Есть дополнительные исключения, связанные с раскрытием контактов и абонементами. Следовательно, у них оплачивается доступ к потенциальному заказчику, получение работы не гарантируется.

Это публичные продуктовые правила, **не доступ к внутреннему коду/БД Профи.ру**. Две статьи не доказывают технический механизм транзакций, точный расчёт границы суток или перевод непосредственно на банковскую карту. Дополнительный поиск не подтвердил способ зачисления; не выдавать его за установленный факт.

## Сопоставление с БЛИЖНИМ

В БЛИЖНЕМ нет абонементов и внутренних переписок; контакты заказчика публично скрыты. Эти функции не добавляются ради копирования внешнего сервиса. Ранее согласованное письмо/уведомление об отказе и закрытие заказа при выборе исполнителя сохраняются.

Подтверждена предпосылка ошибки будущего авторасчёта: текущий `app.applications.status` хранит одно состояние, отдельного неизменяемого first-view факта нет. `PostgresApplicationStore.decide()` переводит как `sent`, так и `viewed` в `rejected`; после этого текущая строка не позволяет узнать, открывали ли контакты раньше. `read()` отдаёт detail отдельно от `decide('viewed')`. Если сначала показать контакты, а отметить просмотр следующим запросом, конкурирующий выбор исполнителя/таймер может ошибочно признать отклик непросмотренным. Поэтому **нельзя** рассчитывать возврат только по нынешнему статусу или отметке браузера.

Следующий безопасный инкремент F02:

1. Неизменяемый first-disclosure журнал и серверная фиксация перед выдачей контактов получателю. Самопросмотр исполнителя, список карточек и техническая проверка статуса не считаются просмотром заказчика. Повтор не меняет первую дату. Сохраняется факт просмотра после отклонения/выбора другого исполнителя.
2. Отдельный финансовый policy anchor для новой оплаченной доставки; начало ожидания связано с подтверждённым `sent_at`, не с черновиком/checkout. Для нашей реализации предлагается120часов серверного времени; это инженерное определение БЛИЖНЕГО, не доказанный внутренний таймер Профи.ру.
3. Выбор другого исполнителя, просмотр и резервирование возврата сериализуются по одному заказу/отклику. Если возврат уже зарезервирован, поздний запрос контактов не должен одновременно дать услугу и компенсацию. Текущая механика выбора единственного исполнителя относится к заказам; вакансии не превращать автоматически в такой же эксклюзивный процесс.
4. Неизменяемый refund journal, один ключ операции и неизменные amount/payment binding. Authoritative provider readback, full/partial totals, повторы, unknown commit и late events обрабатываются до изменения прав на услугу. Кошелёк/внутренний баланс не добавлять без отдельного продуктового решения.
5. Старые `rejected` без истории просмотра не считать автоматически непросмотренными. Требуется явный legacy/unknown статус и ручная сверка; отсутствие журнала не доказывает право или отсутствие права на компенсацию.

Открыты для финансового контракта: частичные возвраты за размещение и их влияние на период; распространение специальных правил на вакансии; правила при отзыве отклика самим специалистом. Не подменять их предположениями из другого сервиса. Обычный отказ от уже просмотренного предложения не создаёт автоматическое основание по проверенному подходу.

## Критерии проверки следующего инкремента

До/после5дней; первый/повторный просмотр; просмотр перед/после выбора; непросмотренный отклик при выборе другого; просмотренный затем отклонённый; запрет самопросмотра; отказ БД/COMMIT без раскрытия контактов; два worker и один возврат; событие провайдера до/после polling; недоставленный оплаченный отклик; исторические строки с неизвестным просмотром. Всё сначала на синтетическом стенде, без изменения LIVE и настоящих возвратов.

Автоматический возврат пока **не реализован и не включён**. Этот документ фиксирует проверенное основание и зависимость от корректного учёта просмотров; текущий завершённый инкремент F03 защищает версии публикаций при оплате отдельно.
