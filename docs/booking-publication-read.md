# Точечное чтение публикации для бронирований

19.10.2026 владелец разрешил после проверок выдать существующей `blizhniy_runtime` только `SELECT(is_paid,published_at,expires_at)` на `app.listings`. Это отдельное разрешение чтения, не изменение роли пользователя и не право назначать оплату или публикацию.

`scripts/grant-booking-read.mjs --plan` показывает фиксированные три поля и полный SHA-журнал 18 миграций. Явный запуск `--apply HOST:DATABASE` проверяет точную цель подключения, PostgreSQL18, весь журнал, отсутствие привилегированных атрибутов роли, широких табличных прав, делегирования, REFERENCES и INSERT/UPDATE новых полей. До/после сравниваются все колоночные права `app.listings`; разрешено изменение только трёх SELECT-битов. Операция транзакционная, с lock/statement timeouts и общим операторским advisory lock. Результат неизвестного COMMIT не повторяется автоматически: сначала read-only проверка ACL.

Запускать только из защищённой операторской среды с owner-доступом и TLS verify-full. Ключи/пароли не в аргументах, Git или журнале. Приложение, startup и deploy не вызывают этот оператор и не содержат owner-доступ.

После применения свежий runtime-login должен успешно выполнить SELECT трёх полей с LIMIT0, а три UPDATE этих полей с WHERE false — получить42501. Проверка не меняет записи. Журнал остаётся на0018, дополнительных схем/таблиц не создаётся.

Откат приложения не требует отзыва добавочного чтения. Если нужно отдельно вернуть ACL, после проверки точной цели отзывается **только** `SELECT(is_paid,published_at,expires_at)`. Табличный `REVOKE SELECT ON app.listings` использовать нельзя: PostgreSQL также снимает предшествующие колоночные SELECT-права, необходимые остальным функциям.

Локальная реальная PG18 fixture проверяет повторную идемпотентную выдачу, отсутствие финансовой записи, неправильный журнал, остаточные UPDATE/table-wide/grant-option права и неизвестный COMMIT. Негативная fixture восстанавливает точный исходный ACL после своего тестового табличного REVOKE; это не обход проверки рабочего оператора. Инверсия проверки HOST:DATABASE воспроизводимо ломает native-тест; исходное условие восстановлено.

Текущее production-применение и результат свежего runtime-login фиксируются в `docs/bookings.md`, а не подразумеваются наличием этого файла.
