# Яндекс.Метрика: runtime-настройка и проверка

Этот документ описывает включение и приемку интеграции. Наличие кода или успешный локальный тест не подтверждает выпуск на VPS, настройку настоящего счетчика или получение визита Яндексом.

## Настройка

Единственная настройка ID — `BLIZHNIY_YANDEX_METRICA_ID`. ID публичный: это положительное целое число из настроек принадлежащего проекту счетчика. Пустое, отсутствующее или некорректное значение выключает интеграцию. В репозитории нет рабочего ID по умолчанию. Синтетические значения из тестов использовать для production нельзя.

`src/lib/metrica-config.ts` проверяет ID. Сервер читает текущий runtime env через allowlisted ключ `metrica-id` в `src/lib/public-runtime-config.ts`. Layout помещает проверенный ID в `meta[name="blizhniy-metrica-id"]` текущего HTML и передает его компоненту `YandexMetrica`. При вызове конфигурационного reader в браузере источником служит только эта meta; встроенного build-time fallback нет. Настройка не дает прав доступа к кабинету или Метрике.

Добавить ID в выбранный защищенный env-файл web-приложения на VPS, сохранив существующего владельца и права. Проверить отсутствие конфликтующего значения в более приоритетном env-файле или окружении PM2. Не выводить содержимое env-файлов в терминал или CI: рядом находятся закрытые настройки.

`scripts/deploy-release.sh` переносит `.env`, `.env.local`, `.env.production`, `.env.production.local` из предыдущего релиза целиком. Отдельного allowlist ключей deployment нет. Добавлять ID в GitHub build secrets, manifest, `ecosystem.config.cjs` или `/etc/blizhniy/web-runtime.json` не нужно. Смена runtime env требует нового web-процесса и нового документа в браузере. В стандартном выпуске процесс запускается с `--update-env`.

Выпуск выполнять существующим pipeline: push в `main` запускает deployment после validate/security/CodeQL. Миграции БД, платежные настройки, mail worker и изменения grants для Метрики не требуются.

## Настройки настоящего счетчика перед активацией

Проверить этот список в интерфейсе принадлежащего проекту счетчика до установки его ID в runtime. Это требования к будущему включению, а не подтверждение, что настройки уже выполнены. Используется базовая публичная статистика после явного согласия; Метрику Про, рекламные кампании и платные дополнения в рамках этой работы не подключать.

- [ ] В поле **Адрес сайта** указано **`ближний-ру.рф`**, кириллицей, без `https://`, пути и параметров. Именно такой ввод кириллического домена, без Punycode, предписывает [инструкция создания счетчика](https://yandex.ru/support/metrica/ru/general/creating-counter). Это правило поля в интерфейсе Яндекса; существующий канонический origin приложения в коде из-за него не менять.
- [ ] Включен прием данных только с заданных адресов сайта; посторонние домены, staging и локальные адреса не добавлены. Проверить настройку после сохранения по [справке счетчика](https://yandex.ru/support/metrica/ru/general/counter-general).
- [ ] **Автоматические цели выключены.** Они могут фиксировать отправку форм, клики по телефонам/email и поиск; ручной `hit` не заменяет проверку этой настройки. См. [автоматические цели](https://yandex.ru/support/metrica/ru/general/auto-goals).
- [ ] **Вебвизор, карта скроллинга, аналитика форм и карты кликов/ссылок выключены** в настройках счетчика; соответствующие отключения в коде также сохранены.
- [ ] **Использовать дополнительные настройки отслеживания** и **Запоминать маскированные данные** выключены. Автоматический Advanced Matching и сбор контактов не включены. Нет ручных вызовов `firstPartyParams`/`firstPartyParamsHashed` или передачи контактных данных через другие методы. Автоматический и ручной способы — отдельные механизмы, описанные в [Advanced Matching](https://yandex.ru/support/metrica/ru/general/advanced-matching); названия настроек контактов — в [настройке счетчика](https://yandex.ru/support/metrica/ru/general/counter-general).
- [ ] Ecommerce/автосбор покупок, контентная аналитика и дополнительные теги выключены. Для этого включения не настраиваются Яндекс Тег Менеджер, CRM, чаты, коллтрекинг, импорт клиентских данных и другие интеграции. Счетчик не связывается с Директом/РСЯ, рекламные аудитории и кампании не запускаются.
- [ ] Сохраненные значения повторно открыты и проверены. Зафиксированы ID счетчика, домен, дата и состояния переключателей; логины, сессии и закрытые данные аккаунта в evidence не включены.

Параметры `init` ограничивают нашу интеграцию, но не являются доказательством всех настроек на стороне Яндекса. Отсутствие доступа к настоящему счетчику означает **BLOCKED: настройка счетчика не подтверждена**; подстановка ID из fixture этот этап не закрывает.

## Ограничения первой интеграции

Используется базовая статистика публичных страниц. Вебвизор, карты кликов, автоматический сбор внешних ссылок и hash, ecommerce и дополнительные теги не входят в этот режим. URL, referrer и заголовки вручную отправляемых событий должны соответствовать принятой публичной политике маршрутов; в них не включаются данные аккаунта, форм, платежей и токены. Фактическое поведение сторонней библиотеки отдельно проверяется с настоящим счетчиком по процедуре ниже.

Параметры URL (включая поисковые строки и UTM) и фрагменты исключены из ручных событий. Карточки, профили продавцов, категории и профессии объединяются в группы маршрутов, поэтому в этой версии нет детализации по конкретным карточкам и рекламным меткам. Разные карточки учитываются отдельными просмотрами, но их локальный ключ перехода не передается Яндексу. Неизвестные новые маршруты требуют явного добавления в публичную политику.

Выбор аналитики отделен от технических cookie. Старое нажатие «Понятно» в информационном сообщении о cookie не означает согласие на новый счетчик. Проверять загрузку и остановку аналитики вместе с актуальным пользовательским выбором.

При валидном ID CSP добавляет только `https://mc.yandex.ru` в `script-src`, `connect-src` и `img-src`. Сохраняются nonce, `strict-dynamic`, запрет inline-обработчиков, прежние ограничения frame/style/worker и режим CSP. Библиотека должна получить nonce исходного документа, в том числе после SPA-перехода. Запрос `tag.js` выполняется с `crossorigin=anonymous`. Это позволяет браузеру применить CORS к ответу Яндекса при строгом `COEP: require-corp`. Настройки `unsafe-inline`, `unsafe-eval`, общие `https:` или `*.yandex.ru` для запуска счетчика не нужны.

Официальная документация описывает [nonce и CSP](https://yandex.ru/support/metrica/ru/code/install-counter-csp), [параметры инициализации](https://yandex.ru/support/metrica/ru/code/counter-initialize) и [SPA: defer, hit, destruct](https://yandex.ru/support/metrica/ru/code/counter-spa-setup). Полный список адресов в справке охватывает дополнительные возможности и регионы. Если реальный базовый счетчик обращается к другому origin, сначала установить назначение запроса; дополнительное разрешение должно быть точечным и проверенным.

## Проверка перед включением

Под Node 22.23.3 focused-конфигурация и CSP проверяются командой:

```bash
node --experimental-strip-types --test \
  tests/metrica-config.test.mjs \
  tests/public-runtime-config.test.mjs \
  tests/html-csp.test.mjs \
  tests/html-csp-middleware.test.mjs
```

Сохранить обязательные `npm run check:floor`, `npm run check:types`, `npm run lint`, `npm test`, `npm run build` и действующие CI/security gates. Browser transport fixture проверяет поведение приложения; он не доказывает получение событий настоящей Метрикой.

После сборки без ID запустить `node scripts/check-yandex-metrica.mjs` с установленным Playwright Chromium (`bash scripts/prepare-ci-browser.sh`). Runner поднимает собственный временный HTTPS-стенд на loopback, использует только синтетический ID, подменяет библиотеку записывающим вызовы stub и блокирует внешний трафик. Проверяются отдельное согласие и старое acknowledgement, отказ/отзыв, синхронизация вкладок, приватный маршрут, SPA/back, поздняя загрузка, закрытое хранилище, недоступная библиотека, размеры экрана, очищенные вызовы, CSP enforce и runtime выключение ID. Проверка включена обязательным шагом в `validate` после production build, до упаковки. Нет браузера или не поднялся стенд — проверка не пройдена; это не основание объявлять успех или пропускать gate.

На production build проверить пустой и невалидный ID, отказ загрузки библиотеки, повторный mount, прямой вход, SPA-переходы и back/forward. При выключенной аналитике не должно быть ее сетевых запросов. При включенной — один экземпляр счетчика и один просмотр принятого перехода. Отдельно проверить переход в приватный маршрут во время загрузки скрипта и прекращение работы после отзыва выбора. Блокировка Метрики не должна ломать навигацию, CAPTCHA или вход.

Для runtime-проверки собрать приложение без ID и запустить один и тот же артефакт с разными синтетическими ID при изолированном транспорте: HTML и вызовы должны использовать настройку процесса, а не старое значение сборки. После настоящего выпуска зафиксировать SHA, корректный ID в ответе, отсутствие новых CSP violations, реальные запросы базового счетчика и появление контролируемого визита в интерфейсе Яндекса. Эти факты фиксируются отдельно от локальных результатов.

## Приемка настоящей библиотеки и получения визита

Все пункты ниже выполняются с сохраненными настройками из предыдущего списка и настоящим ID проекта. Загружается оригинальный `tag.js`, без подмены тела скрипта или ответов отправки событий. Browser smoke со stub проверяет вызовы приложения и гонки согласия; он не подтверждает работу настоящей библиотеки, сетевую совместимость CSP, выключение серверных функций или доставку данных в Яндекс.

1. Зафиксировать SHA/build, ID из нового HTML и время проверки. В новой браузерной сессии без согласия убедиться, что Метрика не загружается; отказ от аналитики также не начинает ее загрузку. После явного согласия на публичной странице проверить реальную загрузку библиотеки и передачу базового просмотра. Официальная [проверка счетчика](https://yandex.ru/support/metrica/ru/general/check-counter) учитывает отложенную загрузку: для нашего сайта сначала требуется пользовательский выбор.
2. В Network и консоли проверить назначение запросов, фактические URL/referrer/payload и CSP. Использовать только синтетические маркеры: строку поиска, query/hash и идентификатор тестовой карточки. Эти значения, поля форм и частные пути не должны попадать в передаваемые аналитические данные. Проверить публичные переходы, переход между двумя разными карточками, back/forward, затем переход в кабинет/авторизацию и отзыв согласия, в том числе во время загрузки библиотеки. После остановки не должны инициироваться новые просмотры или автоматические события; уже начатая перед отзывом отправка не считается гарантированно отмененной вызовом `destruct`.
3. Если требуемый базовый запрос блокируется CSP или реальный SDK отправляет дополнительные события/данные, приемка не пройдена. Сначала установить причину и назначение запроса; не расширять CSP до общих доменных масок, `https:`, `unsafe-inline` или `unsafe-eval`. После конкретного исправления повторить сетевую проверку. Убедиться также, что блокировка Метрики не нарушает навигацию, CAPTCHA и вход.
4. В интерфейсе именно этого счетчика найти контролируемый визит и ожидаемые публичные просмотры после обработки данных сервисом. Проверить, что фильтр собственных посещений не исключил проверяющего. Сохранить минимальное обезличенное подтверждение результата. Успешная загрузка скрипта, HTTP-ответ или вызов stub сами по себе не подтверждают появление визита.

Активация подтверждена только при совместном результате: настройки реального счетчика проверены, настоящая библиотека проходит сетевую/privacy/CSP-приемку, контролируемый визит виден в Метрике. Если любой пункт недоступен, записать **BLOCKED/NOT RUN** с конкретной причиной; не заменять его локальным PASS и не объявлять live-подключение завершенным.

## Выключение

Удалить или обнулить `BLIZHNIY_YANDEX_METRICA_ID` в фактическом защищенном runtime env, затем перезапустить web-приложение штатным способом. Проверить новый документ: ID отсутствует, новые разрешения CSP не добавлены, обращения к Метрике не начинаются. Уже открытые документы могут продолжать прежний lifecycle до обновления страницы или выключения аналитики через пользовательский выбор. Это не обещание мгновенного удаленного отзыва кода из всех открытых вкладок.

Откат аналитики не требует SQL, удаления данных приложения или ослабления CSP. При необходимости отката кода использовать прежний проверенный артефакт и обычную проверку health/readiness.
