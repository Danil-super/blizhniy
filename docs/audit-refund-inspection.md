# F02: чтение состояния перед полным возвратом

Локальный инкремент02.11.2026. `createPrimaryYooKassaRefundInspection` собирает сведения для полного возврата первоначальной TEST-покупки `listing`, `vacancy` или `workRequest`. Это отдельный server-only reader, без подключения к маршрутам, БД или обработчикам. Он не отправляет возврат и не разрешает финансовую операцию. Ручной стенд остаётся на схеме35; рабочая БД и два российских сервера не меняются.

## Проверяемый контракт

Три последовательных GET используют один прежний transport budget:35 секунд, максимум3 HTTP attempts,64KiB на ответ и2048 chunks. Адрес фиксирован `https://api.yookassa.ru`, redirects запрещены, cache отключён. Сначала читается исходный платёж, затем `GET /v3/refunds?payment_id=<original ID>&limit=100`, затем платёж снова. Исходные ID, магазин, TEST, сумма и metadata проверяются в обоих ответах платежа. Конфигурация и ожидаемая привязка копируются до первого await.

В обоих ответах нужны `succeeded`, согласованный `paid` и строго `refundable=true`. По [официальному OpenAPI ЮKassa](https://yookassa.ru/developers/api/yookassa-openapi-specification.yaml), `refundable` обязателен, а `refunded_amount` необязателен и указывается при успешных возвратах. Поэтому отсутствие последнего не превращается в вымышленный ноль: результат содержит `reportedRefundedAmount=null`. Если поле присутствует, для этого полного возврата допустима только точная сумма `0.00 RUB`. Ненулевая/некорректная сумма требует отдельной сверки.

История должна иметь `type=list`, массив не более100 строк и не содержать `next_cursor`. [API использует пагинацию](https://yookassa.ru/developers/using-api/lists); одна неполная страница не доказывает отсутствие других возвратов. Текущий reader намеренно отказывает при любом cursor, включая null, вместо расширения общего лимита запросов. Более длинная история требует отдельного ограниченного обхода/операторской сверки.

Каждая строка проходит существующий строгий refund contract: UUID, исходный payment ID, положительная сумма не больше исходной, RUB, статус и календарная дата с nanosecond precision. UUID не могут дублироваться, включая различие регистром. Для новой полной операции принимается только история отменённых возвратов; `pending` и `succeeded` требуют сверки, включая возможный результат уже начатой собственной операции. Нельзя автоматически создавать новый ключ вместо восстановления прежней.

Если capture time присутствует в обоих снимках платежа, он должен обозначать один момент с полной точностью. Если он появился только во втором ответе, история всё равно проверяется относительно него. Отсутствующий capture не заменяется временем чтения. В возвращаемые сведения попадают только исходный payment ID, сумма/RUB, наблюдённый refunded_amount, число отменённых операций и время завершения чтения. Описания, банковские сведения и посторонняя metadata не сохраняются.

## Границы доказательства

`inspectedAt` — время локального наблюдения, не дата capture и не гарантия доступного остатка. Между последним GET и будущим POST возможна внешняя операция. Этот reader не проверяет финансового инициатора, договорное основание, допустимость способа оплаты/чека и исходное окно отправки. Он не заменяет окончательный допуск провайдера, reservation/request identity, журнал неизвестных исходов или однократное изменение услуги.

При любой сетевой ошибке, исчерпанном общем времени/attempts, неполной истории или противоречивом ответе сведения не возвращаются. Три успешных GET занимают весь нынешний attempt budget: retry расходует тот же бюджет и может не оставить попытки на финальный GET. Успех по старому снимку в таком случае запрещён.

Возврат после подтверждённого canceled, применение услуги, actual dispatch/provider refund ID, компенсации непросмотренных откликов и schema/ACL активация остаются отдельными открытыми этапами F02. LIVE, автоматические и настоящие возвраты выключены.
