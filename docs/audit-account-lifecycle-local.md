## Конкуренция и повтор после исправления

Два одновременных reset одного действующего токена дали200 и400 INVALID_RECOVERY:
одно увеличение auth-version, одна новая запись reset_notice, подходит только
пароль выигравшего запроса. После отдельного восстановления заблокированного
аккаунта блокировка/роль, профиль/legal и прежнее решение заявки сохранились;
обычный вход запрещён, rights-only доступ работает. Сессии проверки завершены.

Регистрация, resend и recover повторно прошли через обновлённый proxy:
чтение клона не потребляет исходное тело. Восстановление pending-аккаунта,
обычный вход новым паролем и последующий отзыв сессии также прошли.

Первый частный concurrent-harness по ошибке выбирал старое перехваченное письмо,
пока новое ещё ожидало worker. Прогон остановился на assertion; журнал сохранён.

Перед дополнительными входами бюджет проверен read-only; счётчики/окна не сбрасывались.

## Исправление локального proxy

Предварительный synthetic-email фильтр делал `request.clone().json()` до штатной
проверки метода/формата. GET или повреждённый JSON вызывали исключение, которое
превращалось в503. На настоящем HTTPS воспроизведено503 вместо405.

Теперь фильтр использует существующий `readAuthJson` и `authJson`: те же POST,
origin, JSON,4KiB и deadline; известные ошибки возвращаются400/405/413/415/422.
Неожиданные исключения сохраняют отказ503. Ограничение `.invalid` сохранено,
ошибки имеют no-store/nosniff/CSP и не содержат исходного тела.
Production account-handler и его бизнес-логика не менялись.

Новая воспроизводимая проверка:

```sh
node --experimental-strip-types scripts/check-local-account-auth-boundary.mjs
```

Она требует уже запущенный owned-стенд, проверяет его ID/image/labels и локальный
CA.27 случаев: register/resend/recover × GET/HEAD/PUT, malformed JSON, null/array,
неподходящий Content-Type, превышение размера и внешний email. Пароли, аккаунты
и письма не используются/не создаются. Это opt-in HTTP acceptance, не новый CI gate.

## Подтверждённый незакрытый R01: пользователи в админке

С обычной сессией настоящего локального администратора:

| Запрос | Ответ |
|---|---|
| `/api/account/login` | 200, роль admin |
| `/api/admin/deletion/list` | 200 |
| `GET /api/admin/users` | 403, Admin access required |

`AdminUsersClient.tsx` получает Supabase access token и обращается к legacy API;
`api/admin/users/route.ts` и `user-store.ts` не подключены к PostgreSQL аккаунтам.
Это существующий функциональный разрыв, не результат текущего исправления.
Наличие страницы `/admin/users` не считается её готовностью.

**Следующий большой функциональный блок:** перенести список/поиск/пагинацию
пользователей на действующую admin-сессию; затем операции блокировки и изменения
авторизационной роли с аудитом, проверкой ревизии и защитой последнего администратора.
Нельзя просто выдавать общей web-роли UPDATE(role,is_blocked): существующий admission
намеренно запрещает такие полномочия. Нужен точный операторский/DB-пакет с минимальными
правами и отдельным review перед установкой. Профили организации/специалиста
не следует превращать в новые административные привилегии по legacy label.
