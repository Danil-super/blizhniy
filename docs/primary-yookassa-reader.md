# Проверка известного платежа ЮKassa

Локальный этап L17 после [подготовки заказа](listing-checkout.md). Новый reader
пока не подключён к HTTP, worker или рабочей БД. Реальных запросов к магазину,
списаний, применения миграций и выдачи услуг на этом этапе нет.

## Решение и границы

Существующие проверки ответа и ограниченный HTTP transport выделены из
`payment-provider.ts` в общие модули. Это сохраняет один набор проверок суммы,
статуса, времени и hosted checkout URL для старого и нового контура вместо двух
расходящихся реализаций. Старый адаптер сохраняет прежнюю совместимость с
историческими платежами без полного metadata; новый её не наследует.

`createPrimaryYooKassaReader` принимает только серверную конфигурацию магазина.
`read` требует исходные привязки приватного intent и уже известный provider ID.
Вызывающий код должен получить их из доверенного хранилища, не из browser DTO.
Отсутствующий или неверный ID, другая конфигурация магазина/режима либо неверная
сумма отклоняются до сети. Режим `test_` — существующее правило конфигурации
проекта, не вывод из NODE_ENV и не универсальная гарантия формата ключей ЮKassa.

Запрос — только GET известного UUID на фиксированном `api.yookassa.ru/v3/payments`.
Нет POST fallback, нового платежа, ключа идемпотентности или автоматической смены
магазина. Redirect запрещён, cache no-store. Три попытки делят один бюджет35s,
включая чтение тела и backoff. Ответ ограничен64KiB и2048 chunks, в том числе
пустых; превышение отменяет чтение. HTTP4xx/429 не повторяются,5xx/сетевая ошибка
могут повторить только тот же GET. Сообщения провайдера/транспорта не выводятся.

Успешный HTTP-ответ ещё не является успешной оплатой. Проверяются точный UUID,
RUB/сумма без float, исходный магазин, test/live, четыре metadata-привязки
localPaymentId/targetId/targetType/tariffId и согласованность status/paid.
`waiting_for_capture` не становится `succeeded`. Время captured_at необязательно;
его отсутствие не заменяется временем запроса или создания заказа. При наличии
сохраняется исходная точность до9 дробных знаков, дата проверяется. Результат не
содержит карточных данных, recipient, description или постороннего metadata.

Reader не пишет финансовый статус, не публикует объявление и не продлевает срок.
Следующий этап — доверенное сохранение сверки и атомарное однократное исполнение
для точной одобренной версии. Затем нужны dispatch/recovery неизвестного исхода,
webhook/история/возвраты, API/UI и sandbox E2E. Наличие reader не закрывает оплату
или полный перенос. Новая production schema/права и выпуск ожидают отдельного
допуска; отложенное владельцем ручное ревью не считается выполненным.

## Проверки

Direct-import тесты используют настоящий validator/transport и синтетический
fetch, без чтения merchant credentials. Старые regression assertions сохранены;
их loaders научены загружать выделенные реальные модули. Дополнительно проверены
чужие привязки, пропущенный metadata, приватные поля, held/missing capture,
неверные дата/redirect, отказ до сети,404 без POST, повтор503 только GET, bytes и
пустые chunks. RED воспроизведён для лишнего metadata и отсутствующего chunk cap,
затем исправлен. Общее native1543/1543 и изолированные платёжные PostgreSQL17
регрессии76/76 прошли без пропусков. Production build завершён с exit0, types и
floor чистые, lint0errors с одним прежним предупреждением. Временное отключение
проверки магазина сломало отрицательный тест; условие восстановлено, direct-import
набор10/10 снова зелёный. Это проверка кода, не sandbox E2E с настоящей ЮKassa.

Документация перед реализацией получена через Context7: API ЮKassa
`/websites/yookassa_ru_developers_api` (GET payment, recipient/status) и Node22
`/nodejs/node/v22_20_0` (abort и чтение stream).
