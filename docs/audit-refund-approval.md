# F02: решение администратора о полном возврате размещения

Локальный инкремент 0042. Не активирован в HTTP, фоновой очереди или production. Реальных обращений к ЮKassa нет.

Владелец согласовал только полный возврат платы за размещение по решению администратора с обязательной причиной. Размещение прекращается после подтверждённого возврата. Частичные возвраты не добавляются. Компенсации непросмотренных откликов — отдельная политика: пять дней без просмотра, выбор другого исполнителя до просмотра либо снятие/удаление заказа заказчиком до просмотра.

## Что реализовано

- Неизменяемое решение с уникальной исходной оплатой, автором, причиной, полной исходной суммой и временем. Клиент передаёт только ID решения, ID оплаты и причину; финансовые поля вычисляются из исходной покупки.
- Повтор требует того же ID, администратора и причины, в том числе после завершённого возврата. Потеря подтверждения COMMIT восстанавливается чтением того же решения.
- Текущая подтверждённая сессия администратора проверяется приложением и независимо SQL-триггером; после ожидания финансовых блокировок повторно проверяется время истечения. Блокировка второго пользователя — NOWAIT, чтобы не создавать взаимную блокировку авторизации.
- Поддержаны TEST-размещения объявлений, вакансий и заказов. Бесплатная анкета, отклики и остальные типы не принимаются этой политикой. Merchant и TEST проверяются перед обработкой.
- Исходный запрос и SHA256, привязка провайдера, подтверждённый capture и первоначальный чек проверяются до решения. Строковые бюджеты SQL совпадают с UTF16-бюджетами JavaScript. Для return URL поддержан ограниченный набор HTTPS с ASCII DNS-именем и необязательным портом443; исторические нестандартные адреса требуют отдельного разбора.
- Обработка использует существующие reservation0036, request0037, inspection, journal0038, dispatch0039 и effect0040. Существующий reservation с другим ключом блокируется для операторского восстановления. Новый ключ автоматически не назначается.
- Известный provider ID восстанавливается через GET, включая истёкшее окно отправки и уже завершённый возврат. Повторного POST нет; сетевой запрос выполняется вне транзакции БД.

Полный возврат в поддерживаемой схеме чеков использует исходные данные чека согласно [документации ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/refunds). Это не доказательство успешной регистрации реального чека: наблюдение фискального результата и приёмка конкретного магазина ещё открыты.

## Проверка

Команда `node --test tests/placement-refund-approval.test.mjs tests/placement-refund-approval-postgres.mjs` прошла17/17, включая14 подзадач реального PostgreSQL18.6 на полном составе0001–0042. Проверены обычный пользователь, заблокированный администратор, другой merchant, отсутствие capture, истечение сессии во время настоящего row-lock wait, узкие права SQL, потеря COMMIT ACK, Unicode/чек/URL и невозможность менять историю.

Сценарии с чеком и без него проходят решение → резерв → подготовку → inspection → подменённый POST → авторитетный GET → однократное прекращение размещения. После завершения и после истечения исходного окна повтор остаётся GET-only. Права новой роли проверены для решения; интеграционная обработка использует владельца только внутри одноразовой синтетической БД и не доказывает ACL будущего production worker.

Полный native-набор2532/2532, без пропусков; floor/types/lint прошли. Сохраняется прежнее предупреждение `targetType` в `tests/checkout-prerequisites.test.cjs`. Сборка прошла. При намеренном удалении финальной проверки срока сессии соответствующий PostgreSQL-тест упал; миграция восстановлена побайтно, выполнен повторный GREEN.
