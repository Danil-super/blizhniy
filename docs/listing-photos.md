# Привязка фотографий к черновику

## Подготовленный слой хранения

Готовый приватный media-object хранится на VPS, в PostgreSQL — его метаданные. Привязка принимает UUID файлов, а не URL/пути/owner или клиентский признак готовности. Это дополнение L10, не разрешение включать local-only worker в production, не загрузка или публичная выдача фотографии.

Добавляется отдельная `0013-listing-photos.sql` и явный план `includeListingPhotos`; существующие планы7/10/11/12 и hashes не меняются. Автоматического применения, grants или backfill нет. Таблица хранит listing_id/media_id/position, FK не дают висячих ссылок, повтор фото в одном объявлении запрещён. Позиция ограничена существующим глобальным бюджетом10000 объектов, не новым продуктовым лимитом фотографий. Удаление связи не удаляет файл/metadata и не освобождает quota. Down отказывает при непустой таблице; откат приложения сохраняет additive schema и данные.

Серверная операция сверяет действительную App-сессию/expectedOwnerId, draft ownership/status и точную revision. Фото должны быть ready и принадлежать тому же владельцу. Чужой, pending и неизвестный UUID одинаково недоступны; admin не обходит owner. Список заменяется целиком в одной транзакции; порядок сохраняется, revision увеличивается SQL CAS, stale/unknown outcome требует readback без retry. Порядок locks: user → session → draft; ready-state/owner metadata неизменяемы существующим SQL trigger. Перед подключением HTTP/UI нужны ограниченный контракт, column grants verifier и реальные проверки загрузки/выдачи, а не URL из старого хранилища.

`PostgresListingPhotoStore.read/replace` возвращает `{id,revision,photos}`, где каждое фото содержит только `{id,mimeType,width,height,size}`. Нет hash/owner/пути/URL/attempt. UUID media канонизируются до lowercase UUIDv4, массив ограничен существующим storage budget10000, дубликаты/дыры/пути/объекты запрещены. Ready и принадлежность проверяются до удаления прежних связей; чужой/pending/unknown элемент откатывает весь список. Даже добавленная оператором ошибочная чужая связь закрывает чтение, а не раскрывает metadata. Замена не меняет core текста, но повышает общую listing revision, поэтому параллельный старый редактор получает конфликт. Metadata immutable/ready transitions охраняются0006; runtime этого слоя не получает UPDATE media или SHA256 SELECT.

Лимит10000 — верхняя граница внутренней SQL работы, не предложение загружать столько фотографий в форме. HTTP дополнительно ограничен64 КиБ JSON. Общие160 МиБ проверяются на сервере по доверенным размерам готовых объектов до unlink; ровно80 объектов по2 МиБ допустимы,81-й отклоняется с сохранением прежнего списка/revision. Это не заменяет ограничение исходного ввода160 МиБ и decoder10 МиБ/24MP до reservation: исходный файл и нормализованный объект — разные величины.

## Закрытый HTTP ассоциаций

`/api/account/listing-photos` доступен только explicit postgres-mode. POST `{expectedOwnerId,listingId}` читает owned draft photo snapshot; PUT `{expectedOwnerId,listingId,expectedRevision,photoIds}` целиком заменяет связи. Это не upload endpoint: нет байтов/URL/файловых имён, произвольных metadata или права отмечать файл ready. GET405; POST/PUT вне PostgreSQL404. Body4096/65536 bytes, deadline2s; cookie-only identity, Host/Origin/custom-header/Sec-Fetch/query/ingress проверки и общий session limiter не заменены и не отключены.

Ошибки401 UNAUTHENTICATED,404 DRAFT_NOT_FOUND (также чужой/pending/unknown media),409 DRAFT_CHANGED,422 INVALID_INPUT (в том числе суммарный размер),429 RATE_LIMITED/Retry-After900,503 PHOTOS_UNAVAILABLE. Unknown write не повторяется; readback сверяет current revision и список. Ответы no-store/no-referrer/nosniff/CSP с request ID; audit только operation/status/code/duration/request ID, не photo/listing/user ID, пути или причина SQL. Runtime использует verified Auth pool и narrow LIMIT0 preflight; это не полный privilege verifier и не auto-provision.

`tests/production-listing-photo-http.test.mjs` проверяет настоящий boundary/handler/route с synthetic store; отдельный PG case соединяет настоящий Request→cookie guard→общий limiter→ограниченную SQL роль и lost-ack readback без retry. Production Next browser fixture отдельно вызывает реальный route для отказа Bearer/privileged input **до** private runtime; остальные account/draft browser regressions сохранены. Ни один из этих тестов не объявляется живой загрузкой/выдачей файла.

Проверка: `tests/listing-photo-schema-plan.test.mjs`, `tests/postgres-listing-photos.test.mjs` и owned loopback `tests/bootstrap-postgres-integration.mjs` с двумя новыми integration модулями. Проверены opt-in prefix/repeat/down, no PUBLIC/runtime grants, FK/duplicate/позиции, два владельца/admin/pending/unknown denial, CAS двух вкладок с конфликтом старого core, rollback после unlink/expiry-after-insert, отсутствие изменений metadata/budget и fresh-pool readback после simulated post-commit loss без retry. Файлов в этих новых PG fixtures нет: ready выставляет оператор синтетическим metadata, это не доказательство живой загрузки или реального фото.

Просмотр плана без подключения: `node --experimental-strip-types scripts/bootstrap-postgres.mjs --plan-listing-photos`. Применение — только операторская `--apply-listing-photos HOST:DATABASE` после подтверждения цели и префикса; deploy/app не применяют миграции. На рабочем сервере БД0013 и новые grants пока не применены. Незавершены upload/byte-serving HTTP, UI фото, production worker/каталог/ресурсные пределы, очистка и проверка файлов с настоящим новым аккаунтом. Слой хранения/ассоциаций не объявляется законченной работой фотографий.

## Локальная композиция загрузки байтов

`LocalMediaUpload.upload(token,intentId,source,mimeType,signal?)` соединяет существующие decoder, SQL reservation и `LocalMediaWriter`. Это local-only Linux development/test, не HTTP route и не переключение production. В рабочей композиции следует передавать `createLocalMediaWorker` и OS-fenced `createLocalMediaFileWorker`, а не raw decoder/file store; прежние guards не сняты.

Вход — канонический lowercase UUIDv4 одного намерения, скопированные до первого await байты не более10 МиБ, точный JPEG/PNG/WebP/GIF MIME. Авторизация через действительную App-сессию выполняется до decoder даже для нового intent. После обработки worker reply проверяется и копируется; reservation получает только нормализованные MIME/width/height/size/SHA256, не client metadata. SQL повторно проверяет сессию. Ответ содержит только `{id,mimeType,width,height,size}` — не bytes, путь, owner, digest или attempt.

Новый объект проходит reserve → committed one-shot claim → fenced FS → verified ready. Existing pending останавливается до decoder: даже отсутствие наблюдаемого файла не даёт права на повторную запись. Existing ready проходит повторную нормализацию и проверку одинакового **нормализованного** payload через reserve, затем owner-private чтение настоящего файла; второй claim/write не выполняется. Неизвестный reserve COMMIT не запускает FS. Неизвестный write/ready не сбрасывает attempt, не удаляет файл и не освобождает бюджет; успешный readback ready не требует второй записи. Исходы pending/unknown требуют отдельного recovery, которого этот модуль не реализует.

Abort учитывается до reservation и передаётся decoder; после начала мутации ограниченная однократная работа доводится до результата независимо от disconnect. Это не гарантия ответа отключившемуся клиенту и не разрешение retry после timeout. Конечные ошибки — `INVALID_MEDIA_UPLOAD`, ошибки изображения/занятости, owner denial, intent conflict/in-progress/quota; неизвестные причины сводятся к `MEDIA_UPLOAD_UNAVAILABLE` без cause/private diagnostics.

`tests/media-upload.test.mjs` проверяет последовательность, caps, подмену input, отказ сессии до decode/на reserve, pending/ready replay, unknown outcomes и abort до/после reservation. Дополнения `tests/media-file-postgres-integration.mjs` используют настоящие пиксели, restricted SQL и OS-fenced файловый процесс: EXIF/ICC отсутствуют, два владельца изолированы, один intent не списывает квоту дважды, конкуренция создаёт один claim/write, lost ready acknowledgement читается без повторной записи. Decoder в этом PG fixture raw/local; проверка systemd/cgroup supervisor остаётся отдельной `tests/media-worker-integration.mjs`, а не выдается за часть этого прогона. Публичный admission/stream/body deadline/лимитер, expectedOwner UI binding, выдача bytes, cleanup/retention и production sandbox всё ещё нужны до HTTP exposure.
