# Локальная постмодерация объявлений

Изменение включается только сочетанием `BLIZHNIY_LISTING_WORKFLOW=postmoderation`,
`BLIZHNIY_LOCAL_PRIMARY=enabled` и точного HTTPS loopback origin. На рабочем сайте
флаги не менялись. Старый режим и схема 24/25 по умолчанию сохранены.

## Блокировка

`0026-listing-blocks.sql` добавляет `app.listing_blocks`: одна неизменяемая запись
на объявление, с администратором, проверенной ревизией, датой и причиной. Блокировка
не переписывает статус размещения, оплату, срок или содержимое объявления. Она
имеет приоритет при отображении статуса в кабинете. Изменение текста владельцем
не удаляет блокировку. Разблокировка этим инкрементом не предусмотрена.

Сервер проверяет текущую роль и сессию внутри транзакции, затем блокирует строку
объявления, сравнивает ревизию и сохраняет решение. Конфликтующие решения получают
409. Точная повторная передача первоначального решения возвращает ту же запись.
При неизвестном исходе клиент предлагает перечитать объявление, не повторяет
запись автоматически. Собственные объявления администратора доступны наравне
с чужими; решение также сохраняет автора действия.

В одной транзакции создаются блокировка, уведомление существующего кабинета и
локальное письмо с причиной. `app.listing_block_mail` — **только перехват для
локального стенда**, не очередь SMTP. Настоящие письма не отправляются. Письма
содержат только ссылку на получателя, тему и текст; срок хранения 30 дней,
удаление пользователя каскадно удаляет записи. Локальный почтовый интерфейс
не должен возвращать записи после `expires_at`. Перед рабочим включением нужен
отдельно проверенный канал доставки и регулярное удаление истёкших записей.

В локальном режиме публичные SQL-запросы карточек, списков продавца, фотографий
и бронирований требуют отсутствия `listing_blocks`. Проверка блокировки
сериализуется на той же строке объявления, что изменение и публикация.
Прежние заявки на бронирование остаются в истории; создать или принять новую
на заблокированное объявление нельзя. Просмотр приватной истории не раскрывает
объявление публично.

## API

`POST /api/admin/listing-management` использует существующие cookie, CSRF,
проверку доверенного ingress, лимитер и `Cache-Control: no-store`.

| action | Поля сверх `action`, `expectedAdminId` |
|---|---|
| `list` | `after`: UUID или null, страницы по 20 записей |
| `inspect` | `listingId` |
| `photo` | `listingId`, `fileId` |
| `block` | `listingId`, `expectedRevision` строкой, `reason` 1–1000 символов |

Роли, автор, статус, стоимость и оплата из запроса не принимаются. Все
объявления доступны администратору независимо от наличия предварительной
модерации. Байты фотографий выдаются только после проверки доступа; URL объекта
браузера отзывается при смене фотографии и аккаунта. Журнал HTTP содержит
только тип события, случайный request ID, код, статус и длительность.

## Проверки

- `tests/listing-block.test.mjs`: причина, контракт, CSRF, cookie, точная форма
  запроса, неизвестный исход и отсутствие секретов в журнале.
- `tests/listing-postmoderation-public.test.mjs`: отдельные SQL-ветки старого
  и нового режима, публичные карточки/списки/фото и инвентарь бронирования.
- `scripts/check-local-listing-blocks.mjs`: строго проверяет владельца loopback
  контейнера и каноническую историю миграций, применяет только локальную 0026,
  проверяет минимальные права, конкурентные решения, откат уведомлений, потерю
  ответа, самоблокировку, отзыв прав и невидимость заблокированной публикации.
  Созданные технические пользователи удаляются; тест фото целиком откатывается.

Production-выкладка, LIVE, SMTP и реальные платежи этим документом не разрешаются.
