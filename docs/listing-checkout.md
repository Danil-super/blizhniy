# Серверная подготовка оплаты обычного объявления

Локальный срез L17, продолжение приватного [журнала](postgres-payment-intents.md).
Внешнее ревью предыдущего среза владелец отложил; разработка продолжается без
переключения рабочего сайта. Нет merchant POST, новой production schema/grants,
включения оплаты или публикации. Рабочая БД остаётся0018.

## Границы

`PostgresListingCheckoutStore` предоставляет `preview`, `prepare`, `readIntent`.
Все операции используют существующую app-session transaction, точный expected
owner, повторную проверку срока перед COMMIT и generic ошибки. Другой аккаунт,
неподтверждённый/заблокированный пользователь, data-subject/отозванная/истёкшая
сессия не дают авторизации. Изменений Auth/лимитов/SSH нет.

Намерение содержит только ID объявления, точную строковую revision, стабильный
creationKey и ожидаемые ID тарифа/цену/срок. Они являются **согласием с предложением**,
не источником финансовой истины: сервер заново читает действующий тариф из БД и
отклоняет расхождение. Контакт объявления не становится email плательщика.

Новая подготовка требует своей draft-версии, текущей approved-модерации,
корректной формы, активной категории/родителя, существующего города и собственных
ready-фото. Проверки формы переиспользованы, не скопированы. Порядок блокировок:
user → session → listing → moderation → вставка order → приватный intent.
Это point-in-time разрешение подготовки, не обещание неизменности справочников
навсегда и не право списывать после последующих изменений цели.

`prepare` сохраняет order и полный byte-exact provider/receipt snapshot в одной
транзакции. Отложенный составной FK не позволяет COMMIT с отсутствующим либо
иначе привязанным intent. Проигравший конкурент не строит новый чек для уже
сохранённого платежа. Неизвестный COMMIT проверяется по исходному creationKey;
автоматического повтора либо нового ключа/списания нет.

Один `(owner,creationKey)` навсегда относится к одному намерению. Один активный
платёж на `(owner,targetType,targetId)` обеспечен UNIQUE partial index, **без
revision в ключе**: редактирование/новая модерация не обходят прежний UNKNOWN.
Другой ключ при активном платеже — конфликт; preview возвращает существующий
платёж владельцу. Возраст записи сам по себе не снимает запрет.

Сейчас active включает created/pending/succeeded: финансовый успех без
реализованного исполнения не разрешает новое списание. Выпуск этого hold после
однократного исполнения, платное продление и возвраты нужно связать с будущим
fulfillment/lifecycle до включения провайдера; этот срез их не реализует.
SQL допускает только монотонные финансовые переходы, но **не доказывает**, что
ЮKassa подтвердила деньги. Runtime не получает права менять status. Нет кода,
выставляющего succeeded/failed/refunded или paid/published.

Приватный чек использует проверенный email из заблокированной транзакцией
учётной записи; browser/public contacts его не задают. Сохранённый чек не
перестраивается при смене тарифа, email, VAT или базового URL. При смене email
старые сессии отзываются существующим Auth; readback требует новую живую сессию.
DTO содержит только ID, ключ, цель/версию, тариф/цену/срок, статус и точное время;
email/body/hash/merchant binding туда не попадают.

## Миграция и ограничения выпуска

0020 включается только `includePaymentOrders:true`; CLI/deploy/startup её не
применяют. Это таблица orders, дополнительный UNIQUE/FK и guard. 0019 и первые18
hashes не меняются. Down проверен только на пустой новой таблице; непустая история
блокирует удаление. Рабочий rollback — прежний код с сохранением данных.

Подготовка имеет статус created, **не оплачено**, без выдачи услуги. Нулевой
тариф не отправляется провайдеру: требуется отдельное корректное no-charge
исполнение, пока оно не готово — явный отказ подготовки, не фиктивная оплата.
Нет HTTP/UI-подключения и merchant health/credentials preflight. Эти границы,
авторизация повторного dispatch, сверка/settlement, webhook, fulfillment, история
и возвраты остаются следующими этапами. Retention/export/erasure финансовых ПД и
точечные production права требуют отдельного решения до применения.

## Проверка

Контрольная точка19.10: native1533/1533 и PostgreSQL273/273, fail0/skipped0;
production build завершён с exit0, lint0errors (прежнее checkout warning),
floor/diff/staged Gitleaks clean. Сборка, прерванная перезапуском локальной среды,
не была засчитана; новый прогон завершён отдельно. Инверсия approved guard
воспроизводимо разрешила неподтверждённую подготовку и сломала отрицательный
SQL-тест; условие восстановлено, полный SQL-набор снова зелёный.

Actual-source module graph и loopback PostgreSQL18 с ограниченным runtime.
Проверяются модерация, owner/session, exact quote, конкуренция ключей, неизвестный
COMMIT, rollback order+body, истечение после записи, первоначальный payer email,
дрейф конфигурации, недоступные фото/справочники, active hold после редактирования,
составной FK, SQL-привилегии и down. Ни один provider запрос не отправляется.
Синтетические financial transitions тестируют SQL, не выдаются за settlement.

Команды: общий `tests/bootstrap-postgres-integration.mjs`, native suite и
`tests/listing-checkout-contract.test.mjs`, затем types/lint/build/floor/scanner.
Предыдущий immutable пакет внешнего ревью не перезаписывается этим срезом.
