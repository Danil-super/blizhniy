## Схема и оператор

`applications`, `booking_requests`, `notifications` — только новые частные таблицы с FK/индексами/конечными состояниями. Публикации, пользователи и первые17 миграций не изменяются. Цена брони — конечный numeric(20,2), snapshot ограничен16KiB, ключи намерений и событий уникальны. Принятое решение требует непустого decided_at; stay требует непустого end_date, а не SQL UNKNOWN. Проверка сначала воспроизвела NULL-лазейку и после исправления проходит.

Команды: `node --experimental-strip-types scripts/bootstrap-postgres.mjs --plan-interactions` и отдельный `--apply-interactions HOST:DATABASE`; grants: `node --experimental-strip-types scripts/grant-interactions.mjs --plan | --apply HOST:DATABASE`. Только явный оператор после разрешения, не startup/deploy. Default и прежние opt-in планы сохраняют прежнюю длину и SHA. Down берёт exclusive lock и отказывается при любой строке новых таблиц; накопленные данные не удаляются.

Runtime получает SELECT3 и перечисленные INSERT-поля. UPDATE откликов — сообщение/snapshot/references/revision/status, но не идентичность, is_paid, sent_at или timestamps создания; SQL state constraint не допускает unpaid sent/selected. UPDATE брони — status/decided_at/revision/updated_at, не цена/даты/гость. UPDATE inbox — read_at/dismissed_at, не получатель/текст/event. Нет hard DELETE/TRUNCATE/TRIGGER/REFERENCES/MAINTAIN, grant options или финансовых EXECUTE. Реализация guarded queries всё равно обязательна: колоночные grants не заменяют проверку предметного владельца.

Общая проверка точечных таблиц вынесена из service-grant оператора в `operator-table-grants.mjs`, чтобы не копировать политику для0018. Прежний service-план остаётся точным17 и использует тот же проверенный алгоритм. Табличные/колоночные SQL identifiers дополнительно проверяются до запроса; mismatch history/target/role/остаточных прав отказывает, неизвестный COMMIT не повторяется.

## Частный inbox: серверный срез

`postgres-notification-inbox.ts` хранит серверный event в транзакции предметной операции; unique(user,event) не допускает дубликата при конкуренции. Повтор с другим payload отказывается, первоначальный текст не перезаписывается. После конфликтующего INSERT выполняется отдельный SELECT с новым Read Committed snapshot, как требует PostgreSQL18; один CTE snapshot здесь недостаточен.

Чтение inbox и read/dismiss используют существующую cookie app-session transaction с проверкой текущего владельца и повторной проверкой срока перед COMMIT. Страница —20 записей, cursor сохраняет6 дробных знаков времени; DTO не содержит user_id/event_key. Изменения принимают1–20 уникальных явно показанных IDs: новые сообщения, пришедшие после открытия списка, не отмечаются прочитанными и не скрываются. Чужие IDs ничего не меняют; повтор read/dismiss не меняет исходное время. Никаких hard DELETE или произвольного создания сообщения для чужого аккаунта по HTTP.

`production-notification-inbox-http.ts` — handler factory для `/api/account/notifications`. Контракт POST `{action:"list",expectedOwnerId,after}` и PUT `{action:"read"|"dismiss",expectedOwnerId,ids}`; только same-origin Host/Origin/CSRF, доверенный ingress IP, канонический cookie, существующий session rate budget, JSON≤4096B и metadata-only audit. expectedOwnerId — защита от смены аккаунта, не источник полномочий. Инфраструктурные ошибки не превращаются в пустой успешный inbox.
