# Сверка статуса публикаций по сроку оплаты

Скрипт `supabase/maintenance/reconcile-expired-publications.sql` переводит оплаченные и неоплаченные строки `listings`, `vacancies` и `work_requests` из `published` в `expired`, когда их известный `expires_at` наступил. Он не меняет `is_paid` (сохранённый флаг), `published_at`, `expires_at` или платежи. Заархивированные, проданные, отклонённые, ожидающие оплаты, записи с пустым сроком и действующие публикации остаются без изменений. Публичные выборки независимо фильтруют paid flag и срок, поэтому таймер не является границей публичного доступа.

Действие восстановления объявления или вакансии меняет `published_at` на момент восстановления для существующего порядка выдачи, но сохраняет исходный `expires_at`. Дата возврата не означает новую оплату и не продлевает размещение. Запись с истёкшим или неизвестным сроком вернуть этим действием нельзя; новый срок потребует отдельного проверенного сценария оплаты и исполнения.

Миграция `20261007180000` добавляет `work_requests.is_paid=false` и `expires_at=NULL` без исторического backfill. Это описание локального контракта, а не подтверждение её исполнения в рабочей БД. Историческая проверка метаданных 25.09.2026 предшествует этим колонкам. `specialist_profiles` и бессрочные `fair_applications` сверка не затрагивает.

## Обязательный legacy gate — этот slice не готов к отдельному rollout

До применения новой публичной политики заказов нужен согласованный аудит исторических данных. Иначе новые default false/NULL скроют даже реально оплаченные старые заказы. Не считать false отсутствием финансовой оплаты, NULL истечением срока или `succeeded` гарантией исполненного размещения.

`supabase/maintenance/inventory-legacy-publication-entitlements.sql` — только инвентаризация: одна `REPEATABLE READ READ ONLY` транзакция, без DML, row locks и автоматических решений. Она работает до/после новых колонок, различает отсутствие колонки и NULL/default false, возвращает IDs, статусы, сохранённые даты, owner matching и snapshot/marker/outcome платежей. Контакты, тексты, credentials и checkout URL не выводятся. `window_state=known_future` означает лишь сохранённый будущий deadline, не финансовое одобрение. Отчёт содержит `manual_decisions_required=true`; не публиковать его как публичный endpoint или артефакт.

На изолированном стенде команда: `psql -X -v ON_ERROR_STOP=1 -d "$STAGING_DATABASE_URL" -f supabase/maintenance/inventory-legacy-publication-entitlements.sql`. Рабочая БД/provider сейчас не опрашиваются; production read-only inventory требует отдельного явного разрешения и минимальных read privileges. Не копировать `.env` или секреты в команды/отчёт.

Перед rollout оператор фиксирует evidence и решение по каждой неоднозначной когорте: missing capture/duration/window, несовпадающий payer/owner, несколько конфликтующих оплат, refunded, legacy marker без target window. Подтверждённое историческое окно можно восстановить только отдельной reviewed операцией для точных IDs и ожидаемых прежних состояний. Нужны исходный известный settlement anchor и доказанный приобретённый срок/существующий оплаченный deadline. Не использовать текущий `tariffs.duration_days`, день запуска или `published_at` после восстановления. Одноразовая миграция `20260927090646` с `greatest(paid_at,published_at)` не является рецептом новой сверки/backfill и не запускается повторно.

Неизвестные записи не демотируются и не ремонтируются этим SQL. Если право/срок нельзя доказать, rollout остаётся закрыт до явного ручного решения; не подменять его массовым скрытием исторически оплаченных карточек. Не публиковать автоматически архивные/отклонённые записи. `fulfillment_status=blocked` — отдельный outcome, не failed/refunded и не повод автоматического возврата. Sticky blocked и исторический NULL paid_at нельзя сбрасывать обычным PATCH, replay или отключением guard; такие решения требуют отдельной контролируемой reviewed операции. Этот slice её не предоставляет.

## Restore объявления и вакансии

Миграция `20261008063110_restore_listing_and_vacancy_within_paid_window.sql`, созданная Supabase CLI, добавляет `restore_listing_within_paid_window(uuid,uuid)` и `restore_vacancy_within_paid_window(uuid,uuid)`. Сервер передаёт только ID записи и текущего authenticated owner; время, срок, paid flag и статус не берутся из HTTP payload. Функции SECURITY INVOKER с пустым search_path, EXECUTE только у service_role. После `FOR UPDATE` и всех ожиданий `clock_timestamp()` проверяет текущего владельца, `is_paid=true` и известный исходный `expires_at > clock_timestamp()`. Объявление допускает прежние состояния sold/archived/expired; вакансия — только archived. Успех возвращает ровно `{id}`, отказ — пустой результат; подавленный UPDATE не считается успехом. Недоступный RPC не включает прежний app-clock PATCH fallback.

Изменяются только `status` и `published_at`: последний сохраняет существующую семантику даты возврата и сортировки, но теперь вычисляется по времени БД после блокировки. `expires_at`, paid flag и финансовая история не меняются. Эти функции сохраняют прежний контракт известного окна объявления/вакансии: не вводят новый payer/snapshot gate для legacy строк и не читают текущий тариф. Они не получают payment locks после target lock и не создают обратного направления к payment→target settlement. Более строгий контракт restore заказа и обязательные legacy/manual gates ниже остаются отдельными требованиями.

`Listing.expiresAt` и `DemoListing.expiresAt` optional: сохранённый NULL остаётся неизвестным и отсутствует в JSON, а известный timestamp передаётся без потери точности. Текущая дата или срок «+30 дней» не синтезируются. Публичные paid/expiry filters и allowlists приватных адресов/контактов остаются прежними. Исходная гонка могла вернуть успешный restore после deadline, но не давала новое окно: следующий публичный запрос исключал запись, owner list показывал эффективный expired, а UI ошибочно сообщал о публикации.

`node --test --test-reporter=spec tests/vacancy-restoration.test.mjs` исполняет полные исходные модули с заменой только внешнего Auth/REST fetch. Отдельный `node --test --test-reporter=spec tests/listing-vacancy-restoration-postgres.mjs` использует cached PostgreSQL17 с `--pull never --network none`, без ports/.env, tmpfs и read-only worktree mount. Его собственные container `blizhniy-publication-restore-pg17-20261008` и DB `blizhniy_publication_restore_fixture` проверяют grants, реальные ожидания строк, expiry crossing, owner/state/delete races, один физический UPDATE при конкуренции, suppression, rollback, исходную app-clock гонку и совместимость с `20261007180000`. Name collision сохраняет существующий container; cleanup проверяет owned label. Это синтетическая проверка, не production rollout или новое разрешение на legacy repair.

## Restore заказа и runtime границы

`restore_work_request_within_paid_window(uuid,uuid)` вызывается сервером с ID заказа и текущим authenticated owner, не HTTP-полями payer/duration. Только service_role имеет EXECUTE; функция SECURITY INVOKER с пустым search_path. Сначала owner/target-bound YooKassa succeeded candidates с известным capture, snapshot 1..365 и applied marker/outcome блокируются FOR SHARE в UUID-порядке; затем заказ FOR UPDATE. После ожидания проверяются текущий владелец, archived, paid flag, известный живой срок и точное равенство deadline исходному paid_at + snapshot × 24 часа. Время берётся clock_timestamp после locks. Current tariff lookup отсутствует; payment→target направление совпадает с settlement.

Успех возвращает одну строку `{id}`, отказ — пустой результат. Изменяется только status, ни одна дата/оплата/marker не меняется; suppressed UPDATE не считается успехом. Архивный expired/unknown/unpaid или оплаченный другим владельцем заказ не получает новое окно. Refund-first запрещает restore; restore-first удерживает candidate locks до commit. Последующий refund не реализует автоматическое снятие публикации: refund workflow остаётся отдельным prerequisite.

Публичные list/detail/metadata заказов требуют published + is_paid=true + известный живой deadline; fallback без image relation сохраняет те же filters. Повторная проверка после REST-ответа исключает уже истёкшую строку. Owner/admin по-прежнему видят приватные поля и эффективный expired только для известного прошедшего срока; NULL не фабрикуется. Application preflight проверяет live paid parent/current owner/no self-response, а settlement RPC независимо повторяет окончательные проверки под locks. Demo остаётся явно nonproduction; missing schema не включает status-only production fallback.

## Проверка и ввод в эксплуатацию

1. На отдельном стенде исполнить тест на временных таблицах: `psql -X -v ON_ERROR_STOP=1 -d "$STAGING_DATABASE_URL" -f tests/reconcile-expired-publications.sql`. Он проверяет границу `expires_at = now()`, действующие и архивные строки, сохранность истории оплаты и повторный запуск. Тест заканчивается `ROLLBACK`; в production не запускать его вместо основного скрипта.
2. После legacy gate снять резервную копию стенда и агрегатно подсчитать будущие изменения: `select count(*) from public.listings where status = 'published' and expires_at <= now();` и аналогично для `public.vacancies`/`public.work_requests`. Проверить права на все три UPDATE и поддержку статуса expired.
3. На стенде выполнить `psql -X -v ON_ERROR_STOP=1 --single-transaction -d "$STAGING_DATABASE_URL" -f supabase/maintenance/reconcile-expired-publications.sql`. Все три счётчика должны стать нулём; проверить кабинет/админку/публичную выдачу, неизменность оплаты/дат, сохранение действующих публикаций и NULL legacy.
4. Только после этого планировать production: согласовать время, сделать backup, записать агрегатные счётчики до запуска, исполнить тот же файл с production URL и сверить числа `expired_count`. Не включать таймер до успешного одиночного прогона и проверки сайта.

## Постоянный запуск на Timeweb

Релизный архив теперь включает `supabase/maintenance/reconcile-expired-publications.sql`. Локальный скрипт `scripts/reconcile-expired-publications.sh` запускает `psql` в одной транзакции и завершает службу с ошибкой, если SQL не исполнился или после него остались просроченные `published` строки. Публичного HTTP-обработчика и секрета для вызова через интернет нет.

Шаблоны `ops/systemd/blizhniy-expiry.service` и `ops/systemd/blizhniy-expiry.timer` рассчитаны на app VPS с релизным симлинком `/var/www/blizhniy`. Таймер запускает сервис каждые 15 минут; systemd не запускает вторую копию активного oneshot-сервиса. Включать его **только после** успешной выкладки этого кода, переноса БД и одиночной проверки подключения.

1. На сервере установить клиент PostgreSQL (`psql`) и создать отдельного системного пользователя `blizhniy-expiry` без входа в shell. SQL-сервису нужен только доступ к БД и на чтение файлов текущего релиза. Если база на отдельном Timeweb VPS, указать её приватный адрес и проверить сетевое соединение между серверами.
2. Создать отдельную роль PostgreSQL `blizhniy_expiry` без `BYPASSRLS`. Выдать USAGE только public, а на listings/vacancies/work_requests — только SELECT(id,status,expires_at) и UPDATE(status). Для каждой из трёх таблиц нужна узкая FOR SELECT TO blizhniy_expiry политика для просроченных published и expired строк, а также FOR UPDATE TO blizhniy_expiry USING (status = 'published' AND expires_at <= now()) WITH CHECK (status = 'expired'). SELECT expired нужен UPDATE RETURNING; другие поля менять нельзя. Эти operator grants/RLS не выполняются новой app migration. Перед таймером проверить итоговые права/пересечение policies и отказ изменения иных колонок. Пароль назначить интерактивно `psql \password blizhniy_expiry`, не хранить в SQL/shell history.
3. В `/etc/blizhniy/pg_service.conf` создать секцию `[blizhniy_expiry]` с `host`, `port`, `dbname`, `user=blizhniy_expiry` и подходящим режимом TLS. В `/etc/blizhniy/pgpass` записать `host:port:dbname:blizhniy_expiry:password`; файл должен принадлежать `blizhniy-expiry` и иметь права `0600`. Каталог `/etc/blizhniy` и service-файл разрешить только root и группе `blizhniy-expiry`. Пароль не передавать в `ExecStart`, переменной `PGPASSWORD` или URL командной строки.
4. Установить оба unit-файла из текущего релиза в `/etc/systemd/system`, выполнить `systemctl daemon-reload`. **Таймер пока не включать.** Сначала выполнить `systemctl start blizhniy-expiry.service`; проверить `systemctl show -p Result blizhniy-expiry.service` и `journalctl -u blizhniy-expiry.service -n 30 --no-pager`. Результат должен быть success, три счётчика в логе, а агрегатные счётчики просроченных published строк — ноль.
5. После проверки сайта включить `systemctl enable --now blizhniy-expiry.timer` и проверить `systemctl list-timers blizhniy-expiry.timer`. Отслеживать ненулевой код сервиса через журнал и мониторинг сервера; не считать ошибку SQL успешным запуском. При переносе релиза systemd продолжит обращаться к `/var/www/blizhniy`, то есть к текущему симлинку.

До появления Timeweb сервера и работающего GitHub Actions Deploy эти команды не запускались. Само слияние PR **не включает** таймер. В промежутке между запусками кабинет и админка показывают эффективный статус `expired` по времени; SQL-сверка приводит в соответствие саму БД.
