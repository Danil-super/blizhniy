# Оповещения БЛИЖНЕГО

Шаблон `blizhniy-site-health-alert.timer` запускает проверку через пять минут после завершения предыдущего запуска. Адрес дежурного задаёт `BLIZHNIY_SITE_ALERT_EMAIL` в закрытом конфиге. Сбои контрольных запросов проверяются ещё раз через 10 секунд. У каждого сигнала свой файл в `StateDirectory`, поэтому письмо о восстановлении одного сигнала отправляется, даже когда другой остаётся активным. [Сервис](../ops/systemd/blizhniy-site-health-alert.service) · [Таймер](../ops/systemd/blizhniy-site-health-alert.timer)

| Сигнал | Условие | Действие дежурного |
|---|---|---|
| Доступность | Два отказа `/api/health` | Проверить прокси, процесс приложения и последний релиз. |
| Публичные страницы | Две проверки подряд обнаружили сбой соединения, неожиданный HTTP-ответ (например, 404) или ответ без HTML | Сопоставить маршрут с журналами Next и прокси. |
| HTTP 5xx | Две проверки подряд обнаружили HTTP 5xx на главной, в объявлениях или в поиске | Проверить ошибки приложения и прокси за время двух замеров. |
| HTTP 5xx по трафику | За интервал между замерами Caddy зарегистрировал не меньше трёх ответов 5xx, и их доля составила не меньше 0,5% | Проверить ошибки Caddy и Next за этот интервал и состояние веб-процесса. |
| Готовность | `/api/health` успешен, `/api/ready` дважды отказал | Проверить статус БД, подключение и совместимость схемы. |
| Время ответа | Успешный ответ хотя бы одной проверки занял больше 2 секунд при подтверждающем замере | Сверить нагрузку узла и время ответа БД. |
| TLS | Публичный HTTPS-сертификат истекает в течение 14 дней или не проходит проверку имени и доверия | Проверить сертификат публичного домена и процедуру обновления. [Проверка TLS в Node.js](https://nodejs.org/docs/latest-v22.x/api/tls.html#tlsconnectoptions-callback) |
| Диск | Не больше 15% доступных блоков или inode на разделе, указанном в `BLIZHNIY_SITE_ALERT_DISK_PATH`, либо раздел не читается | Проверить, что путь указывает на нужный раздел, затем проверить его заполнение и журналы. [Доступные блоки в Node.js](https://nodejs.org/docs/latest-v22.x/api/fs.html#statfsbavail) |
| Фоновые службы | Выбранный таймер остановлен, перестал планировать запуск или его служба завершилась с ошибкой | Проверить названные в письме timer/service и последние записи журнала. [Свойства systemctl show](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html#show%20PATTERN%E2%80%A6%7CJOB%E2%80%A6) |
| Резервная копия | Последняя попытка завершилась ошибкой, снимок старше часа или квитанция недоступна | Сверить обе части копии, время снимка и отчёт о восстановлении. |

Идентификатор SMTP-сообщения сохраняется перед отправкой. Для явной временной ошибки предусмотрено до трёх попыток с тем же идентификатором. При неопределённом ответе запись остаётся для сверки, повтор автоматически не отправляется. При восстановлении после принятого SMTP оповещения отправляется отдельное письмо. Сбой доставки виден по полю `delivery` и коду завершения сервиса. `runId` связывает сигналы одного запуска. [Код отправки](../scripts/site-health-alert.mjs)

Локальный прогон проверяет восстановление сигнала, потерю ответа SMTP, повторный запуск со старым файлом состояния и одновременные инциденты. TLS проверен на локальном сервере с доверенным сертификатом, недоверенной цепочкой и неверным именем. Доставка на адрес дежурного и значения на рабочем узле остаются шагами эксплуатационной приёмки. [Тесты сигналов](../tests/site-health.test.mjs) · [Тесты оповещений](../tests/site-health-alert.test.mjs)

`BLIZHNIY_SITE_ALERT_WORKER_TIMERS` содержит имена установленных служб через запятую, без расширения. Допустимы `blizhniy-auth-mail`, `blizhniy-booking-expiry`, `blizhniy-business-email`, `blizhniy-expiry`, `blizhniy-payment-reconciliation-alert` и `blizhniy-push`. Каждый получает собственное оповещение и письмо о восстановлении. [Проверка таймеров](../scripts/check-site-health.mjs)

`BLIZHNIY_SITE_ALERT_BACKUP_RECEIPT` указывает на ограниченный по размеру файл служебных метаданных. Создатель копии публикует его атомарно. После успешной сверки снимка PostgreSQL и медиа квитанция содержит `version:1`, `status:"verified"`, `snapshotAt` и `verifiedAt` в UTC ISO 8601. Для ошибки используются `version:1`, `status:"failed"` и `attemptedAt`. Квитанция с открытой записью для группы или остальных отклоняется. Возраст считается по времени снимка. Для репетиции на синтетических данных сформирована действительная квитанция после восстановления PostgreSQL и WebP. От создания восстановленного стенда до подтверждения результата прошло 5,4 секунды. Измерения рабочего RPO и RTO остаются частью приёмки внешнего контура. [Репетиция](../tests/basic-erasure-restore-postgres.mjs)

## Независимые оповещения о публичных страницах

Сборка `a779cc2d` ведёт два состояния в `site-public-pages.json` и `site-public-5xx.json`. При обновлении открытое 5xx из старого общего файла переносится вместе с идентификатором и результатом доставки. При возврате к предыдущему пакету монитора открытый 5xx может дать повторное письмо, поскольку предыдущий пакет читает только общий файл.

Распакованный архив монитора прошёл проверку на локальном HTTP и SMTP через TLS. Ответ HTTP 404 сохранил свой открытый инцидент, пока возник и восстановился 503. Для каждого пришло отдельное оповещение о восстановлении. При SMTP 451 следующая попытка сохранила тот же идентификатор. При потере ответа после приёма сообщения следующая проверка оставила статус `unknown` без повторной отправки. Прошли 56 целевых и 3 233 регрессионных теста, сборка и проверка веб-архива. Отчёт, архив монитора и контрольные суммы сохранены в `audit-public-alerts.6VHhv3Wb/`. На рабочем сервере пакет ещё требуется сверить и установить.

## HTTP 5xx по трафику сайта

Для включения сигнала используйте выделенный слушатель Caddy, который обслуживает только HTTPS сайта с внешним маршрутом Caddyfile `subroute`. Имя `blizhniy-public` задайте в существующем блоке `servers` для фактического адреса слушателя. Добавьте `metrics` в глобальные настройки и отдельную точку чтения на loopback. В примере публичный слушатель принимает HTTPS на `:443`.

```caddy
{
    metrics
    servers :443 {
        name blizhniy-public
    }
}

http://127.0.0.1:2018 {
    bind 127.0.0.1
    metrics /metrics
}
```

Перед включением проверьте адаптированный конфиг и доступность `http://127.0.0.1:2018/metrics` под пользователем монитора после контрольного запроса к сайту. В метрике `caddy_http_request_duration_seconds_count` должна появиться серия с `server="blizhniy-public"` и `handler="subroute"`. Адрес `/metrics` на слушателе сайта не должен выдавать метрики. Доступ к административному API меняется отдельно от этой настройки. Для получения оповещений тем же дежурным задайте `BLIZHNIY_SITE_ALERT_CADDY_TRAFFIC=enabled` в конфиге монитора. Для выключения уберите эту переменную. [Метрики Caddy](https://caddyserver.com/docs/metrics) · [Параметры слушателя](https://caddyserver.com/docs/caddyfile/options#servers)

Интервал штатного таймера около пяти минут. Первый замер, перезагрузка Caddy, сброс счётчика или интервал свыше 12 минут создают новую исходную точку. Без новых ответов открытый инцидент сохраняется. После замера ниже порога монитор отправляет одно письмо о восстановлении, если SMTP принял исходное оповещение. `traffic-unavailable` в журнале и ненулевой код сервиса означают, что замер или файл состояния недоступны. Проверьте слушатель, серии, `StateDirectory` и лимит чтения 1 МиБ. Монитор сохраняет отметки времени и суммы ответов, без адресов пользователей, путей и содержимого запросов. В сумму входят и контрольные запросы, которые доходят до слушателя. Ответы, сформированные CDN без обращения к Caddy, остаются за пределами счётчика.

## Очереди

Отдельный таймер раз в минуту после завершения предыдущей проверки читает четыре логических поля через `operations_health.queue_backlog(text)`. Порог для писем регистрации, сброса и Push составляет две минуты после готовности к отправке. Для бизнес-писем и сверки TEST-платежей порог составляет пять минут. Дополнительно проверяются просроченная больше минуты аренда и блокировки платежей выбранного TEST-магазина. [Проверка PostgreSQL](../database/operations/queue-health.sql) · [Таймер](../ops/systemd/blizhniy-queue-health-alert.timer)

При задержке проверьте таймер канала, последний статус воркера и ответ провайдера. Для сверки TEST откройте штатный отчёт оператора. При сбое зонда сохраняются ранее зарегистрированные инциденты. После восстановления каналы проверяются независимо. Монитор получает только признаки задержки и пишет в журнал имя сигнала и статус доставки. [Код зонда](../scripts/queue-health-alert.mjs)

Пакет добавляет отдельную схему `operations_health` поверх полного набора очередей 0087. `blizhniy_queue_monitor` получает CONNECT, USAGE своей схемы и EXECUTE одного зонда. Настройки включают `BLIZHNIY_QUEUE_HEALTH_ALERT=test-v1`, `BLIZHNIY_PAYMENT_MODE=test`, идентификатор TEST-магазина, соединение с проверкой TLS и `BLIZHNIY_QUEUE_ALERT_EMAIL`. При отключении достаточно остановить таймер и отозвать эти права. Фоновые таймеры можно дополнить именем `blizhniy-queue-health-alert`. [Права](../database/permissions/queue-health.sql) · [Сервис](../ops/systemd/blizhniy-queue-health-alert.service)

На одноразовой PostgreSQL с миграциями 0087 проверены сигнал и восстановление для двух почтовых очередей и Push, отсутствие доступа к таблицам и совместимость с исходными правами финансовой службы. Отдельный тест проверяет потерю соединения с БД и сохранение ранее зарегистрированных инцидентов. [Интеграционная проверка](../tests/queue-health-alert-postgres.mjs)
