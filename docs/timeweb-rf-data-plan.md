# Перенос персональных данных БЛИЖНИЙ в РФ

Дата: 25.09.2026. План для проверки на тестовом контуре до регистрации и реальных оплат.

## Текущее состояние

Приложение использует Supabase Auth в браузере, серверный REST/Data API и Storage. Подключенный проект расположен в `eu-west-1` (Ирландия). Замена только PostgreSQL или установка российского прокси не перенесет первичную запись Auth, загрузку файлов и хранение персональных данных в РФ. Полный переход требует совместимого Auth, API, Storage, файлов, резервных копий и логов в российском регионе.

## Выбор размещения по текущему серверу

На скриншоте панели Timeweb указан **Cloud MSK 40: 2 vCPU, 2 ГБ RAM, 40 ГБ NVMe**; московский регион виден по названию тарифа. Физическую локацию именно этого сервера и условия хранения бэкапов подтвердить в панели/договоре. На этой конфигурации можно запустить отдельный небольшой PostgreSQL лишь после измерения ресурсов, но **полный Supabase вместе с работающим Next.js размещать нельзя**: минимум официального self-hosted набора Supabase составляет 2 CPU, 4 ГБ RAM и 40 ГБ SSD без запаса для сайта. Код использует Supabase Auth, Data API и Storage, поэтому самостоятельный PostgreSQL на нынешнем VPS не заменит зарубежный проект и не решит перенос первичного сбора ПД.

| Вариант в РФ | Ресурсы и ориентир Timeweb | Оценка |
| --- | --- | --- |
| Оставить сайт на Cloud-40, поднять отдельный Cloud-80 под полный Supabase | Сайт: 2/2/40, сервисы и БД: 4/8/80; по опубликованной таблице от 900 + 1 800 = **2 700 ₽/мес** при выбранном на странице сроке 12 месяцев | **Предпочтительный стартовый вариант**: отдельные ресурсы БД/ Auth/ Storage и сайта; необходимы частная сеть, резервные копии вне этих VPS и наблюдение за памятью/диском |
| Увеличить текущий VPS до Cloud-100 и разместить всё вместе | 8/12/100, около **2 790 ₽/мес** при том же опубликованном сроке | Меньше серверов, но общий отказ и конкуренция за память/диск; обязательны ограничения контейнеров, измерение пиковой нагрузки и внешние бэкапы |
| Managed PostgreSQL Timeweb в Москве/Санкт-Петербурге | Цена БД и копий зависит от выбранного тарифа | Подходит при желании делегировать сопровождение БД, **но Auth, API и Storage всё равно нужно разместить в РФ** и проверить совместимость/права/миграцию; общая стоимость вырастет |

Числа — ориентиры по публичной странице Timeweb на дату документа, где по умолчанию выбран срок **12 месяцев со скидкой 10%**; помесячная оплата и бэкапы могут стоить иначе. Перед покупкой проверить актуальную цену в своём аккаунте, доступность того же региона и условия изменения тарифа. Supabase рекомендует для полного стека **4 CPU / 8 ГБ RAM / 80 ГБ SSD**; Next.js нужен отдельный ресурс сверх этого. После появления фактических метрик допускается уменьшить число необязательных сервисов, но конфигурацию 2 ГБ для всего стека не считать рабочей.

## Порядок переноса

1. Подтвердить Москву для Cloud MSK 40, фактические свободную RAM/диск и пиковую нагрузку, время простоя и критичные интеграции. Собрать перечень всех мест с ПД: Auth, профили, контакты и точные адреса, платежные метаданные, Storage, SMTP, журналы, аналитика, бэкапы.
2. Поднять отдельный тестовый self-hosted контур в РФ, закрыть PostgreSQL от Интернета, выдать публичный HTTPS только нужному API, настроить почту/подтверждение адреса, ограничение попыток входа, обновления и наблюдаемость.
3. Снять согласованные `roles.sql`, `schema.sql`, `data.sql` по официальной инструкции Supabase; отдельно перенести объекты Storage. Данные содержат `auth.users` и требуют защищённого временного хранения только в РФ. Не класть дампы, ключи и `.env` в GitHub или CI-артефакты.
4. На тестовом контуре проверить восстановление, количество строк, связи, RLS/grants, доступ ролей, файлы, регистрацию, вход, восстановление пароля, блокировки, кабинет на двух аккаунтах, создание/оплату/публикацию, webhook и публичные страницы. Новые JWT-ключи потребуют повторного входа пользователей.
5. Сделать зашифрованные регулярные копии вне основного VPS, хранить их в РФ и проверить восстановление на отдельной машине. Снимок диска не заменяет проверенный дамп PostgreSQL и копии объектов.
6. Перед переключением заморозить запись на старом контуре, выполнить финальный экспорт и сверку, поменять переменные `NEXT_PUBLIC_SUPABASE_URL`, ключи сервера/браузера, URL файлов, SMTP и DNS/реверс-прокси. Проверить, что браузер больше не обращается к зарубежному Auth и Storage. Вернуть запись только после проверки российского контура. Старую зарубежную базу выводить из эксплуатации после юридической проверки сроков и обязанностей.
7. Отдельно проверить документы оператора, уведомления и основания обработки/передачи данных с юристом. Технический перенос сам по себе не завершает правовую работу.

## Следующее решение

Конфигурация текущего сервера установлена по скриншоту: 2 vCPU / 2 ГБ / 40 ГБ. Следующий шаг — подтвердить регион и пиковые свободные ресурсы, выбрать дополнительный Cloud-80 либо увеличение до Cloud-100 после проверки цены в личном кабинете, получить безопасный административный доступ, сделать тестовый контур и проверить восстановление. До этого не менять URL Auth и не переносить рабочие данные наугад.
