# F02: атомарное решение о компенсации отклика

Локальный инкремент0043. Исходные условия — `docs/audit-application-compensation-policy.md`. Реальных вызовов ЮKassa нет; HTTP, очередь и runtime-права не активированы. Ручной стенд сохраняет0001–0035+0041, production —0033.

## Реализованное поведение

Private TEST store принимает только ID исходной оплаты. Сумма, merchant, отклик, причина, срок и фискальный режим выводятся из проверенных данных БД. Объект `eligible`, сумма или доказательства из браузера не принимаются.

В одной READ COMMITTED транзакции блокируются payer → intent → order → work → application. Все новые row-lock переходы используют NOWAIT: конфликт возвращает отдельную ошибку занятости и откатывает попытку. После блокировок перечитываются журнал раскрытия и событие выбора; будущие capture свыше действующего допуска5 минут, неизвестный merchant, отсутствие подтверждённого capture, несогласованный исходный запрос/SHA или недоставленный отклик исключают создание case. Чек проверяется существующим0042 helper; сумма всегда полная и исходная.

`application_compensation_cases` неизменяема и уникальна одновременно по исходной оплате и отклику. В ней сохраняются версия политики, причина/время возникновения условия, доставка, просмотр, выбранный отклик и полная сумма. Повтор сначала читает прежний case, даже если позднее изменились просмотр или состояние оплаты. Потеря ответа COMMIT не создаёт нового ключа. Будущий dispatcher обязан использовать этот же устойчивый идентификатор и сверять исходную оплату перед отправкой.

SQL INSERT-trigger независимо повторяет допуск:120 прошедших часов от доставки либо более ранний выбор другого исполнителя; просмотр до или в момент условия запрещает компенсацию. Поздний просмотр или поздний выбор этого исполнителя сохраняют уже возникшее основание. `legacy_unknown` не превращается в доказательство отсутствия просмотра.

## Достоверные даты выбора и просмотра

`application_selection_events` записывает первый выбор отдельным событием. Для заказа допускается один выбранный отклик; для вакансии — отдельное событие каждого выбора. Время выставляет БД после записи раскрытия контактов, внутри той же транзакции. Последующее изменение `updated_at` не меняет событие выбора. Старые выборы не получают вымышленную дату: если актуальный выбранный отклик не имеет события, требуется операторское восстановление.

Новая версия guard раскрытия контактов захватывает work/application и сама назначает время после блокировок. Она сохраняет первые записи0035 и не позволяет вставкой задним числом повлиять на компенсацию. При конфликте чтение не должно возвращать контакты: действующий авторизованный обработчик выдаёт snapshot только после успешного COMMIT. Новый case не удаляет ранее доставленный отклик или контакты.

Снятие/удаление заказа самим заказчиком пока не подключено: для него в F06 нужен отдельный достоверный журнал действия. `archived`, `expired`, блокировка или исчезновение карточки не подменяют это событие. Helper передаёт `customerClosedAt=null`; данная ветка остаётся открытой.

## Доказательства

- `node --test tests/application-compensation-cases-postgres.mjs`:18/18, включая17 подзадач на PostgreSQL18.6 с полным составом0001–0043. Только синтетические данные в одноразовом контейнере; persistent БД и `.env` тест не читает.
- Узкая роль имеет SELECT case, INSERT только ID оплаты/merchant и EXECUTE проверяющего helper. У неё нет UPDATE денег, изменения исходного запроса, INSERT раскрытия/выбора или удаления истории. Реальные права web/worker не менялись.
- Проверены повторы/потеря COMMIT ACK, конкурентные claims, оба порядка claim/disclosure, прямой SQL, подмена времени просмотра, будущий capture, legacy и отсутствующая история выбора, сохранность уже принятого решения.
- Проверены обычный `PostgresApplicationStore.read/decide`, запись выбора, отклонение других откликов и одно уведомление другому специалисту. Это SQL/application integration, не браузерная и не provider-проверка.
- SQL и чистая политика совпадают при DST-переходе в `America/New_York`: используется `interval '120 hours'`, не календарные пять дней.
- Намеренное удаление SQL-проверки просмотра обнаружено сценарием прямой вставки после выбора другого исполнителя; миграция восстановлена побайтно, GREEN повторён.
- Native2540/2540 без пропусков; floor/types/lint/build прошли. Прежнее lint-предупреждение `targetType` не скрыто. Graphify и Code Graph обновлены для этого проекта.
