# Вакансии и заказы российского контура

Часть утверждённого полного переноса L11/L12, не новый сервис и не сокращение функций. Общая граница этих двух разделов хранит owner-scoped форму, CAS revision, приватные фото и состояние публикации. Вакансия и заказ имеют разные строгие allowlist-поля; произвольный JSON, owner/status/paid/даты от клиента не принимаются. Последующие домены не подключаются автоматически к неподходящему контракту.

Пользовательский путь: существующая форма → сохранение → кабинет → редактирование → модерация → оплата по серверному тарифу → публичное чтение. Первые части не объявляются завершением последующих. Публичный DTO строится явно: телефон, мессенджер, email и контактное лицо не попадают в HTML/RSC/JSON; точный адрес и координаты доступны публично только при явном showExactAddress. Контактный доступ участникам откликов — отдельный авторизованный сценарий L15.

Схема добавляется после проверенного журнала0001–0015, без изменения их байтов и без импорта старых данных. У runtime только необходимые column grants, не owner/DDL/произвольные paid/даты. Внешние роли пользователя и expected owner не заменяют cookie-сессию; session→resource locks и повторная проверка срока перед commit переиспользуются. Модератор не одобряет свою публикацию; решение связано с точной revision. Финансовый provider I/O не выполняется под ресурсной транзакцией.

Доказательства по мере реализации: native Node22 contracts/HTTP; собственный loopback PostgreSQL18 с ограниченной ролью, CAS и отрицательными случаями; Next production build + изолированный Chromium; установленный SHA VPS + health/ready. Удалённые ключи/персональные данные не входят в fixtures. Down отказывает при непустых предметных таблицах; operational rollback сохраняет новую БД и данные, не возвращает старый Auth. Готовность разделов и всего переноса фиксируется только после подключения UI/API и установки, не после создания таблиц.

## Инкремент форм и модерации 18.10.2026

Миграция0016 добавляет только `work_publications`, `work_publication_photos`, `work_moderation` и индексы; предыдущие15 источников неизменны. `bootstrap-postgres.mjs --plan-work-publications` показывает план; `--apply-work-publications HOST:DATABASE` требует точного подтверждения PostgreSQL18 и журнала. Автоприменения при старте/деплое нет. На применение0016 и выдачу описанных ниже прав владелец отдельно согласился 18.10.2026.

Отдельная операция `grant-work-publications.mjs --plan | --apply HOST:DATABASE` сверяет все16 SHA-256 и исходные ACL, не принимает избыточные права как норму. Только SELECT новых таблиц; INSERT формы и фото; UPDATE редактируемого JSON/ссылок/revision; INSERT заявки модерации и UPDATE её решения. DELETE разрешён только для замены связей фото. UPDATE владельца, оплаты, статуса/дат публикации, DELETE предметных записей, TRUNCATE, REFERENCES, TRIGGER и права передавать grants не выдаются. Операция не меняет роли/пароли/функции Auth. При неизвестном COMMIT нет автоматического retry: сначала повторная read-only сверка цели.

Кабинет и канонические формы создания/редактирования работают через cookie-only `/api/account/work-publications`; POST — list/read/intent, PUT — полный create или CAS update. Фото до10МБ загружаются отдельным защищённым upload; JSON хранит только UUID. Новый create пишет сразу весь снимок формы, не пустую запись. Потерянный ответ сверяется read-only intent; повторная запись до сверки запрещена. Временная потеря входа скрывает приватный DOM, но сохраняет ввод в памяти той же вкладки; подтверждённая смена аккаунта уничтожает буфер. Приватный ввод не сохраняется в localStorage/IndexedDB.

`/api/account/work-moderation` принимает точные kind/id/revision; `/api/admin/work-moderation` повторно проверяет текущего администратора для queue/inspect/photo/decide. Собственную публикацию одобрить нельзя. Одобрение/отказ сохраняются ровно для одной revision и не оплачивают/не публикуют материал. После редактирования решение устаревает. Отказ содержит ограниченную причину; неизвестное решение сверяется чтением. Превью фото авторизуется по текущей заявке и принадлежности файла до чтения bytes. Безопасный audit содержит только request ID, фиксированный event, status/code и длительность.

## Публичное чтение и фото — следующий инкремент

Primary public list/detail использует ограниченный российский pool до проверки оставшейся legacy-конфигурации. Нет fallback при отказе PostgreSQL и нет unscoped private read. SQL требует оплаченный published, действующее окно времени, подтверждённого неблокированного автора, активную профессию и approved для текущей revision. Полный ordered список ready owner-media должен совпасть с формой. Финальный DTO повторно проверяет срок после SQL и явно выбирает поля: без телефона, email, messenger, контактного лица и реквизитов; точный адрес/координаты — только по showExactAddress. Деньги форматируются из точной десятичной строки, не через float.

Публичный GET `/api/work-publications/:id/photos/:fileId` сначала проверяет именно действующую публикацию и её прикреплённый owner-ready файл, затем читает проверенным bounded/hash file reader, затем повторно проверяет current revision/eligibility/expiry перед выдачей bytes. Исходный каталог файлов остаётся приватным. Ответы no-store/nosniff, максимум2МБ и прежний общий image read cap4; чужой Host, query и недоверенный ingress отвергаются. Новых миграций/grants/статусов оплаты этот инкремент не вводит.
