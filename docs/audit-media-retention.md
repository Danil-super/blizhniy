На одном соединении и одном bounded REPEATABLE READ READ ONLY snapshot

тела исходных оплат/возвратов проверяются на буквальные UUID, включая
вложенные, повторные, embedded и uppercase значения. JSON Unicode escapes
нормализуются PostgreSQL до поиска; request_body разбирается как JSON.

отчёта. В JSON попадают только выбранные metadata/ID/типы ссылок и счётчики;
телефоны, email, исходные документы, токены, хеши и пути файлов не выводятся.

0600 в проверенном0700 каталоге вне Git. Stdout содержит сводку и путь отчёта;
ошибки содержат только фиксированный код/этап, без SQL/данных соединения.

## 14.11: журнал-кандидат и устранение разрыва claim → filesystem fence

Подготовлен `database/candidates/0058-media-reference-journal.sql`, **вне активных
миграций**. Он проверяется только на новой временной PostgreSQL18.6 с полными
0001–0057. Постоянный ручной стенд остаётся57; установленным handlers/workers
не расширяли допуск, роли и GRANT не меняли.

Журнал хранит media/source/resource ID, тип события и время, без копирования
форм, контактов, тела платежа или хешей. Записываются reserve/ready, присоединение
и снятие трёх photo-связей, UUID в текущих формах/профиле/booking и буквальные
UUID исторических снимков/тел запросов оплаты и возврата. Историческое
наблюдение не исчезает при изменении исходного документа. UPDATE/DELETE/TRUNCATE
журнала запрещены, веб-роли не получают доступ к нему или identity sequence;
SECURITY DEFINER trigger выполняет запись с фиксированным search_path.

События source-таблиц создаются AFTER фактического изменения: пропущенный
`ON CONFLICT DO NOTHING` не создаёт вымышленную ссылку. Общая media identity
блокируется в порядке ID через FOR NO KEY UPDATE: это совместимо с FK KEY SHARE,
но сериализует журнал между загрузчиками связей. Время берётся после ожидания
блокировки. Реальные переходы требуют READ COMMITTED; старые файлы получают
событие наблюдения при активации, без выдуманного unlink time в прошлом.
Это журнал доказательств, **не разрешение удалять**: финансовые связи target →
фото, не содержащие буквальный media ID в сохранённом документе, и утраченные
исторические версии ещё требуют отдельного консервативного удержания.

Общий путь `LocalMediaWriter` теперь получает SQL claim **после** READY от
дочернего процесса, уже доказавшего kernel flock. Только после успешного claim
в тот же процесс отправляется существующий ограниченный BFW1 frame. Отказ или
неопределённый результат COMMIT → пустой EOF, без файловой записи; исходная
ошибка возвращается после проверенного ответа и фактического close. Busy
сохраняет публичный MEDIA_IN_PROGRESS без создания SQL attempt. Нормализованные
байты копируются до первого ожидания, complete вызывается после закрытия child.
Прямой низкоуровневый write остаётся для явных файловых fixtures; штатные local/
production compositions используют обязательный writeClaimed без fallback.

Пятисекундный предел child теперь включает получение claim. Если до отправки
кадра child действительно закрылся, следующий независимый запрос разрешён;
поздний результат SQL никогда не отправляется в старый или новый child. Это
**не отмена SQL-транзакции**: поздний COMMIT может оставить pending attempt,
история и начисление сохраняются. После отправки любых файловых байтов UNKNOWN
по-прежнему блокирует supervisor; отсутствие подтверждённого close также
блокирует его. Ни отказ, ни timeout не освобождают квоту и не дают replay.

Проверки: PostgreSQL-кандидат9/9 (включая конфликт-no-op, реальный lock wait,
двух клиентов с FK KEY SHARE, rollback, reserve→ready и успешную запись роли
без доступа к журналу); bootstrap PostgreSQL364/364 с настоящими HTTP/socket/
файлами и новым поздним COMMIT после отмены child. Итоговая native2737/2737
прошла после последнего дополнительного сценария latch после BFW1;
supervisor22/22 прошёл отдельно. Целевые writer/supervisor/реальные
file-worker41/41 прошли до этого дополнительного сценария.
Ошибки воспроизведены RED, затем исправлены.
Два независимых инженерных ревью учтены; дополнительную проверку другой моделью
владелец пропустил. Check:fast прошёл без изменения floor/ожиданий assertion,
с прежним lint warning. Сборка `DDiu5BJfZWiaJzVbmjN_G` успешно запущена на3045.

## 14.11: финансовые снимки и терминальный учёт — изолированный кандидат

Кандидат58 дополнен без установки на ручной стенд. Новая immutable запись
оплаты различает точный набор фото, неизвестную текущую привязку и legacy.
Для точного набора проверяются владелец/kind/revision и блокируется исходная
карточка, затем выбранные media по ID. Отдельные history events сохраняют
исходные photo FK и буквальные UUID формы/тела запроса. У отклика берётся его
сохранённый snapshot и revision; текущие фото старых родительских публикаций
не подставляются. Нулевая точная выборка отличается от отсутствия доказательств.
Повторный INSERT intent не переснимает обновлённые фотографии.

Для legacy/неразрешённой версии консервативно удерживается фактически выбранный
существующий набор media, до10000 объектов. Утраченная история не заменяется
нынешней версией карточки. Fallback после начала retirement выбранного объекта
даёт отказ; файл не исключается из архивирования молча. Такой fallback может
долго удерживать лишние старые фото и увеличивает число events пропорционально
старым intent×media. Это принятый предел кандидата: перед установкой нужен
замер размера/времени backfill; превышение10s/блокировки откатывает миграцию.

Capture-trigger запускается до общего UUID-trigger: target → media, чтобы
не получить обратный порядок блокировок с редактированием карточки. Предельный
набор считается по уникальным существующим media, а не по повторениям UUID
в booking/форме. Отдельный rollback-сценарий проверил10000 photo FK плюс повтор
одного UUID в booking; это проверка совместимости старого schema-лимита,
а не увеличение нынешней пользовательской квоты500 фото.

Терминальные request/completion сохраняют metadata и `(owner_id,intent_id)`.
Request блокирует общую media identity, затем отдельными свежими SQL statements
проверяет отсутствие текущих/исторических ссылок и истечение168 часов после
максимального времени **всех** наблюдений этого media. Повторное присоединение
перезапускает ожидание, откат часов не стирает более позднее наблюдение.
Новая ссылка, write attempt и переход ready после request запрещаются.
Повтор request допускается только с тем же operation ID; другая операция
не присваивает себе старую работу. READ COMMITTED обязателен.

Completion проверяет точную пару media/operation. Только AFTER фактической
вставки единственной completion уменьшаются global charged bytes/objects;
ON CONFLICT и rollback повторно место не освобождают. `media_active_usage`
считает активные owner bytes/objects, исключая только завершённые операции:
request сам по себе остаётся начисленным. При ошибке счётчика операция
откатывается; metadata, история оплаты и защита intent от replay сохраняются.
Эти SQL-переходы проверены owner-соединением только на новой временной БД.
PostgreSQL не доказывает отсутствие файла: INSERT completion — будущая закрытая
capability файлового обработчика после unlink/fsync. Сейчас эта capability
не выдана ни одной runtime-роли, файловое удаление не реализовано и не запускалось.

Для детерминированной проверки срока используется private VOLATILE функция
с единственным штатным телом `pg_catalog.clock_timestamp()`, без аргументов,
env или клиентского времени. Все retention stamps используют её. Только
владелец временной тестовой БД заменяет часы на фиксированные значения, затем
в finally восстанавливает и сверяет точный pg_get_functiondef. Runtime не может
вызвать или изменять эти часы. Будущий admission обязан сверять их тело вместе
со всей схемой58; существующий допуск57 не расширен.

Проверены настоящий lock wait в обе стороны attach↔request, старые/точные/
неизвестные/нулевые снимки, история после редактирования, граница168 часов,
reattach, откат часов, rollback completion, конкурентный replay, сохранность
metadata/intent и запрет прав runtime. Тест с ошибочным BEFORE-освобождением
воспроизвёл двойное списание256B вместо128B; правильный AFTER устранил его.
Отдельные RED воспроизвели учёт duplicate UUID и обход при откате часов.
Итоговая PostgreSQL-проверка21/21 и общая native-регрессия2737/2737 прошли.
Check:fast прошёл с прежним lint warning, без изменения floor или старых
ожиданий. Новая сборка и повтор браузера не требовались: приложение не менялось.
Инженерное ревью завершено, оба замечания исправлены; дополнительную проверку
другой моделью владелец пропустил. Код приложения/сборка не менялись;
на3045 продолжает работать `DDiu5BJfZWiaJzVbmjN_G` со схемой57.

## 14.11: чтение, квота и файловое завершение во временном контуре

`MediaMetadataRepository` получил явный trusted-параметр retention, по умолчанию
false. Установленные compositions его не включают. В новом режиме все owned
операции требуют READ COMMITTED; перед отдельной проверкой terminal marker
блокируется media. Read держит блокировку до окончания файлового чтения.
Get-by-intent/reserve/claim/complete отвергают terminal identity через уже
существующий MEDIA_INTENT_CONFLICT; read/get-write-attempt не возвращают файл.
Upload не нормализует и не пересоздаёт старый terminal intent. Quota admission
использует `media_active_usage`, с нулевым значением для отсутствующего owner:
request остаётся начисленным, только completion освобождает место.

Отдельный `createLocalMediaFileRetirer` сохраняет прежний трёхметодный интерфейс
file store. Он проверяет два точных известных имени под pinned root descriptor:
private regular inode, UID/0600, размер, digest/формат, число hardlinks и стабильность
снимка. **Оба** файла проверяются до первого unlink. Разрешены только complete
или absent; пара имён может объяснять ровно два hardlink одного inode.
Неполный, пустой, повреждённый, чужой hardlink, symlink, directory или неизвестный
файл не удаляются; даже корректный второй файл остаётся на месте. Без write
attempt разрешено подтвердить только уже отсутствующий final. Нет rm/рекурсии,
путей от клиента, перечисления и удаления чужих временных файлов.

После unlink выполняется directory fsync и повторная проверка отсутствия.
Даже полностью отсутствующие имена требуют fsync: прежний процесс мог умереть
между удалением и подтверждением долговечности. Ошибка после начала unlink
означает UNKNOWN. Новый BFR1 frame116B связывает metadata с nullable attempt;
он отдельно проверяет тип операции и повторно использует строгий BFI1 parser.
Нулевое binary поле attempt отличается от любого допустимого UUID.

`LocalMediaRetirement` работает только в test runtime и не имеет HTTP/cron/queue
или автоматического retry. Сначала отдельный child получает тот же kernel flock,
передаёт READY, затем callback коммитит terminal request (либо читает его
прежний operation ID) и возвращает точную metadata/attempt пару. После bounded
удаления/проверки child передаёт ACK и действительно закрывается; только после
валидного close и закрытия descriptors начинается SQL completion. Child не
получает соединение/пароли БД. Файловое retirement также запрещено в production.

Освобождение fence перед completion безопасно в принятой модели: terminal
request необратим, metadata/attempt identity неизменяемы, старый разрешённый
writer уже завершился/умер до взятия этого flock, а новый claim отвергается.
Все application writes обязаны идти через claim внутри flock; raw file-store/
worker.write не являются разрешённым application-путём. Как и прежняя файловая
модель, это не защита от root/постороннего writer с тем же UID, обходящего протокол.

До доказанного ACK/close completion вообще не вызывается. Потеря ответа request
COMMIT может оставить marker, но не запускает FS; свежий явный проход продолжает
ту же операцию. Потеря ответа completion COMMIT означает **неизвестный** исход:
начисление могло уже освободиться. Компенсации/авторетрай нет; свежий fenced
проход заново доказывает отсутствие и видит прежнюю immutable completion,
не освобождая бюджет повторно. Incomplete evidence остаётся на диске с request
и начислением: одного UUID для доказательства происхождения недостаточно.

Проверки на новом disposable PG18 и настоящих child/flock/files: ready→unlink→
completion, старый intent не оживает, первая загрузка пустого owner и owner
после удаления последнего объекта, ровно один конкурентный replacement на
границе500 фото и отдельно250MiB, чтение перед удалением и чтение за terminal
lock wait, потеря каждого COMMIT ACK, смерть child после настоящего fsync до
ACK, явное восстановление без двойного release, неполный temp с сохранением
обоих файлов/начисления. Кандидат/контур28/28, прежний bootstrap364/364,
native2751/2751 и check:fast прошли, прежнее lint warning сохранено.
Инженерное ревью замечаний к реализации не нашло; дополнительную проверку
другой моделью владелец пропустил. Сборка `NkbuSgsuvSucg0UGYuaya` запущена на3045;
браузерный upload/replay/quota409 проверил сохранность формы/учёта и320/1440 без
JS-ошибок. На ручном стенде по-прежнему57, retention=false; его файлы не удаляли.

## Оставшийся пакет реализации очистки

1. **Активация истории.** Журнал, финансовые captures и terminal ledger готовы
   в кандидате; нужны точный schema fingerprint, проверка backfill и допуск
   совместной работы всех установленных локальных handlers/workers.
2. **Включение terminal в compositions.** Новый режим чтения/replay/quota готов,
   но текущие handlers/proxy создают repository с default false. Нужен единый
   локальный rollout после проверки прав/view и schema admission; production
   не включается этой работой.
3. **Операторское исполнение и quarantine.** One-shot файловое исполнение и
   явная сверка готовы для whole verified leaves/absence. Нужны ограниченная
   роль, runner/допуск и операция восстановления для постоянного local58.
   Неполные/неизвестные файлы требуют отдельного доказательства происхождения
   или ручного рассмотрения; автоматическое освобождение их квоты запрещено.
4. **Пакет допуска.** Новые права, SQL guards и расширение схемы готовятся
   изолированно, с проверками attach-vs-retire, delayed writer, replay, рестарт,
   lost ACK и session/lock expiry. Локальные handlers/operators/workers57
   сверяют полный fingerprint: установка58 без согласованной совместимости
   остановит их. Установка на ручной стенд и изменение этих guard проходят
   одним конкретным пакетом review; текущие57-проверки не обходятся.

Такой порядок следует найденным гонкам, а не разрешает удаление семи строк
из сегодняшнего отчёта. F08 и весь этап3 остаются открытыми. Этот инкремент
не устанавливает миграций/GRANT, не меняет установленные workers и не удаляет файлы.
Production, два российских сервера, push/deploy и настоящие платежи не тронуты.
