## Проверенный внешний контракт

Через Context7 прочитаны официальные [идемпотентность ЮKassa](https://yookassa.ru/developers/using-api/interaction-format), [полные возвраты](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds), [чеки ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/refunds) и [отдельная отправка чеков](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/other-services/refunds). Также прочитан [OpenAPI](https://yookassa.ru/developers/api/yookassa-openapi-specification.yaml): RefundRequest требует payment_id/amount и допускает metadata. Ключ до64 символов, идемпотентность сохраняется24часа; новый ключ может создать новую операцию.

Отсутствие receipt в базовом полном refund request **не доказывает освобождение от чека**. В сценарии чеков от ЮKassa полный возврат может использовать исходный чек; в другом сценарии чек нужно отдельно сформировать/отправить. Текущий код не выбирает фискальный сценарий и не отправляет этот запрос. Перед реальным POST обязательны проверка настроек/способа платежа и согласованная обработка чека.

## Локальный контракт

`prepare(operationId)` принимает только UUID существующей reservation0036. Merchant/TEST задаются доверенной конфигурацией; сумма, original payment/provider ID и тип берутся из неизменяемой покупки. Сначала блокируются user → intent → order, проверяются исходные bytes/hash, provider link, reservation binding и подтверждённый capture. Новая подготовка требует `order=succeeded`; сохранённый запрос можно восстановить после `refunded` с сохранением первоначального capture proof. Текущие цена/тариф/контакты/содержимое карточки не пересобирают запрос.

`payment_refund_requests` хранит ровно один первоначальный request на reservation: его точные bytes, SHA256, ключ и дату БД. Body содержит только payment_id, полную исходную RUB-сумму и metadata localRefundId/localPaymentId. Контакты/receipt/описание/секреты не копируются. Ключ `refund-<operationUUID>` имеет43 символа и отдельное пространство от исходных payment UUID. `operationId` — локальный ключ, не ID возврата у провайдера. JS и SQL проверяют одну каноническую сериализацию; даже другой порядок ключей или пробелы не принимаются как замена сохранённого body.

`openWindow(operationId)` требует уже сохранённый request и по-прежнему succeeded/captured исходный платёж. Он фиксирует одну `payment_refund_dispatch_anchors.authorized_at`, выставленную БД, и возвращает технический остаток23ч55м от первой отметки. Повтор не обновляет дату, bytes, hash или ключ. Истёкшее неизвестное окно остаётся закрытым; .prepare продолжает возвращать сохранённую историю. Время pool/SQL/блокировок/COMMIT дополнительно вычитается локальными монотонными часами после завершения транзакции. Неизвестный COMMIT не вызывает внутреннего retry или создания другого ключа.

Это **не бизнес-разрешение на возврат и не доказательство отправки**. Будущий dispatcher должен отдельно подтвердить инициатора/основание, актуальный доступный остаток и отсутствие внешних возвратов, совместимый способ оплаты/чек; затем повторно проверить окно непосредственно перед каждой сетевой попыткой и ограничить общий сетевой deadline. Wall-clock окно предполагает контролируемую синхронизацию часов БД; после значительного сдвига часов или неизвестной истории автоматический POST недопустим без сверки. Число реальных HTTP-попыток сейчас не учитывается, поскольку их нет.

SQL-триггер остаётся invoker с пустым search_path, VOLATILE, PUBLIC EXECUTE отозван. Он блокирует только intent → order, после ожидания отдельным запросом сверяет immutable provider/verification binding. Исходные CHECK/FK0019–0021 продолжают проверять capture/metadata/amount;0037 дополнительно проверяет SHA/тип/TEST/магазин/reservation и канонические bytes/hash запроса. Hash и обе даты задаёт БД. UPDATE/DELETE/TRUNCATE обоих журналов запрещены; down отказывается удалять непустую историю. Старая36 receipt fence сохраняется.

## Проверка и оставшаяся часть

RED установлен отсутствующим модулем. Чистые native-проверки проверяют точные bytes/namespace, границы UUID/сумм и отсутствие новых копий контактов. `scripts/check-local-refund-requests.mjs` проверяет настоящий PostgreSQL18.6: конкуренцию, SQL/ACL, источник и hash drift, реальные ожидания intent/order/user, пересечение cutoff, удержанный COMMIT, rollback и фактически выполненный COMMIT с потерей ACK. Исходные CHECK/FK, отклоняющие невозможную порчу данных до0037, проверяются как отдельные унаследованные ограничения, а не приписываются новому триггеру.
