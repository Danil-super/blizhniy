# Приёмка WebAuthn для администраторов БЛИЖНЕГО

## Подготовка пакета

Собрать веб-архив, верификатор WebAuthn, оператор прав, оператор возвратов и при необходимости подготовки архивов из одного проверенного релиза. Сверить действующие режимы, журналы базы и права ролей по установке на VPS. Пакеты для рабочей БД должны подключаться к PostgreSQL на том же сервере с проверкой сертификата.

Проверить пакеты сверки платежей, оператора и обработчика возвратов на исходной схеме 0087 и на схеме после установки WebAuthn. Совместимые версии финансовых служб устанавливаются до миграций. При переключении финансовый режим остаётся TEST. [Пакет проверки прав оператора](../scripts/build-user-access-operator.mjs) · [Пакет возвратов](../scripts/build-refund-operator.mjs)

## Переключение

1. Сохранить закрытую копию БД, проверить восстановление на одноразовом контуре и дождаться завершения текущих действий администраторов. Владелец отдельно согласует установку и включение режимов.
2. Подготовить логин `blizhniy_passkey_verifier` без членств и административных привилегий, с лимитом четырёх подключений. Дать ему только подключение к рабочей базе. Точные права выдаёт 0092. Фактический владелец БД применяет единый `database/admin-passkey-upgrade.sql` из пакета оператора прав и становится владельцем схемы `app_admin_passkey`. Установить совместимые службы с отдельными Unix-сокетами и сверить фактический доступ пользователя возвратов к сокету верификатора. Остановить прежние `blizhniy-refund-operator.socket` и `blizhniy-refund-operator.service` и отключить их автозапуск до включения защищённого оператора. [Точные права верификатора](../database/candidates/0092-admin-passkey-verifier.sql) · [Службы systemd](../ops/systemd)
3. Включить в веб-конфигурации пару `BLIZHNIY_ADMIN_PASSKEYS=hosted-v1` и `BLIZHNIY_USER_ACCESS_OPERATOR=hosted-passkey-v1`. При действующем редактировании тарифов выбрать соответствующий пакет оператора прав. Для TEST-возвратов использовать `BLIZHNIY_REFUND_ADMIN=hosted-passkey-test-v1` и режим службы `BLIZHNIY_REFUND_OPERATOR=hosted-passkey-test-v1`. Включать подготовку архивов с действующим верификатором после возобновления пилота. [Настройки веб-доступа](../src/lib/hosted-user-access-config.ts) · [Настройки возвратов](../src/lib/local-refund-admin-config.ts)
4. Проверить выпуск кода и регистрацию ключа у согласованного администратора, доступ обычного пользователя и отозванной сессии, три защищённых действия и чтение уже записанных квитанций. Отдельно подтвердить возврат и чек в реальном TEST-магазине. Проверить рабочие очереди и доступность публичных маршрутов.

## Выпуск кода

Оператор вне сайта проверяет заявку и личность администратора. В доверенном интерактивном терминале без записи сессии, с существующим подключением владельца БД, запускает `scripts/issue-admin-passkey.mjs --add` из пакета верификатора. Для восстановления используется `--replace`, прежние ключи отзываются после успешной регистрации нового. Команда `--check` сверяет владельца, каталог и лишние права сторонних ролей. Точные права логина верификатора проверяет сама служба под этим логином. Код живёт пять минут, передаётся администратору по проверенному закрытому каналу и вводится в разделе «Пользователи». [Команда выпуска кода](../scripts/issue-admin-passkey.mjs)

## Восстановление работы при сбое

Ошибка до фиксации SQL сохраняет исходную схему. После фиксации при сбое убрать из веб-конфигурации `BLIZHNIY_REFUND_ADMIN`, `BLIZHNIY_ADMIN_TARIFFS`, `BLIZHNIY_USER_ACCESS_OPERATOR` и `BLIZHNIY_ADMIN_PASSKEYS`. Отключить сокеты защищённых действий. Оставить прежние refund-юниты остановленными и с отключённым автозапуском, так как режим `BLIZHNIY_REFUND_ADMIN=hosted-test-v1` снова откроет прежний маршрут. Сохранить новые таблицы, ключи, квитанции и совместимые финансовые службы. Проверить готовность сайта, профиль и бронирования, затем восстановить защищённые службы и повторить приёмку. Отдельный SQL-откат 0090 оставляет иной каталог, при котором предзапуск финансовых служб остановится.
