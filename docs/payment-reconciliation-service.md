## Решение и критерии

Один процесс вызывает существующий `worker.tick()` последовательно, без новой
финансовой логики и provider POST. Состояние задач принадлежит PostgreSQL, не
памяти процесса. Не создаются новый платёж или новый idempotence key.

`scripts/payment-reconciliation-service.mjs` экспортирует два явных интерфейса:

- `runPaymentReconciliationService({mode,createRuntime,signal,report,entryPoint})`
  возвращает exit code. Режим только `check` или `run`, без default `run`.
- `runPaymentReconciliationProcess({mode,createRuntime,entryPoint,report})`
  добавляет SIGTERM/SIGINT и обработчик ошибок stdout на время запуска,
  снимает их в finally. По умолчанию пишет JSON с ожиданием callback stdout.
  Вызывающая программа присваивает результат `process.exitCode`, не обрывает I/O
  вызовом `process.exit()`.

Доверенная `createRuntime` должна вернуть `preflight()`, `worker.tick()` и
`close()`. Если сама фабрика падает после открытия ресурсов, она закрывает их
сама; после успешного возврата закрытие ровно один раз принадлежит циклу.
`preflight` должен быть read-only и проверить точные schema/hash/роль/TEST scope
до первого claim. `check` вызывает только фабрику, preflight и close, не tick.

**Граница среза:** production фабрика ещё не подключена. Само наличие метода
preflight не доказывает безопасную конфигурацию. Исходные service-тесты использовали
fixture-owner; последующий [role-срез](payment-reconciliation-role.md) проверяет
настоящий read-only ACL/journal/guard preflight и полный цикл на выделенном
ограниченном логине. Это локальная приёмка, не production provisioning/установка
и не настоящий merchant E2E.

Импорт ничего не запускает: нет чтения env/секретов, подключения БД, merchant
запроса или регистрации сигналов. Нет standalone CLI, автоматически выбирающей
production-учётные данные, и нет PM2/systemd/deploy hook. Доверенную фабрику и
проверенный способ упаковки TS-зависимостей нужно закончить перед установкой.
Другой renderer, пользовательский HTTP или произвольный URL не могут подставить
фабрику через запрос: это интерфейс доверенного server-side кода, не API сайта.

## Работа и остановка

Перед началом проверяются режим, entryPoint `cli|service`, native AbortSignal,
фабрика и функции report/wait. Внутри цикла всегда одна задача; параллельных
tick нет. После idle пауза 5000ms, после любого другого результата 250ms.
SQL backoff отдельной задачи остаётся внутри очереди и этим интервалом не
сбрасывается. Предварительно прерванный signal не открывает runtime.

SIGTERM/SIGINT запрещают следующую задачу и прерывают сон. Они **не** отменяют
уже начатый GET или транзакцию: текущий tick заканчивается, результат фиксируется,
затем закрывается пул. Signal во время фабрики/preflight также не разрешает claim.
При жёстком убийстве процесса восстанавливается прежняя SQL lease, а не создаётся
новый платёж; процессный тест проверяет graceful stop, а не имитирует гарантию
транзакционного завершения при SIGKILL.

Исключение tick, включая неизвестный COMMIT claim/finish, завершает цикл с code1.
Повтора внутри этого процесса нет. Новый процесс использует обычные lease,
идемпотентную сверку и receipt. Завершённые задачи больше не исполняются;
арендованная задача остаётся недоступной до истечения SQL lease.

Результат tick ограничен idle/lost/completed/deferred/blocked, code — прежним
allowlist очереди. Ошибка preflight/tick/ожидания/закрытия или неверный результат
дают только фиксированный failureStage без исходного текста исключения.

## Наблюдаемость и ограничения

Вопросы оператора: начал ли цикл работу после preflight; где он остановился;
выполняет ли задачи и какие результаты получает? Сигнал — JSON-событие
`payment_reconciliation_service`, случайный runId на запуск, явный entryPoint,
mode, status и durationMs. Для tick дополнительно state/code/tickDurationMs;
в конце — счётчики пяти фиксированных outcomes. Нет provider/order/user ID,
email, merchant secret, body или произвольных result/error полей.

Запись report ожидается до следующего claim: backpressure не создаёт фонового
накопления задач. Отказ sink прекращает работу с code1; не предпринимается
повторная запись в тот же сломанный sink. Ошибка stdout адаптера также останавливает
admission. Это проверено реальным дочерним процессом без печати сырой ошибки.

Внешний supervisor пока не подготовлен: RestartSec, лимиты ресурсов и предельное
время graceful stop надо согласовать с таймаутами PostgreSQL/transport. Цикл не
обещает прервать зависшую доверенную фабрику, tick, report или close; его signal
не заменяет таймауты этих операций. Нет установленных alert/метрик/trace collector,
нет измеренного SLO. L25 не закрыт. Публичная ready-проверка сайта этим не меняется.

## Доказательства и следующий допуск

Native-тесты проверяют read-only check, preflight до claim, последовательность,
фиксированные интервалы, остановку на всех стадиях, generic ошибки и backpressure.
Отдельные Node-процессы проверяют SIGTERM/SIGINT, drain и повреждение stdout.
Owned PostgreSQL18 проверяет остановку во время GET с завершением первой оплаты,
сохранение второй задачи до перезапуска и отсутствие повторного receipt;
неизвестный COMMIT claim приводит к code1, новый процесс ждёт lease и затем
выполняет прежнюю задачу одним GET. ЮKassa transport в этих тестах синтетический.
Проверочная инверсия условия запуска сломала read-only тест; условие восстановлено.
