## Исправления

Два реальных RED-сценария показали пробелы: после задержанного ACK последней проверки старый worker успевал сделать POST по истёкшей lease; ожидание FK-блокировки строки отклика внутри effect INSERT позволяло применить возврат после первоначальной проверки.

Добавочная0053 вводит только private `assert_application_compensation_job_remaining`: существующий0049 guard блокирует строку задачи и проверяет shop/token/state/expiry, затем новый helper вычисляет оставшиеся миллисекунды через wall-clock `clock_timestamp()`. Значение должно быть целым в пределах1–300000. PUBLIC EXECUTE отозван. Прежний void helper, API `assertActive()` и его права сохранены; новая возможность выдана только ограниченной роли disposable fixture.

Worker сохраняет отдельный монотонный deadline каждого tick. Начало замера — до ожидания SQL, поэтому задержка запроса или COMMIT ACK не продлевает срок. Непосредственно перед реальным fetch POST синхронно проверяется deadline. Конфигурация магазина копируется; параллельные tick не делят изменяемый deadline. GET/readback известной операции остаётся доступен, новый ключ/окно/резервирование не добавляется.

Effect повторяет необязательную проверку после INSERT и чтения результата. Истечение во время FK/notification wait откатывает исходный payment status, effect и уведомление в одной транзакции. Сохранённое ранее доказательство провайдера позволяет следующей lease продолжить GET-only. Snapshot, доставка, контакты и статус отклика сохраняются. Вызовы без callback продолжают работать с прежними правами.
