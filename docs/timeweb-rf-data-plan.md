# Перенос персональных данных БЛИЖНИЙ в РФ

Дата: 25.09.2026. План для проверки на тестовом контуре до регистрации и реальных оплат.

## Текущее состояние

Приложение использует Supabase Auth в браузере, серверный REST/Data API и Storage. Подключенный проект расположен в `eu-west-1` (Ирландия). Замена только PostgreSQL или установка российского прокси не перенесет первичную запись Auth, загрузку файлов и хранение персональных данных в РФ. Полный переход требует совместимого Auth, API, Storage, файлов, резервных копий и логов в российском регионе.

## Выбор размещения

| Вариант | Когда подходит | Что потребуется |
| --- | --- | --- |
| Supabase self-hosted на существующем VPS Timeweb в РФ | Есть запас ресурсов и администрирования; минимальная переделка текущего кода | Docker, PostgreSQL, Auth, REST, Storage, TLS, SMTP, мониторинг, резервирование и обновления на своем сервере |
| Отдельный VPS Timeweb в РФ под Supabase | Сайту и БД тесно на текущей машине, хочется разделить нагрузку | Дополнительный VPS и приватная сеть; остальная схема та же |
| Managed PostgreSQL Timeweb в Москве/Санкт-Петербурге | Нужны управляемые обновления/бэкапы БД | Отдельное размещение Auth, REST, Storage в РФ и дополнительная работа с интеграцией; одной управляемой БД недостаточно |

Документация Supabase указывает для полного self-hosted стека минимум 2 CPU / 4 ГБ RAM / 40 ГБ SSD и рекомендует 4 CPU / 8 ГБ RAM / 80 ГБ SSD **для самого стека**. Приложению Next.js нужен ресурс сверх этого. Поэтому совместное размещение рассматриваем после измерения памяти и диска текущего VPS; рабочий ориентир для одного сервера — 4 CPU, от 12 ГБ RAM и от 100 ГБ доступного SSD. Это ориентир проекта, а не тарифное требование Timeweb. Если текущий VPS меньше, сначала оценить стоимость увеличения или второй VPS. Не заказывать услуги до проверки параметров и бюджета.

## Порядок переноса

1. Зафиксировать регион российского VPS, CPU/RAM/диск, текущую нагрузку, время простоя и критичные интеграции. Собрать перечень всех мест с ПД: Auth, профили, контакты и точные адреса, платежные метаданные, Storage, SMTP, журналы, аналитика, бэкапы.
2. Поднять отдельный тестовый self-hosted контур в РФ, закрыть PostgreSQL от Интернета, выдать публичный HTTPS только нужному API, настроить почту/подтверждение адреса, ограничение попыток входа, обновления и наблюдаемость.
3. Снять согласованные `roles.sql`, `schema.sql`, `data.sql` по официальной инструкции Supabase; отдельно перенести объекты Storage. Данные содержат `auth.users` и требуют защищённого временного хранения только в РФ. Не класть дампы, ключи и `.env` в GitHub или CI-артефакты.
4. На тестовом контуре проверить восстановление, количество строк, связи, RLS/grants, доступ ролей, файлы, регистрацию, вход, восстановление пароля, блокировки, кабинет на двух аккаунтах, создание/оплату/публикацию, webhook и публичные страницы. Новые JWT-ключи потребуют повторного входа пользователей.
5. Сделать зашифрованные регулярные копии вне основного VPS, хранить их в РФ и проверить восстановление на отдельной машине. Снимок диска не заменяет проверенный дамп PostgreSQL и копии объектов.
6. Перед переключением заморозить запись на старом контуре, выполнить финальный экспорт и сверку, поменять переменные `NEXT_PUBLIC_SUPABASE_URL`, ключи сервера/браузера, URL файлов, SMTP и DNS/реверс-прокси. Проверить, что браузер больше не обращается к зарубежному Auth и Storage. Вернуть запись только после проверки российского контура. Старую зарубежную базу выводить из эксплуатации после юридической проверки сроков и обязанностей.
7. Отдельно проверить документы оператора, уведомления и основания обработки/передачи данных с юристом. Технический перенос сам по себе не завершает правовую работу.

## Следующее решение

Нужны конфигурация и регион текущего Timeweb VPS, свободные ресурсы в пике и доступ к управлению сервером через безопасный канал. До этого не менять URL Auth и не переносить рабочие данные наугад.
