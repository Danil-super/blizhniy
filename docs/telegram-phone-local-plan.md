# Telegram phone — локальная реализация по ТЗ владельца, 28.10.2026

Исходное ТЗ: приложенный владельцем документ «ТЗ: подтверждение телефона через Telegram Login». Пользователь поручил реализовать локально, без публикации, и уточнил: внутренние переписки не предусмотрены; Login-клиента ещё нет. Эти требования принимаются как утверждённая спецификация. Новые аккаунты/чаты/SMS/Gateway не создаются.

## Контур

Существующий Next.js backend работает на российском VPS, данные — в отдельной управляемой PostgreSQL Timeweb; файлы — на VPS вне релизов. Telegram служит внешним источником подтверждения с явным согласием пользователя. Supabase, Auth0 и дополнительные серверы не подключаются. Сейчас меняются только локальные исходники/изолированные тестовые БД. Изменения рабочего сайта и рабочей БД не разрешены этой задачей.

## Реализованная схема

1. Один новый модуль phone-verification. Authorization Code + S256 PKCE + state + nonce, только scope openid phone, фиксированные HTTPS endpoints Telegram. openid-client с обязательной дополнительной проверкой криптографической подписи (enableNonRepudiationChecks), RS256, issuer/audience/exp/iat/nonce, phone_number_verified=true. Сетевые запросы ограничены по времени/размеру, без redirect, произвольных адресов и userinfo. Браузер не передаёт достоверные phone/Telegram ID/verified.
2. Попытка привязана к существующему user_id, точному хешу app-сессии и её auth_version. State хранится хешированным. Срок — 10 минут. Callback атомарно забирает попытку до сетевого обмена, повтор запрещён. После обмена с проверкой JWT сохраняются только кандидат номера, Telegram sub, хеш токена и короткоживущие служебные данные; сам токен не сохраняется. Затем отдельный CSRF-защищённый POST явно подтверждает номер/замену с проверкой текущего revision профиля. До этого прежняя привязка не меняется.
3. Добавочная миграция 0031: защищённые таблицы попыток и привязок, уникальные индексы на user_id/phone/telegram subject, RLS и точечные права только серверной роли. Клиентского SQL/Data API нет в текущем контуре; PUBLIC/anon/authenticated не получают доступ. Обычный профиль не сохраняет verification claims; его достоверное представление получает их из защищённой привязки. При ручном вводе другого номера прежняя привязка сохраняется, но новый номер остаётся неподтверждённым; явное удаление очищает привязку. Все замены атомарны, конфликты не раскрывают чужой аккаунт.
4. Владелец уточнил: подтверждение требуется перед размещением во всех разделах. Политика по умолчанию выключена; UI сохраняет форму и открывает подтверждение до продолжения. SQL защищает новые переходы listings/work/service в published и создание намерения оплаты размещения (отклики не являются новым размещением). Старые публикации и их обычное редактирование остаются доступны. Для снятия номера во время уже начатой оплаты миграция 0032 добавляет waiting_phone: подтверждение пробуждает очередь без потери гонки; первый оплаченный срок начинается с фактической публикации, без продления при replay/restore. Установленный триггер определяется из БД, отдельного расходящегося env-флага нет. Worker не получает новых прав или EXECUTE. Внутренних переписок нет.
5. Подтверждение открывается в отдельном окне, сохраняя объявление/настройки в прежнем окне. Callback возвращается только на заранее разрешённую страницу обзора номера. Межоконное сообщение — только сигнал перечитать состояние с сервера, не источник доверенных данных. Несохранённые поля не перезаписываются, конфликт revision не обходится. Локальный ingress разрешает cross-site GET только для точного callback с последующей проверкой state/session; прочие origin/CSRF ограничения сохранены.
6. Без конфигурации UI сообщает о недоступности, обязательность выключена. Настоящую привязку без Telegram не имитировать. Криптографические/сетевые тесты используют явно синтетический OIDC сервер/JWK и отдельную БД. Инструкция BotFather и локального приватного файла настроек готовится без секретов. При opt-in локальный процесс разрешает только HTTPS oauth.telegram.org для этой интеграции, без разблокировки SMTP/merchant/прочих внешних адресов.

## Проверки

Node22 native tests; types/lint/build; реальные криптографические JWT проверки и отрицательные nonce/issuer/aud/expired/signature; одноразовость и session revocation; конкуренция уникальных привязок и rollback замены на PostgreSQL; неизменённость email; защита profile API/прямого SQL; публикация/повторная публикация/оплата; восстановление исходного действия; адаптивный интерфейс. Существующие tests/guard/workflows не ослабляются.

## Ограничения готовности

Реальный Telegram E2E заблокирован отсутствием Login Client ID/Secret и регистрации Allowed URLs. Нельзя объявлять функцию проверенной с Telegram или работающей в production. Локальная реализация и тесты выполняются независимо. Публикация/рабочая миграция требуют отдельного этапа.

## Разбор инженерного ревью

Приняты и исправлены: terminal blocked вместо ожидания телефона; расходование срока до публикации; гонка подтверждения с acknowledgement; расхождение env-флага со схемой и квитанцией; потеря отметки ожидания после временного retry; устаревший parser доверенного профиля; потеря dirty settings и гонка с параллельным save; фиксированный callback при локальном canonical ingress. Негативные сценарии покрыты криптографическими, HTTP, SQL и profile-provider тестами. Дополнительную проверку другой моделью владелец явно пропустил; внешние CLI не запускались.

Настройка, локальные команды и честные ограничения: [telegram-phone-setup.md](telegram-phone-setup.md).
