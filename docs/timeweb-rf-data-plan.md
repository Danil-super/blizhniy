# Перенос первичного сбора данных БЛИЖНИЙ на контур в РФ

Статус: технический план на 27.09.2026. Сервер Timeweb ещё не предоставлен; рабочую БД и ключи этим документом не переносим. По подтверждению владельца существующие записи тестовые и могут быть удалены, поэтому для первого переключения предпочтителен чистый контур с повторной регистрацией тестовых аккаунтов. Правовую оценку размещения и сторонних сервисов выполняют отдельно.

## Что нужно перенести вместе

| Поток в коде | Сейчас | Условие переключения |
| --- | --- | --- |
| Регистрация, вход, восстановление, сессии | `src/lib/supabase-browser.ts` и `AuthForm` обращаются из браузера в Supabase Auth; `src/lib/server-auth.ts` проверяет токен через `/auth/v1/user` | Auth, его база, почта и публичный HTTPS API работают в РФ. Не оставлять зарубежный Auth при российской PostgreSQL. |
| Данные приложения | `src/lib/supabase-rest.ts` использует PostgREST `/rest/v1` с серверным `SUPABASE_SERVICE_ROLE_KEY`; публикация платежа использует RPC | В РФ работают PostgREST и полная схема PostgreSQL: `auth`, `public`, `storage`, роли, функции, RLS и grants. БД закрыта от Интернета. |
| Фотографии | `src/lib/storage-upload.ts` пишет сервером в публичный bucket `blizhniy-media`; `/storage/v1/object/public/blizhniy-media/` зашит также в клиентском разборе URL | Storage API, байты объектов и резервные копии находятся в РФ. Если сохранять старые файлы, перенести объекты отдельно и проверить все ссылки/пути; SQL dump не содержит байты файлов. |
| Сбор через сайт | Next.js API принимает анкеты, контакты, адреса, бронирования и платежные запросы | Публичный production Next.js и его журналы размещены в РФ; старые VPS/preview с формами и зарубежными `NEXT_PUBLIC_SUPABASE_*` отключены либо обновлены до открытия записи. |

Текущий подключённый Supabase расположен в `eu-west-1`. Российский прокси перед ним или одна PostgreSQL на Timeweb не меняют точку первичной записи Auth и Storage. Самостоятельно развёрнутый полный стек Supabase на отдельном сервере в РФ — рабочий вариант для проверки; [официальная инструкция](https://supabase.com/docs/guides/self-hosting/docker) указывает минимум 2 CPU / 4 ГБ / 40 ГБ и рекомендует 4 CPU / 8 ГБ / 80 ГБ для всех компонентов, **без ресурса для Next.js**. Конкретный тариф, диски и регион выбрать после данных от Timeweb и измерений.

## Архитектура и зависимости

1. Закрепить проверенную версию self-hosted Supabase Docker Compose: PostgreSQL, Auth, PostgREST, Storage, API gateway. TLS открыть только на gateway; Studio и PostgreSQL оставить в закрытой сети. Уточнить [изменения self-hosted конфигурации](https://supabase.com/changelog?types=breaking-change) перед установкой, особенно маршруты Auth и ключи. Код сейчас отправляет anon/service-role ключ как `Authorization: Bearer`, поэтому для первого cutover нужны совместимые JWT `ANON_KEY`/`SERVICE_ROLE_KEY` либо отдельная правка и тесты кода для нового формата publishable/secret ключей. Service-role ключ никогда не отдавать браузеру.
2. Настроить в РФ хранилище файлов: локальный том с независимой копией или S3-совместимый backend с подтверждённым размещением объектов и копий в РФ. Bucket `blizhniy-media` должен сохранить ограничения 10 МБ и JPG/PNG/WEBP/GIF; загрузка идёт через серверный `/api/uploads/media`. Для публичных изображений проверить прямую выдачу без права перечисления bucket.
3. Проверить полную воспроизводимость схемы на чистом disposable стенде. `docs/SUPABASE_SETUP.md`, `supabase/schema.sql`, `seed.sql`, `rls.sql` описывают исторический старт и **не равны текущей БД**. Сверить `supabase/migrations/`, фактическую историю миграций и прямые изменения в действующей БД; проверить `auth`/`storage`, extensions, триггеры, функции, роли, RLS/grants и seed до направления трафика. Для managed PostgreSQL сначала доказать совместимость требуемых ролей, расширений и прав Auth/Storage.
4. Настроить Auth целиком: домен API, Site URL и redirect allowlist, подтверждение email, SMTP с известным местом обработки и хранения, восстановление пароля, ограничения попыток и CAPTCHA. Действующую проверку Turnstile на сервере приложения нельзя считать защитой прямого вызова Auth без проверки конфигурации самого Auth.
5. Выдать **новые** ключи и секреты вне Git и CI-артефактов. `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` попадают в клиентский bundle и требуют новой сборки Next.js; `SUPABASE_SERVICE_ROLE_KEY` остаётся только на сервере. Проверить также `NEXT_PUBLIC_SITE_URL`, платежные и webhook-ключи, SMTP и фактически используемый `NEXT_PUBLIC_2GIS_API_KEY` (в `.env.example` пока указан устаревший ключ Яндекс Карт).
6. Отдельно инвентаризовать внешние потоки: Cloudflare Turnstile (браузер и siteverify, IP), 2ГИС (скрипт карты и геокодирование адреса), ЮKassa (платёж и webhook), ссылки на Яндекс Карты, почтовый провайдер, Vercel preview, GitHub Actions/артефакты. Отключить или заменить передачу точного адреса, контактов и других данных сторонним сервисам до согласования технического режима; не считать перенос Supabase закрытием этого вопроса. Журналы Next.js/PM2, reverse proxy, Auth, PostgREST, Storage и backup тоже учитывать как отдельные места хранения.

## Тестовый cutover и выпуск

1. До теста закрыть новые регистрации и реальные оплаты на всех доступных экземплярах сайта. На российском стенде установить стек и применить сверенную схему **без старых тестовых пользователей и объектов**. Если позже потребуется сохранить реальные данные, сначала подготовить отдельный однократный перенос `roles/schema/data` по [инструкции Supabase](https://supabase.com/docs/guides/self-hosting/restore-from-platform) с сохранением связей по UUID; файлы Storage переносятся отдельно. Не выполнять rolling migration с двумя Auth.
2. На двух новых синтетических аккаунтах проверить регистрацию, подтверждение email, вход, refresh/выход, восстановление, блокировку, изоляцию кабинетов, RLS и запрет клиентских платёжных записей. Проверить объявления, вакансии, заказы, специалистов, изображения, бронирования, платёжный sandbox, повторы webhook, уведомления, `/api/ready`, sitemap и публичные URL. Зафиксировать результаты и проверить восстановление БД **и файлов** из зашифрованной копии в РФ на отдельном контуре.
3. На время переключения остановить записи, фоновые обработчики платежей и входящие webhook; сделать финальную сверку/снимок, даже если данные тестовые. Обновить URL и ключи одновременно в окружении Next.js и self-hosted стека, затем **пересобрать** приложение и сменить DNS/маршруты. `scripts/deploy-release.sh` копирует `.env*` из предыдущего релиза; перед сборкой заменить их безопасно. Старые релизы и автоматический rollback не должны возвращать клиентский bundle или `.env` с зарубежным Auth. При сбое оставить запись выключенной и восстановить российский релиз, а не автоматически включать старый Auth.
4. Проверить в браузерном network trace и серверных egress/DNS, что signup/login/refresh/recovery, `/rest/v1`, upload и media URL идут на новый российский API и **не обращаются к старому `*.supabase.co`**. Проверить TLS, webhook endpoint, письмо со ссылкой на верный домен, логи без токенов/лишних ПД, актуальную версию VPS и отсутствие действующего Vercel/preview со старыми ключами. Открыть регистрацию и оплаты только после этих проверок; старый проект вывести из записи и затем из эксплуатации по отдельному решению.

## Что понадобится от Timeweb и владельца

- Подтверждённый физический регион для серверов, томов, object storage, журналов, снимков и резервных копий; состав тарифа и возможность увеличить CPU/RAM/диск. Для полного стека планировать отдельный ресурс от Next.js.
- Доступ к проекту Timeweb с правом создать серверы/диски/сеть, SSH ключ для ограниченного deploy-пользователя, статические IP, правила firewall/private network, доступ к DNS для домена приложения и нового API, TLS.
- Решение «том + отдельная копия» или S3-совместимое хранилище в РФ; endpoint, region, bucket, учётная запись с ограниченными правами, политика резервирования и тест восстановления.
- Расписание и срок хранения зашифрованных копий PostgreSQL **и объектов**, место хранения вне основного VPS, ответственный за восстановление, допустимые RPO/RTO; место и срок хранения логов.
- SMTP/почтовый провайдер и его регион, учётные данные, домен отправителя/SPF/DKIM, допустимые redirect URL; доступ к настройке ЮKassa webhook и к секретам деплоя. Секреты передавать через защищённый канал, не в PR.
- Окно остановки записи и ответственный за go/no-go. Подтверждение перечня публичных экземпляров (VPS, Vercel и preview), которые надо закрыть или перенастроить в тот же момент.

Это технический план проверки. Он не подтверждает юридическую достаточность выбранного размещения или внешних сервисов; требования к первичному сбору и внешним передачам отдельно сверить с [частью 5 статьи 18 закона № 152-ФЗ](https://mintrud.gov.ru/docs/laws/130).
