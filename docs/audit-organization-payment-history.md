# Организация и история платежей: локальная приёмка 13.11.2026

Продолжение [разделения профиля](audit-profile-loading.md), только локально.
Обнаружен функциональный пробел: PostgreSQL-кабинет загружал историю через
старый `/api/cabinet/payments`, требующий Supabase. Ответ503 превращался
старым клиентом в пустой список. История новой БД не отображалась.

## Изменения

- Новый `/api/account/payments` читает заказы по существующей HttpOnly-сессии.
  POST, строгие Origin/Host/ingress/body/cookie проверки, общий лимитер и
  `withAppSessionTransaction` сохранены. Ожидаемый владелец должен совпасть
  с текущим пользователем; даже администратор здесь читает только свои платежи.
- Используются существующие SELECT-права. Нет миграций, новых GRANT или ролей.
  Соединение заказов с неизменяемыми намерениями сверяет все поля привязки.
  В ответе только ID, тип, точная сумма, статус, TEST и дата создания.
  Чеки, адреса, request_body, merchant и секреты не передаются.
- История показывает все пять статусов, включая отмену и возврат, независимо
  от текущего магазина. Порции по50, курсор created_at/UUID с микросекундами;
  отдельный запрос выбирает максимум51 запись. Ошибка не заменяется пустым
  списком; доступны повтор и подгрузка следующей порции. Смена владельца
  сбрасывает экран, уход отменяет чтение, поздний ответ игнорируется.
- В истории нет подтверждения/создания оплаты. Ссылки ведут в соответствующие
  разделы кабинета, а не в зависящие от текущего магазина старые status readers.
  Это также исключает случайный запуск simulator recovery отклика из истории.
  Авторизация обновляет last_seen сессии; финансовые записи не изменяются.
- Форма организации вынесена из общего legacy-модуля. В PostgreSQL используется
  существующий профильный provider и его CAS/owner-защита. Legacy-адаптер
  сохраняет прежний saveCabinetProfile. Поля, лимиты и проверки ИНН/ОГРН
  сохранены; ошибка не очищает введённые значения. Форма имеет ключ владельца.
- Организация и история загружаются отдельными client chunks. Открытые настройки
  пока по-прежнему используют старый редактор по запросу. Режимы backend
  не переключаются. Новые зависимости и исключения guard не добавлены.
- Реальный axe обнаружил недостаточный контраст прежнего зелёного статуса
  телефона и статуса организации; заменён на используемый проектом #0a7b2b.

## Проверки

Native2712/2712 на окончательном кандидате, focused проверки контрактов, HTTP,
владельца/истечения сессии, порции51 при одинаковой дате, отказа/retry,
отменённого чтения и полей организации прошли. Сборка и fast окончательного кандидата прошли.
Прежнее lint-предупреждение targetType не скрывалось.

На постоянном synthetic57 выполнены Chromium → HTTP → действующая runtime-роль:
сохранение пяти полей организации, reload и неизменность остальных полей
профиля;19 существующих платежей сверены с PostgreSQL. Проверены отказ чужому
владельцу, лишнему ключу запроса и после logout; реальный seek после первой
записи вернул остальные18. Намеренная ошибка503 в первом
чтении с успешным повтором. Хеш финансовых заказов до/после одинаковый.
Три ширины320/768/1440, два экрана:6 axe-проверок без serious/critical и overflow.
JS-ошибок и внешних browser-запросов нет. Проверка воспроизводится командой
`node --experimental-strip-types scripts/check-local-organization-payments-ui.mjs`
на принадлежащем проекту синтетическом стенде после core checkout fixtures.
Она изменяет только данные организации тестового @local.invalid аккаунта.

В раннем проверочном скрипте исправлены неверные ожидания адреса после входа
и GET вместо действующего POST session; продуктовая авторизация не менялась.
Одновременный запуск types и build однажды дал TS6053 на генерируемых .next
файлах; fast повторён последовательно после сборки, настройки TS не менялись.
Замечание ревью о неверном bare URL оплаты бегущей строки исправлено на
существующий список; добавлена проверка ссылки. Владелец пропустил внешнее
ревью другой моделью.
