# F02: отдельные права обработчика возвратов

10.11.2026. Локальный кандидат; запуск службы и production не разрешаются этим документом.

`scripts/refund-worker-role.mjs` возвращает SQL-план для новой роли `blizhniy_refund_worker`: NOLOGIN, без наследования/членств и административных признаков, максимум четыре подключения. Пароль, включение LOGIN, выполнение GRANT и выбор подключения отсутствуют. Старый reconciler, его допуск managed PostgreSQL, runtime и workflows не изменены.

План даёт чтение конкретных финансовых колонок, INSERT только входных полей неизменяемых журналов и EXECUTE четырнадцати частных функций очередей/компенсаций. Нет доступа к сессиям, паролям, профилям, прямому изменению публикаций/оплаты, записи решений администратора, operator recovery, таблицам очередей, DELETE или выдаче прав. Даты источников включены в SELECT: существующие SECURITY INVOKER guards читают полные строки. Сохранённый request_body может содержать исходный чек; это доверенный финансовый процесс, эти данные не выводятся в журналы.

Для SELECT FOR UPDATE необходимо UPDATE хотя бы одной колонки. Добавочная 0054 разрешает использовать UPDATE(id) только как возможность блокировки: три ALWAYS BEFORE UPDATE OF id триггера отклоняют любые такие UPDATE от current_user или session_user новой роли, включая id=id и SECURITY DEFINER. Отдельное условие OF id сохраняет штатное изменение payment_orders.status внутри существующего доверенного эффекта возврата. Миграция не создаёт роль и не выдаёт права.

Read-only preflight проверяет PG18, текущую БД, совпадение текущей/исходной роли, read-only/origin, LOGIN/лимит, отсутствие членств/административных признаков, точные эффективные колоночные и EXECUTE права без grant options, отсутствие CREATE/TEMP/опасных прав таблиц и последовательностей. Проверяются все namespace CREATE, повышенные права параметров и дополнительные ACL системных функций/таблиц/колонок относительно initdb. Явные права чтения серверных файлов через pg_read_binary_file и доступ к pg_authid запрещаются, в том числе через PUBLIC. Запросы имеют statement_timeout 5s и lock_timeout 1s.

Допуск журнала — только полный статический список 0001–0054 с SHA256 исходников. Неизвестная 0055, неверный хеш, отключённый/изменённый lock guard или другой набор его колонок отклоняются. Ошибки возвращаются без SQL, ключей и реквизитов.

Особенность исходного PostgreSQL18.6: 62 публичных SELECT из information_schema.sql создаются после записи pg_init_privs. Их точный список взят из официального REL_18_6, допускаются только SELECT без grant option у встроенных таблиц/представлений с системным OID. Иначе стандартное schemata ошибочно отклонялось бы как лишний доступ. Новые объекты, внутреннее _pg_foreign_servers и UPDATE этим списком не разрешаются; отдельные негативные проверки это подтверждают. Источник: [information_schema.sql](https://github.com/postgres/postgres/blob/REL_18_6/src/backend/catalog/information_schema.sql), [порядок initdb](https://github.com/postgres/postgres/blob/REL_18_6/src/bin/initdb/initdb.c).

Проверка не является полной аттестацией фактических business-функций/ограничений БД: журнал сам по себе не доказывает отсутствие ручного изменения этих объектов. Перед подключением к службе ещё нужны такая сверка, проверка runtime/артефакта/TLS/TEST-магазина и отдельное решение владельца. Проверка прав в начале не защищает от последующего вмешательства владельца БД. Это доверенный финансовый worker, а не разделение магазинов через RLS; фактический магазин и TEST проверяют существующие stores/процессоры. Ни LIVE, ни автоматический запуск этим кандидатом не добавлены.

Отдельный остаток: перенести расширенные проверки системных ACL/параметров/схем на старый payment-reconciliation-role.mjs с review точного diff. Его прежние проверки охватывают меньше категорий прав; наличие опасных grant на production в этой работе не проверялось и не утверждается. Роль approval/recovery оператора также требует отдельного плана: worker не получает её полномочия.

Проверки используют только owned disposable PostgreSQL18.6 и fake HTTP. Они покрывают три вида размещения и непросмотренный оплаченный отклик, ровно один POST/эффект, сохранность отклика, уведомление о размещении, отрицательные изменения ACL/схемы/guard. Реальный RED до подключения 0054: UPDATE users SET id=id прошёл вместо ожидаемого отказа. После 0054 блокировка проходит, UPDATE запрещён; финансовые definer-эффекты продолжают работать.

Итоговая регрессия: focused46/46, native2576/2576, все13 обязательных PG-наборов774/774 за216.8s без skips. Временная диагностика удалена; точные итоговые версии кода одобрены владельцем для локального сохранения.

Ручная локальная БД и production не получают 0054 или новую роль. Откат кандидата до установки роли — удаление трёх refund_worker_lock_only триггеров и guard_refund_worker_locks(); существующие журналы/данные не меняются.

Основание поведения PostgreSQL: [SELECT: права для блокировки](https://www.postgresql.org/docs/18/sql-select.html), [column-specific triggers](https://www.postgresql.org/docs/18/sql-createtrigger.html), [начальные ACL](https://www.postgresql.org/docs/18/catalog-pg-init-privs.html). Context7 PostgreSQL18 был получен после восстановления доступности MCP.
