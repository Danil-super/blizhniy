# Полная форма черновика на PostgreSQL

Форма `/razmestit/obyavlenie` сохраняется через cookie-only `/api/account/listing-form`, без Supabase или browser bearer token. Обычный «Сохранить черновик» переносит тип, название, описание, точную RUB-цену, категорию/подкатегорию, город, адрес/координаты, телефон/мессенджер, параметры аренды и порядок фотографий. Опубликованный статус и деньги этот инкремент не меняет: кнопка оплаты сообщает, что этот этап ещё переносится, и не вызывает старый платёжный API.

## Контракт и доступ

POST `{expectedOwnerId,listingId}` читает полную приватную форму; PUT добавляет `{expectedRevision,form}` и заменяет форму целиком. Ответ `{id,revision,form,photos}`. GET405. Cookie, Host/Origin/custom header/Sec-Fetch/query/trusted ingress и общий PostgreSQL session limiter такие же, как у существующих приватных черновиков. Body cap4КиБ/64КиБ, чтение2s. Вне postgres-mode404. Ошибки401/404/409/422/429 и generic503, no-store/no-referrer/nosniff/CSP; audit не содержит форм, контактов, IDs или SQL причин.

`ListingFormDraft` — строгий allowlist16 полей, без owner/status/isPaid/tariff/готовности файлов. Частичный черновик допустим. Категория задаётся slug корневой категории и точным именем прямой подкатегории; город — точным именем. Сопоставление происходит в новой БД в транзакции: неизвестное или неоднозначное имя отклоняется. UUID старой БД не принимаются. Существующая политика черновиков допускает неактивную сохранённую категорию; полнота/активность для публикации проверяется будущим lifecycle, не этим сохранением.

Описание≤10000, title≤160, адрес≤300, телефон≤40, мессенджер≤500; недопустимые controls и malformed Unicode отвергаются. Мессенджер — прежняя нормализация http(s)/Telegram, без credentials и без server-side fetch. Координаты finite, в пределах±90/±180 и только парой; showExact требует координат. Booking — только известные поля, ограниченные значения/даты/время/списки; неизвестные поля не игнорируются. Цена объявления — точная decimal string, не float. Денежные расчёты бронирования здесь не запускаются.

Каждое чтение/сохранение проходит App session transaction и проверку expected owner. User→session→owned draft lock, общая bigint-string CAS с текстовым редактором и фото. Все поля, FK и связи фото изменяются в одной транзакции; чужой/pending/unknown media отклоняется до изменения связей. Metadata/files/quota при этом не изменяются; суммарный media bound160МиБ проверяется на сервере. До commit сессия повторно проверяется. Unknown COMMIT не повторяется автоматически.

## Браузер

Создание пустого draft использует прежний стабильный creation intent. Для каждого File создаётся один upload intent; потерянный ответ проверяется тем же intent. После начала сохраняется неизменяемый снимок формы, поля блокируются от изменений, чтобы новые правки не игнорировались. Неизвестный полный PUT блокирует повторную запись. Явное чтение сравнивает все поля и порядок фото: совпадение подтверждает результат; отличающаяся версия показана владельцу перед его явным решением заменить её. Повтор PUT после выбора использует прочитанную revision, а не отключает CAS.

Форма не пишет поля/файлы в localStorage. При временной перепроверке сессии owner-keyed новая форма сохраняет несохранённые DOM controls/File в скрытом inert subtree, без разрешения взаимодействовать. При подтверждённом выходе или другом owner subtree уничтожается. Это особенность формы с uncontrolled inputs; она не является заявлением об отсутствии private DOM во время recheck. Старый приватный редактор кабинета по-прежнему прячет DOM с сохранением своих текстовых state buffers. Незавершённые запросы при уничтожении формы отменяются; сервер не считает disconnect доказательством rollback.

В кабинете блок «Категория, место и контакты из полной формы» читает owner-only snapshot. Кнопка «Изменить дополнительные поля» открывает редактор категории/подкатегории, города/района, адреса/координат, контактов и всех существующих параметров аренды. Подсказки категорий и городов используют прежний локальный каталог; существующие значения не отбрасываются, окончательное сопоставление проверяет новая БД. Основной текст и фотографии редактируются отдельно; одновременные действия в одном кабинете блокируются. Закрытие дополнительного редактора возвращает к списку, а не к устаревшему снимку основного редактора.

Дополнительный редактор отправляет полную форму с точной revision исходного чтения, сохраняя её текст и порядок фото. Ошибка/неизвестный результат блокирует повтор до явной сверки; совпавшее чтение подтверждает потерянный ответ без второго PUT. При конфликте показана полная сохранённая версия. Владелец может принять её или оставить только свои дополнительные правки: при последующем сохранении основной текст и фото берутся из явно прочитанной новой версии, revision не округляется. Буферы живут только в owner-keyed React state, без браузерного хранилища, переживают временное удаление private DOM при проверке сессии и уничтожаются при смене аккаунта. Валидация черновика не подменяет будущие правила публикации.

На `/cabinet` и `/cabinet/obyavleniya` PostgreSQL workspace использует собственную private display-границу без внешнего gate, который раньше уничтожил бы буфер при recheck. Legacy-ветки и остальные кабинетные экраны сохраняют прежний gate; дополнительные ссылки обзора остаются за проверкой входа. Серверная авторизация, session store и права API не меняются.

Публикация/модерация/оплата и остальные типы публикаций остаются незавершёнными шагами. Общий guarded account/media deletion и restore rehearsal также ещё не завершены: массовый запуск не объявлен готовым.

## Установка и откат

Миграции0001–0013 не меняются; новая схема не нужна. Явно добавить runtime SELECT/UPDATE только восьми существующих колонок `district,address,latitude,longitude,show_exact_address,contact_phone,messenger_url,booking`. Прежние author/status/payment/DELETE/DDL ограничения сохранить. HTTP не выдаёт grants и не использует owner credential. Проверить ограниченную роль до выкладки. При откате к предыдущему проверенному коду сохранить PostgreSQL Auth, ключ/почту, ingress overwrite, файлы и additive schema: не возвращать legacy Auth после появления аккаунтов.

Проверки: pure contract/intent/body guards; настоящая owned PG18 с column grants, atomic rollback, чужими/pending media, конфликтом двух писателей и lost acknowledgement; настоящий Next production build + Chromium с synthetic-only SQL/API transports; затем такой же сценарий на рабочем VPS с собственным техническим аккаунтом. SQL fixture metadata не является доказательством файлов; реальные upload/private pixels отдельно проверены в media cutover.
