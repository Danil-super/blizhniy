# F02: проверенная привязка возврата и история исходов

Локальный инкремент02.11.2026: `PostgresRefundJournalStore`, добавочная opt-in миграция0038 и отдельный disposable PostgreSQL runner. Новый код делает только GET и сохраняет проверенные сведения в приватный журнал. Нет POST возврата, маршрута для пользователя/администратора, изменения исходной оплаты, снятия размещения или автоматического освобождения reservation. Ручной стенд остаётся35; production БД, её права и оба российских сервера не меняются.

## Что и как сохраняется

`payment_refund_provider_links` навсегда связывает одну локальную reservation/request operation с одним provider refund UUID; один provider UUID нельзя связать с другой операцией. Ссылка требует существующего первоначального окна0037, но истечение окна не запрещает безопасное чтение уже известного возврата. `payment_refund_observations` хранит append-only наблюдения `pending`, затем не более одного из `succeeded`/`canceled`. У каждой записи исходная дата возврата с полной nanosecond precision и отдельное время наблюдения БД. Ссылки и наблюдения нельзя UPDATE/DELETE/TRUNCATE. Схема не выдаёт новых GRANT.

`reconcile(operationId, candidateRefundId)` предназначен только для доверенного финансового обработчика. Первый candidate должен происходить из будущего корректно обработанного ответа провайдера; browser/webhook payload не является источником доверия. Если ссылка уже есть, `reconcile(operationId)` использует её, а другой candidate отклоняется до сети. Если ссылки нет и ID неизвестен, метод отказывает: это не разрешение отправить запрос с новым ключом.

Сначала отдельная короткая READ COMMITTED транзакция читает reservation, блокирует исходный intent, затем order и новым запросом проверяет неизменяемые source/request/anchor/capture. Только полный TEST `listing`/`vacancy`/`workRequest`, исходная сумма, магазин, canonical body/SHA/idempotence key. Допустим исходный order `succeeded` или уже `refunded`: поздняя сверка должна оставаться доступной. Текущие тарифы, профессия, профиль, блокировка пользователя и phone proof не заменяют первоначальную покупку. Позднего user lock нет.

После завершения транзакции existing known-refund reader делает GET исходной оплаты и GET кандидата с прежним общим35s/3attempt budget. Проверяются магазин/TEST/payment metadata и полный refund binding. Дополнительный RED выявил недочёт: fingerprint двух DB-транзакций не обнаруживал противоречие между неизменяемым capture в БД и новым GET capture, если возврат датирован позже обоих. Теперь журнал передаёт сохранённый `paymentCapturedAt`; reader сравнивает полный момент списания через `mergePaymentVerification` и отклоняет расхождение ещё до GET возврата. Эквивалентная nanosecond запись допустима, отсутствие optional capture в GET сохраняет известный нижний предел. Прежние callers, не передающие stored capture, сохраняют прежний known-ID contract.

Для связи с нашей operation дополнительно обязательны `metadata.localRefundId` и `metadata.localPaymentId`. По [официальному OpenAPI ЮKassa](https://yookassa.ru/developers/api/yookassa-openapi-specification.yaml), inline `POST /refunds` RefundRequest принимает `metadata`; объект Refund возвращает её. Старый reader без operationId сохраняет прежний known-ID contract; новый журнал всегда требует operation metadata.

Вторая короткая транзакция снова берёт intent→order, сравнивает fingerprint всех исходных immutable полей/bytes/hash/window/capture, проверяет актуальную ссылку и историю. Whitelisted GET observation повторно проверяется относительно свежего source/capture; metadata не создаётся искусственно для повторной проверки. Затем связь и первое наблюдение сохраняются атомарно. Сбой до COMMIT откатывает оба INSERT; успешный COMMIT с потерянным ACK восстанавливается чтением того же ID. Автоматических SQL retries нет.

`read(operationId)` возвращает сохранённый проверенный итог без GET. Отсутствие записи возвращает null и ничего не говорит о результате неизвестного POST. Отдельная ссылка без наблюдения считается противоречивой историей: store никогда не фиксирует такое состояние самостоятельно. Восстановление известного ID после неизвестного POST-исхода до GET proof остаётся задачей будущего dispatch journal.

## Порядок исходов и ограничения

Начальный ответ может сразу быть terminal. Запоздалый `pending` сохраняет прежний terminal, дату первого наблюдения и число записей. Повтор того же исхода также не меняет историю. Противоположный terminal, новый provider ID или другой момент создания возврата требуют reconciliation, а не перезаписи. Эквивалентные UTC timestamps с разным числом завершающих нулей обозначают один момент; store сохраняет первоначальную запись.

SQL invoker/VOLATILE trigger с пустым search_path и отозванным PUBLIC EXECUTE самостоятельно проверяет source/canonical request/anchor/capture и берёт те же intent→order locks. История перечитывается отдельными запросами после lock wait. Для дат проверяется календарь, capture≤created и created≤now+5мин. PostgreSQL округляет timestamptz до микросекунд, поэтому дата провайдера хранится как text, а хронология/тождество сравниваются дополненными до9 цифр UTC ключами с C collation. Нельзя потерять изменение на1ns из-за преобразования к timestamptz. Время наблюдения задаёт БД, не worker.

Worker получает только точечные права в disposable fixture: SELECT приватного источника и журналов, UPDATE(id) для row locks, INSERT перечисленных колонок новых таблиц. Он не читает account email/password и не меняет оплату, capture, публикацию или часы журнала. Исходный payment request может содержать receipt/customer данные и остаётся приватным; в новые таблицы, возвращаемый результат и журналы тестов они не копируются. SQL guard проверяет целостность, а не заменяет доверие к сконфигурированному financial worker и авторитетным GET.

Down разрешён только для пустых новых таблиц с блокировкой обеих таблиц; непустая история не удаляется. Ни canceled, ни отсутствие свежего ответа не освобождает reservation и не запускает размещение заново.

## Оставшаяся работа F02

Это журнал GET-подтверждённой привязки/исходов, не финансовое разрешение или полный dispatch journal. Ещё нужны допуск инициатора/основания и фискального сценария, actual POST с исходными bytes/key и ограниченным окном, сохранение неизвестного результата отправки/provider ID, очередь/повторы/reconciliation и однократное применение подтверждённого изменения услуги. Provider inspection не гарантирует отсутствие внешней операции после последнего GET. Компенсации непросмотренных откликов и schema/ACL активация остаются отдельными этапами. LIVE и реальные операции выключены.
