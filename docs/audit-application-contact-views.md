# F02: локальная история раскрытия контактов

01.11.2026. Устранена потеря положительного факта раскрытия контактов после отклонения отклика. Это первый технический шаг для специальных возвратов за непросмотренные отклики; финансовые операции, таймер и автоматический расчёт права на компенсацию ещё не включены.

## Что фиксируется

Новая0035 создаёт `app.application_contact_views`: UUID отклика, UUID получателя, тип свидетельства и серверная дата записи. Телефон, email, сообщение, snapshot, IP, токен и hash сессии не копируются. Ключ `(application_id,evidence)` сохраняет только первую запись каждого типа; UPDATE/DELETE запрещены. Связи RESTRICT и отказ down на непустом журнале предотвращают тихое стирание истории. Исполнение удаления аккаунта F04 должно отдельно учитывать согласованные сроки хранения; период хранения этим инкрементом не придуман.

`recipient_read` означает **серверную подготовку раскрытия** авторизованному получателю, не доказательство того, что человек увидел экран. COMMIT может пройти, а сеть оборваться до получения ответа. При неизвестном COMMIT контакты не возвращаются, запись при этом может сохраниться; повтор не меняет первую дату. Это ограничение нужно учитывать в будущем финансовом процессе и спорных случаях.

У ранее доставленных записей при подключении добавляется отдельный `legacy_unknown`. Его время — момент регистрации неопределённой истории, **не историческая дата просмотра**. Он сохраняется и после нового подтверждённого раскрытия; отсутствующие старые данные не реконструируются по нынешнему статусу. Ни этот marker, ни отсутствие записи не являются сами по себе основанием для автоматического возврата или отказа в нём.

## Порядок ответа и права

В `PostgresApplicationStore` новая локальная policy направляет recipient `read` и все успешные ветки `decide` через одну запись в существующей авторизованной транзакции. Сначала user/session authority, затем блокировки work/application, затем INSERT свидетельства и проверка активности сессии, COMMIT, и только после этого snapshot может попасть в HTTP-ответ. Ошибка записи или неопределённый COMMIT дают приватную503 без контактов. Read не меняет revision/status и не ломает существующее последующее подтверждение viewed клиентом.

Idempotent decide-ветки тоже возвращают контакты и поэтому записываются; прямое отклонение своего выбранного отклика не обходит журнал. Самопросмотр исполнителя и список кратких карточек ничего не раскрывают заказчику. Create/update/intent/preview принадлежат исполнителю и не создают recipient-событий. SQL-trigger сохраняет явный переход viewed/selected от прежних разрешённых клиентов; автоматическое отклонение **других** ответов не означает просмотра и не записывается.

Runtime получает только INSERT(application_id,recipient_id), без SELECT, UPDATE, DELETE, metadata и grant option. Дата и evidence имеют server defaults. Привязка проверяется trigger по доставленному оплаченному отклику и реальному автору заказа/вакансии; нельзя подставить исполнителя или постороннего пользователя. Используется `ON CONFLICT DO NOTHING` без conflict target и RETURNING: иначе PostgreSQL потребовал бы SELECT, которого у веб-роли нет. Финансовые таблицы и их права не меняются.

SQL-свидетельство не заменяет HTTP-аутентификацию. Runtime — доверенный серверный SQL principal, имеющий прежнее чтение applications/work; скомпрометированный DB principal мог бы подделывать положительные действия. Здесь защищены пути API и минимальные полномочия, а не заявлена защита от захватившего БД администратора.

## Локальное включение и граница старой версии

Режим выключен по умолчанию. `BLIZHNIY_APPLICATION_CONTACT_VIEWS` принимает только enabled/disabled/отсутствие; опечатка не отключает доказательства молча. Для enabled constructor также требует trusted local primary и точный origin `https://127.0.0.1:3045`, а также localActions. Эти настройки не берутся из запроса. Существующий production режим не включается.

0035 берёт SHARE ROW EXCLUSIVE на applications **до** регистрации legacy-состояния: delivery/decision writer завершится до границы или продолжит после установки trigger. Work-row locks в DDL не берутся, чтобы не инвертировать порядок живого writer. До применения нужно остановить старый local web: он ещё может возвращать read без новой записи. Новая сборка запускается только после успешного DDL и сверки схемы35.

`apply-local-application-contact-views.mjs --plan` — read-only. `--apply-local` требует свободных3045/3046, проверяет закрытый owned state, точный контейнер/loopback/PG18/owner/runtime, все34 прежних hash, затем атомарно устанавливает35 и точечный INSERT grant. Проверяются отсутствие лишних прав, свойства trigger/function, прежние финансовые ACL. При неизвестном COMMIT автоматического повтора нет; отдельный readback проверяет журнал. Повтор с уже точным35 не переустанавливает DDL и не стирает evidence.

Отсутствие записей пока **не используется** как финансовое доказательство: старые потребители и будущая смена версий требуют отдельного policy/coverage anchor. Перед автокомпенсациями нужно связать новый policy с подтверждённой доставкой и проверенными версиями всех потребителей, сериализовать резервирование возврата с раскрытием и выбором исполнителя.
