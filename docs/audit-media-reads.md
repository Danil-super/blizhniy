# F13 — ограниченная очередь загрузки фотографий

Основа `30dcce5`. Исправление подготовлено локально; production, схема БД, runtime-привилегии и upload admission не менялись.

## Причина и поведение

При четырёх незавершённых чтениях пятый допустимый photo GET сразу получал503/MEDIA_BUSY. Браузер сохранял сломанную картинку, поскольку автоматического повтора не было. Новый regression настоящего handler воспроизвёл `503 !== 200` до исправления.

Все шесть существующих public/private/admin read paths используют одну очередь и прежний общий счётчик. Ограничения на процесс: четыре активных чтения, 64 ожидающих всего, 24 ожидающих на доверенный ingress IP, ожидание не более1500ms. FIFO внутри IP, round-robin между IP. Состояние общее между Next bundles через глобальный WeakMap, как нынешний счётчик. Между разными процессами/VPS очередь не распределяется. Идентификаторы IP удерживаются только на время ожидания; они не записываются в аудит или постоянный кеш.

Ожидающий запрос не читает ресурс и файл. Abort/timeout удаляют его из очереди, освобождение слота идемпотентное. Проверка монотонного deadline при выдаче слота предотвращает запуск просроченной работы, если event loop задержал таймер. Активное чтение сохраняет слот до фактического завершения, даже после abort. Переполнение/timeout остаются503/MEDIA_BUSY с Retry-After1; очередь не обещает бесконечную доступность под любой нагрузкой.

Private/admin сохраняют origin/CSRF, cookie, actor и rate-limit boundaries; действующую сессию/роль проверяет репозиторий после ожидания. Public SQL авторизует точную текущую связь после admission, затем повторно проверяет её после файлового чтения. Оплата, срок, состояние автора, публикации, блокировки, фотографии и ревизия не обходятся. WebP≤2MiB, закрытый каталог и no-store сохранены. Загрузка изображений, финансовые и остальные пишущие операции не получают автоматических повторов.

У `StoredMediaImage` появились максимум два повторных GET с задержками1–1,25s и2–2,25s. Повторяется только относительный URL существующих публичных photo endpoints, без query, смены URL или прав. Native img не сообщает HTTP-статус: повтор может затронуть404, но он ограничен двумя попытками и каждый раз заново проходит серверную авторизацию. External, blob/data, static и private POST не повторяются. Смена источника и unmount уничтожают controller/таймер; успешная загрузка отменяет ожидающий повтор. Дополнительная проверка DOM после hydration охватывает SSR-картинку, получившую ошибку до присоединения React listener.

## Проверка настоящими файлами и SQL

[Метрики](performance/photo-burst-20261031.json): собственная disposable PostgreSQL18.6, 1 CPU/512MiB; отдельная SELECT-роль, настоящие приватные WebP и loopback HTTP. Размеры файлов: 129194, 804718, 1808800 байта. Два синтетических доверенных ingress IP, три серии по48 запросов; управляемая задержка25ms удерживает физическое чтение, чтобы воспроизвести конкуренцию. Один прогрев перед каждым алгоритмом; старая версия handler загружается из точной основы Git.

| Проверка | До | После |
|---|---:|---:|
| Успешных ответов в каждой серии48 | 4 | 48 |
| MEDIA_BUSY в каждой серии | 44 | 0 |
| Максимум одновременно читаемых файлов | 4 | 4 |
| p95 времени успешного профиля после исправления | — | 504–519ms |

Быстро возвращённый503 не считается быстрым успешным фото, поэтому его latency не сравнивается как улучшение. RSS измерен для совмещённого процесса HTTP-сервера и тестового клиента: пик примерно211MiB до /235MiB после, при12 против144 успешных скачиваний. Это не измерение памяти отдельного production-сервера и не доказательство отсутствия утечки. Ограничение четырёх физических чтений не ограничивает все сетевые буферы downstream-сервера. Slow-client/soak,100active/30min и мобильные CWV остаются отдельной нагрузочной работой.

Настоящий SQL дополнительно подтвердил отзыв: публикация архивируется, пока пятый запрос ожидает за четырьмя чтениями; после освобождения он получает404 без доступа к файлу. Архивация во время чтения тоже возвращает404 без WebP. Одноразовый контейнер и временные файлы удаляются после проверки с проверкой их принадлежности.

Первый эксперимент использовал общий локальный стенд; cleanup обнаружил неизменяемость ready media (открытый F08). Только этот синтетический набор из24 карточек архивирован, автор заблокирован, категория выключена. Три синтетических файла (2742474 байта) и их учёт сохранены; manifest вне Git: `~/.local/state/blizhniy/local-primary-private/photo-burst-retained-20261031.json`. Защита удаления и storage budget не обходились. Последующие эксперименты перенесены в полностью одноразовый контейнер, чтобы не накапливать данные общего стенда.

Уменьшенные варианты изображений и другая cache policy не добавлены: они требуют отдельной модели хранения/очистки/отзыва. Этот инкремент подтверждает очередь и конечные повторы в указанном локальном профиле, не закрывает F08 или общую программу производительности.
