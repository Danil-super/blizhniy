## Контракт

Основание выводится существующей политикой0043/0045:120 прошедших часов без просмотра, выбор другого исполнителя до просмотра либо снятие/удаление заказа заказчиком до просмотра. Неизменяемый case сохраняет уже возникшее право при позднем просмотре. Сумма всегда полная и исходная, только TEST. Новый wallet, частичные компенсации и внутренний чат не добавляются.

Private processor принимает только ID исходной оплаты. Этот же UUID становится единственным operation ID. БД связывает case с исходным откликом, магазином, суммой, версией политики и фискальным режимом проверенного исходного запроса. Browser-суммы, доказательства и произвольный ключ не принимаются. Перед каждым возможным POST повторно проверяются case, исходный capture/merchant и состояние заказа; прежняя browser-сессия для исполнения сохранённого права не нужна.

Используется существующий dispatcher: оригинальные bytes/key `refund-<payment UUID>`, исходное окно23h55m, не более12 попыток, неизменяемый provider candidate, GET-сверка метаданных и исходного платежа. UNKNOWN не превращается в новый ключ; после истечения окна без известного candidate нужен операторский recovery. Известный candidate читается только GET, включая повтор после успешного возврата и истёкшего окна. Основные поля и идемпотентность сверены с [официальным API ЮKassa](https://yookassa.ru/developers/api?lang=ru) через Context7; реальная фискальная приёмка магазина остаётся отдельным этапом.

Только GET-подтверждённый `succeeded` допускает новую неизменяемую запись `application_compensation_refunds`. BEFORE-trigger проверяет источник, точные request bytes/key/hash, исходное окно/capture и непротиворечивую успешную историю. AFTER INSERT переводит только исходный payment order в `refunded` и создаёт одно уведомление специалисту. Повтор/ON CONFLICT не повторяет переход и не восстанавливает удалённое уведомление. При `pending` или `canceled` финансового эффекта и уведомления нет.

Уже доставленные отклик, snapshot, `is_paid`, даты доставки и журнал раскрытия контактов сохраняются. Компенсация не стирает историю общения и не отзывает уже раскрытые контакты.

## Совместимость и права

0048 сохраняет прежние проверки четырёх guards0036–0039 и добавляет отдельную application-ветку. Новые EXECUTE/SELECT права прежним placement-ролям не нужны. Доступ к helper вызывается отдельным PL/pgSQL IF: CASE оказался недостаточным при выполнении с ограниченной ролью и был отвергнут реальным тестом. Placement reservation/admin approval и обычный read-only inspection по-прежнему отказывают типу application; отдельный inspection вызывается dispatcher только после проверки источника БД.

Новая роль существует только в одноразовом тестовом контейнере. У неё ограниченные INSERT, чтение финансовых источников и UPDATE(id) для блокировки строк. Нет права непосредственно менять оплату, контакты, snapshot, историю или outcome. Миграция не выдаёт grants и не меняет runtime/web/production роли. Helper не берёт новых user/work/application locks после intent/order, сохраняя порядок блокировок общей финансовой цепочки.

Новый helper оставлен в существующем request-store: это предотвращает обратную зависимость общего механизма от большого компенсационного модуля. Явные поля конструктора вместо parameter properties сохраняют импорт в действующем Node22 strip-only runner.
