# Задачи перехода на PostgreSQL

Статусы фиксируют только проверенный результат. Общие условия — [plan.md](plan.md); архитектурное решение — [ADR-001](../docs/decisions/0001-two-server-postgresql.md).

## 0. План и инвентаризация — выполнено

- [x] Зафиксировать принятые два сервера, отказ от Supabase и чистый старт.
- [x] Проверить ресурсы VPS и TLS/пустоту/версию БД только чтением.
- [x] Записать зависимости, критерии, риски и условия переключения.

Проверка: SSH read-only 09.10; SQL read-only 09.10; структура старого кода и CI прочитаны. Действующие окружения не менялись.

## 1. Безопасное подключение PostgreSQL — в работе

Зависит от 0. Файлы: `src/lib/postgres.ts`, `tests/postgres.test.mjs`, `package.json`, `package-lock.json` (связанные инструкции/шаблон окружения обновляются отдельно).

- [ ] Только явная серверная конфигурация; удалённый TLS с проверкой CA/имени, отсутствие PG*/Supabase fallback; безопасное локальное исключение только для разработки.
- [ ] Параметризованный query и транзакция на одном соединении, rollback/release, без автоматического повторения записей; ограниченный пул и таймауты.
- [ ] Unit/отрицательные тесты и реальная локальная SQL-интеграция, lint, типы, production build проходят; код не подключён к рабочим маршрутам.

Проверка: focused `tests/postgres.test.mjs`, opt-in PostgreSQL integration, полный native suite, lint/tsc/build. Схема удалённой БД не изменяется.

## 2. Аккаунты и серверные сессии

Зависит от 1. Файлы: новая identity SQL, серверные password/session модули и их тесты (до 5 файлов на инкремент).

- [ ] Хеширование пароля и случайные токены; в БД только хеши токенов с TTL.
- [ ] Сессия отзывается; заблокированный пользователь не получает обычный API-доступ, запрос удаления остаётся возможным.
- [ ] Проверены таймауты, истечение, повторное использование и конкурентные обращения.

Проверка: unit + isolated SQL на PostgreSQL 18.6; типы/lint/build. Не применяем старую синтетическую `auth.users` как production-Auth.

## 3. Регистрация и подтверждение email

Зависит от 2. Файлы: регистрационный handler, email-confirm handler, форма и focused тесты.

- [ ] Регистрация создаёт только обычного пользователя и две отметки документов; email уникален, контакты скрыты.
- [ ] Подтверждение одноразовое и ограничено сроком; локальные письма не уходят внешним получателям.
- [ ] Форма не вызывает Supabase SDK в новом контуре.

Проверка: API/SQL + реальный браузер signup → письмо → подтверждение; отрицательные тесты CSRF/роли/повтора.

## 4. Вход, выход и восстановление

Зависит от 3. Файлы: auth handlers, общий серверный guard, клиентский auth adapter и тесты (разбить по действиям).

- [ ] HttpOnly cookies, origin/CSRF и общий лимит попыток; токены не читаются из localStorage.
- [ ] Выход и смена аккаунта очищают прежний кабинет; сброс пароля отзывается/одноразовый.
- [ ] Проверены два аккаунта, блокировка и администрация без клиентского повышения роли.

Проверка: unit/API/browser login → logout → другой аккаунт, recovery и попытки подмены.

## Контрольная точка A

- [ ] Идентификация полностью работает без Supabase, отрицательные тесты зелёные, браузер обращается только к локальному backend.

## 5. Каталог и тарифы

Зависит от 1 (публичное чтение), от 4 для администрирования. Файлы: reference SQL/seed, category/tariff repositories и тесты (отдельно каждый репозиторий).

- [ ] Воспроизводимый чистый seed: 105 категорий и 7 тарифов; никаких demo-аккаунтов/публикаций/платежей.
- [ ] Публичное чтение возвращает прежний контракт, фильтры параметризованы.
- [ ] Редактирование только администратором, повторный запуск не перезаписывает ручные тарифы.

Проверка: isolated SQL, API и страницы каталога; повторная инициализация не теряет изменения.

## 6. Фотографии на VPS

Зависит от 4. Файлы: media repository, upload handler, file-serving boundary и focused тесты.

- [ ] Постоянный каталог вне релизов; владелец/байты/MIME/размер/квота проверяются, приватная выдача защищена.
- [ ] Метаданные только в БД; чужой файл нельзя привязать/перечислить/удалить.
- [ ] Сбой между записью файла и БД не оставляет неограниченные сироты, очистка проверяет принадлежность.

Проверка: API/SQL/browser upload; traversal, symlink, чужой UUID, неверные байты, заполнение квоты, restart/release.

## 7. Объявления и кабинет

Зависит от 5, 6. Файлы: listing repository, draft/cabinet handlers и тесты; публичное чтение отдельным инкрементом.

- [ ] Владелец создаёт/изменяет черновик, видит его после перезапуска; второй аккаунт не видит.
- [ ] Публичные ответы скрывают контакты/точный адрес; разрешённый доступ выдаёт только необходимые поля.
- [ ] Нельзя установить paid/published/expiry клиентским payload или привязать чужое фото.

Проверка: API/SQL/browser draft → кабинет → второй аккаунт, прямые попытки обхода.

## 8. Остальные публикации

Зависит от 7. Отдельные инкременты до 5 файлов: вакансии → заказы → специалисты → ярмарка.

- [ ] Для каждого типа сохранены формы, статусы, владение и приватность контактов.
- [ ] Клиент не выставляет оплаченный статус/срок; администратор проверяется на сервере.
- [ ] Каждый тип проходит isolated SQL/API и браузерную проверку.

Проверка: предметные focused tests + общий suite; не заменять проверки заглушками.

## 9. Отклики, бронирования, уведомления, удаление

Зависит от 8. По одному предметному сценарию на инкремент.

- [ ] Контакты доступны только владельцу и разрешённым участникам отклика/бронирования.
- [ ] Конкурентное бронирование соблюдает остатки/сроки; уведомление не раскрывает чужие данные.
- [ ] Запрос удаления/экспорт охватывает аккаунт, связанные данные и фото, с явными сроками резервов.

Проверка: isolated SQL/concurrency/API/browser; воспроизвести старые негативные сценарии.

## Контрольная точка B

- [ ] Каталог → регистрация → фото → черновик → отклик/бронирование работают без Supabase, права и приватность проверены.

## 10. Платежи и публикация

Зависит от 8, 9. Инкременты: checkout snapshot → проверенное подтверждение → atomic fulfillment → срок/восстановление.

- [ ] Сохранены цена/срок/idempotency и все инварианты прежних 76 SQL-тестов; никаких trusted client success.
- [ ] Повтор webhook/сбой/конкуренция не исполняют платёж повторно; sandbox не создаёт production entitlement.
- [ ] Оплаченная публикация и восстановление действуют строго в оплаченный срок.

Проверка: обновлённые PostgreSQL lifecycle tests + API/provider sandbox + UI; реальные деньги не используются.

## 11. Российский контур и восстановление

Зависит от A, B, 10. Раздельные операционные инкременты: учётные записи/сеть → файлы → SMTP/CAPTCHA → backup/restore.

- [ ] Пароль из чата заменён, runtime и migration credentials разделены; TLS + allowlist/private network; CPU/RAM/диск/лимиты БД подтверждены.
- [ ] SMTP, CAPTCHA, карты, мониторинг/логи и копии проверены на размещение и передачу ПД; секреты вне Git/артефактов.
- [ ] Восстановлены и БД, и фотографии на изолированной цели в РФ; измерены время восстановления и ресурсный запас VPS.

Проверка: network/browser trace, права БД, измерения и самостоятельный restore; дополнительные платные услуги отдельно согласуются.

## 12. Переключение и удаление зависимости Supabase

Зависит от 11. Файлы: режим приложения/готовность, deployment config, env template/README и dependency removal отдельными инкрементами.

- [ ] Полные тесты, lint, типы, build, аудит и российский staging проходят; нет обращений к Supabase Auth/REST/Storage.
- [ ] Запись/платежи остановлены на время cutover; новый build и секреты согласованы, rollback не возвращает зарубежный backend.
- [ ] После проверки удалены SDK/старые runtime-модули, preview/старые ключи закрыты; исторические SQL/доказательства не уничтожены.

Проверка: production smoke двух пользователей, media, sandbox payment, TTL/TLS; старую БД удалять только по отдельному решению.
