# F03: локальная защита версии во время оплаты

01.11.2026. Исправлена возможность изменить покупаемое объявление, вакансию или заказ после подготовки checkout. Миграция0034 подключается только к синтетическому локальному стенду. Production rollout, LIVE, финансовые права веб-сервера и существующие ограничения account TEST не меняются.

## Поведение

После подготовки оплаты текст, поля, ревизия и фотографии защищены, пока заказ имеет `created`/`pending` либо `succeeded` без записи исполнения. HTTP возвращает409 `CHECKOUT_ACTIVE` с понятным сообщением; форма сохраняет исходные правки в памяти вкладки, а основная форма объявления показывает ссылку к начатой оплате в кабинете. Чтение и проверка статуса доступны, mutation не повторяется автоматически.

`failed`/`refunded` и `succeeded` с историческим fulfillment не мешают редактированию. Действующие проверки валидности и прав остаются обязательными; разрешение редактирования не даёт права заново публиковать возвращённую или заблокированную запись. Правка после размещения сохраняет оплаченный период, финансовую историю и единственный receipt.

Неизвестный dispatch и старое несовпадение ревизии остаются защищёнными без освобождения по времени. Старые уже оплаченные несовпадения не исправляются задним числом: для них ещё требуется операторский процесс с авторитетной сверкой/возвратом, F02 и оставшаяся часть F03. Подготовленную оплату можно продолжить; отдельная безопасная отмена до dispatch ещё не реализована. Это ограничение не выдаётся за завершённый recovery.

## Граница реализации

`0034-checkout-edit-fence.sql` добавляет два trigger-function и четыре trigger, таблиц и grants не добавляет. Защита родительских строк сравнивает весь JSON строки, исключая только bookkeeping/финансовые поля. Обычный title объявления защищён; вычисляемый title work исключён отдельно, его исходный form сравнивается целиком. Поэтому изменение текста без увеличения revision тоже отклоняется. `deleted_at` рабочих записей считается изменением содержания/доступности.

Фото защищены до INSERT/UPDATE/DELETE связи. Проверяются оба родителя при переносе связи, блокировки берутся по отсортированным ID. Обычные stores уже держат родителя перед изменением фото; частичное удаление фото не может закоммититься при отказе последующей ревизии. Новые trigger не берут intent/order locks и не меняют покупку или её ключ.

Операции prepare/edit используют существующий порядок user → session → target, финансовый worker — user → intent → order → target. При READ COMMITTED запрос из volatile trigger после ожидания видит уже сохранённый checkout. [Правила снимков PostgreSQL](https://www.postgresql.org/docs/18/transaction-iso.html) не дают такого свойства REPEATABLE READ, если заблокированная строка сама не менялась. Поэтому изменения содержания/фото в другом isolation level отклоняются через `PBL02`; наружу выходит общая503, а не ложная ошибка активности платежа. Конфигурация транзакции автоматически не переписывается.

Runtime не получает SELECT финансовых таблиц. Функции SECURITY DEFINER выполняют только фиксированные квалифицированные проверки и row locks; `search_path=''`, public EXECUTE отозван, владельцем остаётся bootstrap owner. Параметров, динамического SQL, финансовых UPDATE и выдачи данных нет. Доступ к UPDATE самой публикации и привязке фото по-прежнему нужен у вызывающего. Напрямую вызывать/заменять/переназначать функцию или отключать trigger runtime не может. При успешном fulfillment исходной версии разрешён переход draft/not-paid → published/paid; финансовую власть по-прежнему определяют прежние ACL, проверки и trigger.

Вычисляемый work title доступен после BEFORE trigger, поэтому его нельзя сравнивать как обычное введённое поле; это проверено настоящим fulfillment обоих рабочих типов. [Документация PostgreSQL о stored generated columns](https://www.postgresql.org/docs/18/ddl-generated-columns.html).

## Локальное подключение

`apply-local-checkout-edit-fence.mjs` принимает только `--plan`/`--apply-local`, читает прежний закрытый state и проверяет точный owned Docker container, loopback и синтетическую БД. Сверяет все33 прежних migration hash, режим runtime, PG18 и локального owner. DDL и журнал0034 коммитятся вместе под migration lock; новых grants нет. После COMMIT retry не выполняется: отдельный readback журнала позволяет проверить неизвестный результат. Повторный запуск с уже точным34 только проверяет существующую схему. Auto-bootstrap при старте приложения не применяется к уже существующему стенду.

После проверки0034 входит в строгий local manifest; отсутствие/несовпадение migration hash не игнорируется. Production plan, роль worker и release guard не адаптированы к34; публикация потребует отдельной проверенной интеграции. Down-файл — только операторский откат при остановленном приёме checkout, не автоматическое действие.
