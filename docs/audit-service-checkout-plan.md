# Оплата ярмарки и бегущей строки — локальный этап

После отдельного одобрения владельца13.11 точный пакет0057 установлен и
принят только локально: [установка/сквозная приёмка/перезапуск](audit-service-checkout-local-activation.md).
Без push/production/реальных денег. Ниже сохранены контракт и подготовительные доказательства.

## Контракт

- Бесплатная анкета специалиста остаётся бесплатной; новый checkout принимает
  только fair_application/ad_marquee. Действующая модерация этих двух услуг
  сохраняется: оплачивается только утверждённая текущая версия.
- Ярмарка: покупка привязана к конкретной дате последнего воскресенья месяца
  по Москве. Окончание — полночь после этого дня. Условия сохраняются вместе
  с immutable intent; прочитанная вчера покупка не превращается в следующую
  ярмарку при смене месяца. После окончания события новая отправка запрещена;
  поздний capture сохраняется, но не публикует карточку на другое событие.
- Бегущая строка: одновременно максимум5 действующих оплаченных публикаций.
  Остальные оплаченные заявки ожидают по времени capture и ID; срок начинается
  при фактическом выделении места. Повтор/перезапуск не сдвигает начало.
- Сессия, подтверждённые email/телефон, владелец, версия, форма, справочники,
  готовые фото, одобрение и активный тариф проверяются перед подготовкой и
  первой отправкой. Известный provider ID остаётся доступен для GET-recovery
  после изменения текущего тарифа. Старый receipt не пересобирается.
- Изменение формы/фото не меняет уже оплаченные условия; при активной/неясной
  оплате запрещено редактирование, удаление и смена владельца цели. Новый ключ
  не освобождает существующий created/pending/succeeded заказ.
- Полный возврат по решению администратора поддерживается до подключения
  оплаты: неопубликованная/ожидающая услуга не запускается после возврата,
  опубликованная снимается. Один refund/effect/notice; прежние три типа
  размещений, продления и компенсации откликов сохраняют свои правила.
- В интерфейсе явно показываются дата ярмарки либо ожидание рекламного места;
  paid queue не выдаётся за опубликованную услугу. Неизвестный исход оплаты
  допускает только readback/recovery прежнего ID, а не повтор покупки.

## Реализация и порядок блокировок

Используются существующие payment_orders/checkout_intents/verifications,
провайдер и журнал возвратов. Дополнительные серверные условия услуги
сохраняются отдельной неизменяемой строкой по intent_id в той же транзакции.
Даты события не принимаются как полномочие клиента. PostgreSQL вычисляет
каноническое событие по своим часам; UI подтверждает показанную точную дату.

Для рекламы обработчик принимает одну покупку за транзакцию: user → intent →
order → service → общий transaction advisory lock ёмкости. Под этим lock
перечитывается количество действующих окон; чужие user/intent/target строки
после него не блокируются и не изменяются. Истёкшие окна исключаются по
clock_timestamp без массового UPDATE чужих публикаций. Discovery выбирает
оплаченные ожидания ограниченной порцией и передаёт каждый ID в тот же
однопокупочный обработчик; внешние HTTP не выполняются под SQL-блокировками.
Перед выделением места каждый путь, включая свежий capture, под тем же lock
проверяет отсутствие более раннего пригодного ожидания. Discovery фильтрует
пригодность до LIMIT, чтобы недоступные заявки не заслоняли живую очередь.
FIFO применяется к пригодным ожиданиям; заблокированный/неподтверждённый
аккаунт, отозванное одобрение либо неготовые фото не получают место.

## Проверки единого пакета

Изолированная PostgreSQL: atomic prepare/COMMIT recovery, replay/mismatched
key, сессия/владелец/телефон/одобрение, поля/фото и тариф при оплате, смена
месяца/конец дня/late capture, шестая и параллельные рекламные покупки,
освобождение места без потери оплаченного срока, возврат queued/live/missing,
lease expiry, повтор/restart и прежние три типа/отклики. Отдельно ограниченные
runtime/operator/worker роли и точные schema/ACL guards.

Chromium: утверждённая форма → показанные условия → сохранённый ID → оплата →
карточка/очередь → возврат/уведомление; lost ACK/reload, блокировка чужого ID,
mobile/desktop и отсутствие serious/critical axe. Затем общая регрессия,
сборка, scan секретов и единый конкретный пакет обязательного review.

Это план, не заявление о готовности checkout или разрешение ставить0057.

## Доказательства кандидата13.11

Кандидат0057 существует только в исходниках и disposable PostgreSQL. Пройдены
15 проверок основного service-набора, включая реальный ограниченный LOGIN, cookie HTTP, synthetic
dispatch/capture, запуск очереди после освобождения места, approved full refunds
для fair/live marquee/queued marquee, canceled refund, atomic lost-ACK recovery
и отмену подготовки до anchor. Новый runtime получает только чтение трёх
полей условий, INSERT(intent_id) и EXECUTE календаря; не получает прав менять
оплату/публикацию или записывать receipts/refunds. План GRANT пока не установлен.

Независимое инженерное ревью исправило два дефекта: freeze оплаченного
содержимого после fulfillment и освобождение очереди после авторитетного
canceled refund. Третий проход финансовых границ замечаний не выявил; отдельная
дополнительная модель владельцем пропущена. UI, схема/ACL и общая регрессия проверены отдельно; постоянный стенд пока56,
услуги выключены. Подготовлен единый [пакет review/установки57](review/local-service-checkout57.md):
856 общих SQL-проверок,22 candidate SQL/guard,2669 native, сборка/Chromium/Gitleaks.
Только после отдельного разрешения — применение точного guard и установка57
с перечисленными минимальными веб-правами, затем приёмка постоянного стенда.
