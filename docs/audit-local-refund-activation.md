# Подключение ручного контура возвратов — 12.11.2026

Подготовлен явный `scripts/local-primary.mjs --start --refunds` и такой же
opt-in для `--background`. Обычный запуск не загружает финансовый runtime,
не читает новую конфигурацию и не включает refund UI. Existing financial
guards, role plans, migrations и fingerprints не изменены.

Режим читает защищённые state/refunds.json, связанные с точными project и
containerId. Два64hex пароля отдельны друг от друга и от прежних credentials;
файл0600 в реальном owned0700 каталоге, без symlink/hardlink, чтение не более
2049 байтов с отказом при переполнении. URL/пути модулей/merchant keys в этой
конфигурации не принимаются. CA имеет фиксированное имя refund-db-ca.pem.

Оба пакета собираются из текущих проверенных исходников в новом закрытом
каталоге при каждом запуске. Старые artifacts не усыновляются. Actual Pool
CA сравнивается с сертификатом физически проверенного контейнера; перед DDL
симулятора дополнительно читаются точные55 journal/schema в READ ONLY.
Оператор и worker используют свои прежние ограниченные роли. Provider
фиксирован и синтетический; сетевого fallback нет. Next получает только
существующий UI-флаг, без двух финансовых паролей.

Общий lifecycle устанавливает отмену до первого финансового await, сразу
наблюдает done, проверяет остановку после async startup, закрывает поздние
handles и пытается закрыть каждый ресурс даже при предыдущей ошибке.
Proxy теперь убирает частичные DB/timer ресурсы при ошибках создания, ждёт
текущую перехватываемую почту и закрывает оба pool. Child Next получает
SIGTERM и при необходимости SIGKILL через5s. Конфигурация, роли или неверный
TLS не приводят к запуску сайта с наполовину активированными возвратами.
Same-UID код и Docker admin остаются доверенной границей.

Прежнее [согласование](review/local-refund-provider-launcher55.md) разрешало
только локальное сохранение и прямо исключало установку. Поэтому применение
плана на постоянной ручной БД требует отдельного решения владельца:

1. Повторная проверка owned state/container/live port/journal и частная
   резервная копия БД до первого DDL; никаких production данных/серверов.
2. Только16 добавочных миграций, две точные роли с LOGIN и отдельными
   сгенерированными паролями, прежние web-права сохраняются.
3. Только локальный DB TLS и закрытые CA/config файлы, без выдачи прав
   финансовых ролей веб-процессу и без передачи секретов в чат/Git.
4. Явный запуск synthetic режима, browser-проверка HTTP approval/recovery,
   рестарт, остановка и отсутствие дублей. Неизвестный исход не повторяется
   автоматически; резервная копия не восстанавливается вслепую.

На момент сохранения490413a постоянная схема/роли/TLS ещё не менялись.
Следующее согласование владельца разрешило установку именно этого плана
только на постоянном локальном стенде. Исходный review-only JSON сохранён
как артефакт согласования; актуальный результат приведён ниже.
