# PostgreSQL: серверный контур перехода

Новый серверный модуль `src/lib/postgres.ts` не зависит от Supabase. К нему подключены только явно включаемые локальные account API и API администрирования справочников; действующие маршруты сайта используют прежний backend. Он предоставляет параметризованный `query`, транзакцию на одном соединении и `close`. Создавайте один экземпляр на процесс, не на HTTP-запрос. Транзакционные запросы нужно `await` внутри callback; внешние платёжные вызовы не держат транзакцию открытой.

## Конфигурация и диагностика

Node.js 22. Передайте серверу все `BLIZHNIY_DB_*` из `.env.example` через защищённое окружение. Диагностика `npm run db:check` намеренно не загружает `.env` автоматически: она начинает READ ONLY транзакцию, выводит версию/TLS/число пользовательских таблиц и не меняет схему. Не передавайте пароль аргументом командной строки и не публикуйте окружение/конфиг в логах.

Для Timeweb используйте DNS-имя БД из панели и CA по официальной ссылке `https://st.timeweb.com/cloud-static/ca.crt`, скачанный по HTTPS вне репозитория. TLS проверяет CA **и имя сервера**; сертификат сайта и сертификат БД — разные вещи. Не заменяйте DNS-имя публичным IP, если сертификат не содержит этот IP. Пароль из чата заменить перед production.

Общие `PG*` переменные запрещены, чтобы драйвер не подхватил скрытые параметры окружения. `sslmode=require` и `rejectUnauthorized=false` не поддерживаются. Отключение TLS допускается только явно на `127.0.0.1`/`::1` с `NODE_ENV=development` или `test`; production всегда проверяет сертификат.

Пул: максимум 5 соединений, ожидание соединения 3 с, простой 10 с, срок соединения 5 минут. Серверные ограничения: запрос 8 с, блокировка 3 с, простой внутри транзакции 10 с. При потере ответа COMMIT результат **неизвестен**, повторять запись автоматически нельзя. Будущие платежи опираются на идемпотентный intent и сверку с провайдером.

## Явная установка чистой схемы

`scripts/bootstrap-postgres.mjs` — отдельная операторская команда, не часть запуска приложения или автодеплоя. Node.js 22, защищённое серверное окружение `BLIZHNIY_DB_*`, без автоматического чтения `.env`. Пароль не передаётся аргументом команды.

```bash
node --experimental-strip-types scripts/bootstrap-postgres.mjs --plan
node --experimental-strip-types scripts/bootstrap-postgres.mjs --apply 17e86f80f26733d39ef4b84d.twc1.net:default_db
node --experimental-strip-types --test tests/bootstrap-postgres-integration.mjs
```

`--plan` не подключается к БД. `--apply` требует точного подтверждения host/database, PostgreSQL 18 и проверенной конфигурации TLS. Первая установка отказывается работать поверх посторонних таблиц, представлений, последовательностей, функций или схем; объекты расширений не принимаются за пользовательские отношения/функции. Семь фиксированных миграций, журнал SHA-256 и reference seed выполняются в одной транзакции под advisory lock. Ошибка откатывает всю установку, неизвестный результат COMMIT не повторяется автоматически. Локальные 0006–0007 пока **не применены на Timeweb**; перед следующим удалённым `--apply` проверить отдельный план ниже, а не считать команду прежним пятишаговым bootstrap.

Повтор сверяет непрерывный журнал `blizhniy_meta.migrations` с исходниками; изменённая миграция или пропуск — ошибка, не попытка автоматического исправления. Seed добавляет недостающие справочники через `ON CONFLICT DO NOTHING`, сохраняя ID, ручные названия, цены, сроки и флаги активности. В payload только регион/города/категории/специализации/тарифы из проверенных reference exports: никаких demo-аккаунтов, объявлений, фотографий и платежей.

Миграция 0005 добавляет пять таблиц справочников, ограничения точной цены `numeric(12,2)`, FK-индексы и запрет доступа PUBLIC. Её down допустим только для пустых таблиц; заполненные справочники не удаляются автоматически. Для операторского rollback отдельно согласовать восстановление/состояние журнала; не запускать down против подключённого приложения.

10.10.2026 в Timeweb применены 0001–0005: 105 категорий (18 корневых), 26 городов, 14 специализаций и 7 тарифов, 0 аккаунтов; повторное чтение подтвердило журнал и TLS. С VPS проверен PostgreSQL TLS handshake с CA и проверкой DNS-имени (`Verify return code: 0`); приватная сеть этим не подтверждается. Это подготовка новой БД, **не переключение сайта**. `gen_user` использован только оператором для подготовки среды разработки; пароль до пользовательского production меняется. У него нет CREATEROLE. Отдельную ограниченную runtime-учётную запись нужно создать через [панель Timeweb](https://timeweb.cloud/docs/dbaas/postgresql/users-and-privileges), затем выдать права только нужным таблицам; owner/migration credentials не подключать к HTTP runtime.

## Чтение каталога

`PostgresCatalogRepository` получает существующий `PostgresQueries`, не создаёт пул и не читает окружение. Он работает только на сервере; HTTP-маршруты и страницы ещё используют старое хранилище до общего cutover публикаций. Файлы новой схемы и установленный журнал не изменяются.

- `getPublicCategories()` — прежний `Category[]`: slug, name, уникальные имена активных прямых детей; без ID/флагов/других столбцов.
- `getPublicCategoriesWithListingScope()` — активные корневые категории и отдельно scope из ID корня и всех прямых детей, включая скрытые. Общий чистый mapper `category-contract.ts` используется также прежним store, чтобы правила отображения не расходились.
- `getPublicCategoryWithListingScope(slug)` — тот же контракт для активного корня, один параметризованный SQL/snapshot. Неизвестный, скрытый корень или slug подкатегории возвращает `undefined`; неверный формат/длина slug — `CatalogInputError` до SQL.

Пустая БД даёт пустой список, ошибка чтения передаётся вызывающему коду; скрытого fallback к Supabase/seed/demo и retry нет. Полный список справочника читается одним запросом, без N+1; это существующий контракт меню, не список публикаций. Права достаточно ограничить `USAGE app` и `SELECT app.categories`, без доступа к identity и без записи. До включения runtime роль создаётся отдельно через панель.

Проверка: `node --experimental-strip-types --test tests/postgres-catalog.test.mjs`; SQL/ограниченные права проверяются внутри `tests/bootstrap-postgres-integration.mjs` на собственном локальном PostgreSQL 18.6. Его тестовые категории откатываются, роль удаляется; удалённая БД не используется.

## Чтение тарифов

`PostgresTariffRepository` получает тот же `PostgresQueries` без собственного пула/окружения. Методы `getStoredTariffs()` и `getPublicTariffs()` сохраняют контракт `Tariff[]`, включая поле `active` и неактивные строки, как прежний store. Lookup `getStoredTariffById(id)` возвращает сохранённую запись, `getActiveStoredTariffById(id)` — только активную. Неизвестный ID даёт `undefined`, неправильный формат/длина — `TariffInputError` до SQL; ID и active-only параметризованы.

ID берётся из БД, не восстанавливается по action/static seed. Цена `numeric(12,2)` явно читается как текст и проверяется перед преобразованием в прежний UI-тип `number`; срок `NULL` сохраняется. Это представление для совместимости, **не арифметика оплаты**: checkout/fulfillment будут хранить точный серверный снимок отдельно. Сортировка выполняется по квалифицированному числовому столбцу `app.tariffs.price`, затем ID: простое `ORDER BY price` после cast сортировало бы текстовый результат ([PostgreSQL ORDER BY](https://www.postgresql.org/docs/18/queries-order.html)).

Чтения не кэшируют старую цену, не восстанавливают пустую таблицу, не перезаписывают ручные настройки и не вызывают Supabase. Ошибка передаётся вызывающему коду, без retry. Runtime достаточно `USAGE app` и `SELECT app.tariffs`; запись и identity не нужны. HTTP-потребители тарифов/оплаты пока не переключены.

Unit-проверки: `node --experimental-strip-types --test tests/postgres-tariffs.test.mjs`; реальный SQL/active-only/цены/SELECT-only роль — `tests/bootstrap-postgres-integration.mjs`. Новые модули также проверены на Timeweb в **READ ONLY + TLS**: 105 категорий/7 тарифов, цены по числовому возрастанию, 5 записей журнала/0 аккаунтов. Это операторская проверка, не установка owner credentials в приложении.

## Администрирование справочников: серверные операции

`CatalogAdministration` и `TariffAdministration` используют существующий `PostgresDatabase.transaction`; операции подключены только к явно включаемому локальному API ниже, **не к действующей админке**. Новых зависимостей, migration/seed reset и удалённых аккаунтов нет. Действующие страницы и рабочая БД пока не переключены.

`withAdminTransaction(db, token, work)` принимает только случайный app-session token, не объект пользователя/роль из браузера. В одной транзакции блокирует пользователя, проверяет подтверждение/блокировку/актуальную admin-роль, затем блокирует сессию и проверяет scope, auth_version, абсолютный срок и простой. Порядок user → session согласован со входом/восстановлением пароля. После SQL-операций снова проверяет срок по `clock_timestamp()`: истечение во время ожидания справочника откатывает запись. Ошибки полномочий — одинаковый `AdminAccessError`, без информации об аккаунте; ошибка БД не превращается в успешный ответ. Никакого demo bypass или автоматического retry после COMMIT uncertainty. Callback только для ожидаемых SQL-операций, без внешних вызовов.

- `updateCategory(token, input)` принимает только `{id, name?, sortOrder?, active?}` и хотя бы одно поле изменения. UUID обязателен, название обрезается по краям и ограничено 200 UTF-16 units без control/unpaired surrogate, rank — целое 0–1000000, active — boolean. Иерархия/slug/ID неизменны. Возвращает сохранённую `CategoryRow` или `undefined`, не создаёт строку.
- `reorderCategories(token, ids)` принимает полный уникальный список корневых UUID (1–1000); дети, пропуски и неизвестные ID отклоняются. Все корни блокируются по ID, одна параметризованная запись назначает позиции 10,20,…; порядок не может сохраниться частично. Создание/удаление/смена parent здесь не предусмотрены; будущие операции над иерархией должны отдельно согласовать блокировки.
- `updateTariff(token, input)` принимает только `{id, name?, price?, durationDays?, active?}` и хотя бы одно изменение. Цена — конечный number 0–9999999999.99 с максимум двумя десятичными знаками; дробные копейки отклоняются, не округляются. В SQL отправляется точный decimal text. `durationDays` — целое 1–3650 либо явно null; отсутствие поля сохраняет срок. Возвращает boolean существования строки, не меняет ID/action и не создаёт/удаляет тариф. Это не payment arithmetic или снимок цены checkout.

Минимальные права именно этого контура: `USAGE app`; SELECT на справочники, UPDATE только name/sort_order/active у categories и name/price/active/duration_days у tariffs; у users SELECT(id,role,is_blocked,email_verified_at,auth_version), UPDATE(auth_version); у sessions SELECT(token_hash,user_id,auth_version,scope,expires_at,last_seen_at), UPDATE(last_seen_at). UPDATE одного столбца users нужен для FOR UPDATE, а не для повышения роли ([PostgreSQL SELECT privileges](https://www.postgresql.org/docs/18/sql-select.html)). Эти grants **не применены на Timeweb** и не заменяют права остальных identity-операций; общий runtime создаётся отдельно без DDL/role management. Владелец БД не используется в HTTP.

Проверки: native `tests/admin-authorization.test.mjs` и `tests/reference-administration.test.mjs`, реальный SQL в `tests/bootstrap-postgres-integration.mjs`. Изолированные synthetic accounts, настоящие identity sessions, демоция/отзыв под lock, expiry во время записи, rollback, конкурентные полные порядки двух администраторов и column-scoped роль с отказом чтения паролей/повышения ролей/DELETE/DDL. `listCategoryRows(token)` возвращает плоский справочник, включая скрытые строки, только id/parent_id/slug/name/sort_order/active; `listTariffs(token)` переиспользует canonical `PostgresTariffRepository` и возвращает `Tariff[]`. Оба чтения проверяют администратора и обновляют last_seen в той же транзакции. Fixture удаляет только свои аккаунты/роли/контейнер; Timeweb и реальные пользователи не используются. Backend guard не заменяет HTTP boundary.

## Локальный API администрирования

`/api/admin/local/[resource]` использует тот же `BLIZHNIY_AUTH_MODE=local` и строгую loopback development/test конфигурацию, что account API; origin обязательно HTTPS. При пустом mode — 404; попытка включить local mode в production — generic 503 до пула. `ENABLE_DEMO_ADMIN_BYPASS` не даёт доступа. Старые `/api/admin/categories`, `/api/admin/tariffs` и UI не переключены; новая схема и старые IDs не смешиваются.

| Метод и путь | Вход JSON | Успех |
| --- | --- | --- |
| POST `/api/admin/local/categories` | ровно `{}` | 200 `{categories: CategoryRow[]}` |
| PATCH `/api/admin/local/categories` | строгий category patch выше | 200 `{category: CategoryRow}`, неизвестный ID — 404 |
| PATCH `/api/admin/local/category-order` | ровно `{ids: string[]}`, полный порядок корней | 200 `{status:"saved"}` |
| POST `/api/admin/local/tariffs` | ровно `{}` | 200 `{tariffs: Tariff[]}` |
| PATCH `/api/admin/local/tariffs` | строгий tariff patch выше | 200 `{status:"saved"}`, неизвестный ID — 404 |

Чтение намеренно использует POST, как локальный account/session: сохраняем одинаковую проверку exact Origin и bounded JSON, не вводим ослабленный GET fallback. GET/HEAD/OPTIONS/PUT/DELETE запрещены (405); POST для category-order тоже запрещён. Нет create/delete/reset endpoint и автоматического создания admin-аккаунта. Это полный управляемый справочник, не пагинированные пользовательские публикации.

Все допустимые запросы требуют actual Host из конфигурации, exact Origin, `X-Blizhniy-Request: 1`, JSON, отсутствие query и cross-site Fetch Metadata. Тело ≤4096 фактических байт, deadline 2 с, затем ровно одна canonical `__Host-blizhniy_session` cookie; Bearer/body/query/duplicate cookie не являются авторизацией. HTTP-лимит тела строже внутреннего лимита 1000 IDs: для нынешних 18 корней достаточно, увеличение лимита требует отдельного решения. PATCH явно разрешён общему reader только этим handler; account API остаётся POST-only. Защита использует несколько слоёв, не одну SameSite cookie ([OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)).

Нет cookie — 401 UNAUTHENTICATED до пула; предъявленная сессия без актуальных admin-полномочий — одинаковый 403 ADMIN_REQUIRED; invalid edit — 422 INVALID_INPUT; неизвестный ресурс/ID — 404 NOT_FOUND; сбой БД/неопределённый commit — 503 ADMIN_UNAVAILABLE. Body/origin/method errors сохраняют код общей HTTP-границы. Все application-ответы no-store/no-referrer/nosniff, с X-Request-ID, без Set-Cookie и credential fields. Срок cookie не продлевается. Запись не повторять автоматически после timeout/503: результат может быть неизвестен; отдельно перечитать актуальный справочник после восстановления доступа.

Account и admin handlers используют `getLocalDatabase()` из `local-database.ts`: один lazy PostgreSQL pool на процесс, максимум 5 соединений, ничего при импорте. `account-cookie.ts` — единый strict parser. Изменение конфигурации требует рестарта, не подмены runtime во время запроса.

Admin limiter использует существующую SQL-таблицу и AuthRateLimiter с отдельным HMAC-derived secret namespace `local-admin`; 60 запросов всего за фиксированные 15 минут, без per-email счётчика и без PII в ключах. Счётчик общий для процессов и сохраняется при рестарте; admin traffic не расходует login quota. Проверяется до guarded операций; отказ — 429 с Retry-After 900, сбой SQL — generic 503 без записи справочника. Это **локальная** политика, не готовый production per-IP/per-user rate control.

Наблюдаемость: `local_admin_request` содержит только requestId, entryPoint=http, конечный набор operation/status/code, durationMs. Вопросы диагностики: что отклоняет запросы, растёт ли 429/503, какова задержка? Ответ связывается с событием по X-Request-ID. Нет URL, body, email, user ID, session token/hash, DB message или цены в логах. Next development access logging исключает `/api/admin/local`, а последний header rule сохраняет no-referrer; rejection query token проверен через настоящий Next HTTPS. Это не durable audit trail/production metrics/alerts.

Проверки: `tests/local-admin-http.test.mjs`, SQL list/guard в bootstrap fixture, HTTP в `tests/local-admin-web-integration.mjs`, запускаемом `npm run test:postgres:local`. Последний runner также проверяет account/recovery UI и отдельный локальный экран справочников в Chromium. Только собственные localhost PostgreSQL/HTTPS Next/mail capture и synthetic accounts; реальные серверы не используются. Отдельный production smoke с включённым demo bypass проверяет default-off 404 и forced-local 503. Полный dependency audit не зелёный — ограничения и дата повторного разбора в [dependency-security.md](dependency-security.md).

## Локальный экран справочников

`/auth/local/admin` открывается только с той же валидной local development/test конфигурацией и HTTPS origin; production, пустой режим и неверная конфигурация дают 404. Ссылка находится в локальной форме аккаунта. Используются существующие цвета, поля и интервалы проекта: на узком экране формы идут одной колонкой, с md — двумя. Это отдельный экран, не переключение старого `/admin` или публичного каталога. Метаданные запрещают индексацию; существующее правило `/auth/local/:path*` сохраняет no-referrer.

Экран не получает session token, не читает browser storage и не доверяет показанной ранее роли: оба справочника запрашиваются через guarded API. Редактируются только существующие name/active/price/durationDays/sortOrder; ID, slug, action и parent не меняются. Цена вводится десятичной строкой с точкой или запятой, до двух знаков, без округления; пустая цена недопустима, 0 допустим. Пустой срок — явный null, иначе целые 1–3650 дней. UI-проверка помогает пользователю, но не заменяет серверную валидацию. Полный порядок корней (включая скрытые) меняется кнопками ↑/↓, затем отдельным сохранением; это черновик, не optimistic SQL write.

Во время проверки или записи редакторы скрыты; busy ref блокирует повторное сохранение. После подтверждённой записи выполняется чтение актуальных данных, не подстановка введённой цены. После сетевого/неизвестного ответа показано предупреждение о неизвестном результате, редакторы скрыты до перечитывания; PATCH не повторяется автоматически. 401/403, отсутствие справочника, invalid input и rate limit имеют отдельные сообщения без raw server errors. Пустой справочник объясняется текстом и не восстанавливается из seed.

Возврат на вкладку, focus, persisted pageshow и сообщение `changed` из существующего локального auth BroadcastChannel сбрасывают данные и несохранённые черновики. Сообщение не содержит identity/credentials и само не даёт прав: запускается новое серверное чтение. Счётчик версии игнорирует старые ответы после logout/смены контекста; ошибки не оставляют ранее загруженные редакторы. Фоновый polling и автоматическое повышение роли отсутствуют. Администратора заранее назначает оператор отдельно; UI/API не создают admin-аккаунт.

Проверки клиентского адаптера и SSR — `tests/local-reference-admin*.test.mjs`. `tests/local-reference-admin-ui-web.mjs` проверяет реальные SQL-записи через UI, обычного пользователя/демоцию/logout, поздний list response после logout, неизвестный результат PATCH без retry, keyboard reorder, состояние пустоты/429 (для этих двух состояний HTTP response подменяется только в браузерном fixture). Скриншоты и DOM проверены на 320/768/1024/1440; существующий axe-core проверяет WCAG A/AA внутри main, не весь прежний сайт. Chromium изолирован, внешние HTTP-запросы запрещены. Новых пакетов, миграций и прав на Timeweb нет.

## Подготовка фотографий: локальный модуль

`src/lib/media-image.ts` — серверная функция `normalizeMediaImage(bytes, claimedType)`, без HTTP, SQL, файловых путей и сетевых запросов. Это первый инкремент media, не замена действующей загрузки. Вход — только `Uint8Array`/Buffer, не filename/URL; копия создаётся до первого await. Результат: новые WebP-байты, MIME, фактические размер/ширина/высота и SHA-256 результата. Digest не является проверкой владельца или разрешением на публикацию.

Sharp загружается только внутри нормализации после проверки входа; импорт `MediaImageError`/типов не загружает native codec. `tests/media-image-import.test.mjs` проверяет это в новом Node-процессе по native module cache, включая ESM entry установленного Sharp.

Граница недоверенных байтов защищает память VPS, приватность метаданных и будущую выдачу файлов: подпись контейнера должна соответствовать заявленному MIME, но этого недостаточно — после чтения заголовков обязательно выполняется декодирование пикселей и повторное кодирование. Допускаются статические JPEG/PNG/WebP/GIF. GIF/WebP с несколькими кадрами и APNG отклоняются, не превращаются молча в первый кадр; SVG/TIFF/AVIF/прочие типы не принимаются. RIFF WebP должен иметь точную длину контейнера. Дописанные к допустимому PNG байты не сохраняются в результате.

Ограничения: вход ≤10 МиБ; ≤24 000 000 пикселей, максимум 4 канала; результат вписывается в 2048×2048 без увеличения, WebP quality 80/effort 3, ≤2 МиБ. Высокодетализированный/шумный снимок может превысить выходной предел и быть отклонён даже при допустимом входном размере. Это политика новой подготовки, не изменение существующих browser/form лимитов. EXIF/GPS, XMP, ICC и IPTC не переносятся; ориентация применяется к пикселям, цвета конвертируются в sRGB стандартным поведением Sharp.

Одновременно работает одно декодирование **на экземпляр модуля**, без очереди; следующий вызов получает `MEDIA_BUSY`. Это не общий лимит между Next bundles/процессами. Slot освобождается в finally; неизвестные native ошибки заменяются `INVALID_IMAGE`, без cause/исходных подробностей. Остальные коды: `UNSUPPORTED_IMAGE`, `IMAGE_TOO_LARGE`, `MEDIA_UNAVAILABLE`. Модуль не пишет логи с байтами/именами/метаданными. HTTP status mapping ещё не создан.

Timeout Sharp 5 секунд ограничивает обработку libvips, **не полное wall-clock время**: ожидание libuv очереди не учитывается. Ограничение пикселей зависит от корректности заголовков; это не гарантия ограничения RSS и не sandbox нативных кодеков. До подключения недоверенного HTTP нужен отдельный worker на том же VPS с ОС-лимитами памяти/CPU, жёстким внешним deadline/завершением процесса, ограниченным IPC/очередью и fail-closed ответами. Не менять глобальные Sharp cache/concurrency ради media: они общие с Next image optimizer.

Sharp 0.35.5 уже был установлен через Next; теперь это явная pinned production dependency. Версии, адреса и integrity существующего package graph не изменены, install lifecycle остаётся запрещённым. Не выполнены запись вне releases, квоты, метаданные БД, ownership, выдача, удаление/очистка сирот, browser upload, production cutover и резервирование.

Проверка: `node --experimental-strip-types --test tests/media-image.test.mjs` — реальные синтетические байты и установленный native codec, без фото пользователей. Проверяются повреждённый PNG с читаемым заголовком, входная/выходная/pixel границы, анимация включая APNG, GPS-bearing EXIF, ориентация, мутация входа и занятость/освобождение slot. Общий native suite включает этот файл. Эти тесты не доказывают защищённость native parser от неизвестных уязвимостей или готовность HTTP/file storage.

Основания: [Sharp constructor](https://sharp.pixelplumbing.com/api-constructor/), [header-only metadata](https://sharp.pixelplumbing.com/api-input/), [выходные метаданные и timeout](https://sharp.pixelplumbing.com/api-output/), [autoOrient](https://sharp.pixelplumbing.com/api-operation/), [ОС-изоляция и ресурсы](https://sharp.pixelplumbing.com/security/).

## Локальный ограниченный worker фотографий

`createLocalMediaWorker(rootDirectory)` из `src/lib/media-worker.ts` возвращает `normalize(bytes, mimeType, signal?)`. Factory и каждый вызов требуют Linux, Node.js 22 и `NODE_ENV=development|test`; browser/production/неизвестный режим отклоняются до запуска. Это серверный модуль для компиляции Next, не прямой CLI-entry с extensionless imports. `rootDirectory` — доверенный абсолютный каталог исходников оператора, не поле загрузки. Последняя проверка VPS показывала Node.js 20; в этом этапе runtime не обновлялся и worker не устанавливался на сервер.

Для каждого задания создаётся собственный transient user-service `blizhniy-media-<random UUID>.service` через абсолютный `/usr/bin/systemd-run`, без shell и environment expansion. Нужны доступный user manager и делегированные cgroup v2 memory/cpu/pids controllers; неполная поддержка даёт отказ, не fallback на декодирование в Next. Третий VPS, Docker, внешнее хранилище и новые npm-пакеты для этого не нужны.

ОС-политика: `MemoryMax=512M`, `MemorySwapMax=0`, `CPUQuota=100%`, `TasksMax=32` (включая threads), `RuntimeMaxSec=8s`, `TimeoutStopSec=1s`, `KillMode=control-group`, `KillSignal=SIGKILL`, `NoNewPrivileges=yes`, `LimitCORE=0`. Node old-space — 128 МиБ, libuv pool — 2, VIPS concurrency — 1. `scripts/media-worker-runtime.mjs` до импорта native codec проверяет текущую kernel cgroup, точные memory/swap/pids значения, CPU quota ≤ одного CPU и NoNewPrivs. RuntimeMaxSec — внешний deadline относительно активного сервиса, независимо от timeout декодера; запуск/IPC дополнительно ограничены таймером supervisor 10 секунд. Задержки event loop/планировщика не превращают этот таймер в абсолютную wall-clock гарантию.

Сам Node запускается через `env -i` с тремя явными переменными: `NODE_ENV=test`, `UV_THREADPOOL_SIZE=2`, `VIPS_CONCURRENCY=1`; credentials и NODE_OPTIONS не передаются. Для обращения к manager launcher получает только фиксированные NODE_ENV/LANG и локальные bus/runtime адреса собственного UID. stderr игнорируется, root `.env` не читается. Байты/EXIF/имя файла не передаются аргументами, не пишутся на диск и не логируются.

Входной IPC — один byte индекса разрешённого MIME и ≤10 МиБ изображения. Выход — versioned `BLM1` header 45 bytes и ≤2 МиБ WebP, либо один конечный error code без payload. `media-worker-protocol.ts` проверяет ширину/высоту, фактический размер, RIFF/WEBP контейнер и SHA-256; пиксели в supervisor повторно не декодируются. Буфер stdout ограничен также 256 chunks. Результат принимается только после успешного закрытия child; частичный/невалидный/oversized ответ, crash, OOM и timeout дают generic `MEDIA_UNAVAILABLE`. Данные самого worker остаются отдельной недоверенной границей; digest не является защитой от взломанного codec/worker.

Один slot хранится в global state процесса, общий для повторных экземпляров/загрузок модуля; очереди и автоматического retry нет. Это **не** межпроцессный лимит и не общий лимит VPS. Abort/deadline/overflow останавливают только собственный UUID-service через `systemctl --user stop`, затем закрывают launcher. Убийство одного systemd-run не считается остановкой worker. Если подтверждение остановки не получено, supervisor блокирует новые задания до проверки оператором и перезапуска; поздний close не снимает блокировку. RuntimeMaxSec действует также при исчезновении родительского Node-процесса при работающем manager.

Проверки без системного manager: `node --experimental-strip-types --test tests/media-worker*.test.mjs`. Protocol использует реальные synthetic WebP; supervisor lifecycle/control faults проверяются fake subprocess boundary, executable без cgroup — реальным uncapped child и должен отказать. Полный native suite включает эти тесты. Отдельный opt-in `node --experimental-strip-types --test tests/media-worker-integration.mjs` запускает настоящие локальные user-services/cgroups; не требует рабочих серверов или БД. Supervisor транспилируется TypeScript→CommonJS в тестовом VM, как модуль приложения; это не HTTP/Next integration. Проверяются 24 MP, EXIF/orientation, malformed bytes, чистое env, crash, overflow, abort, фактические systemd `oom-kill`/`timeout` и следующий успешный job. Только fault executable подменяется тестом; для чтения Result у faults убран `--collect`, после проверки очищаются только собственные failed units.

Это **ограничение ресурсов, не полноценный security sandbox**: тот же UID может читать разрешённые ему файлы/процессы и обращаться к сервисам; `env -i`/NoNewPrivileges не устраняют native RCE. До production нужны отдельная ограниченная identity, запрет доступа к секретам/БД/файлам приложения и сети, глобальный admission limit, runtime/deploy assets, наблюдаемость и VPS-проверки под реальными ОС-политиками. Upload HTTP и файловое хранилище не подключены, production factory по-прежнему запрещён. Этап 6 остаётся открытым.

Основания: [systemd-run v257](https://raw.githubusercontent.com/systemd/systemd/v257/man/systemd-run.xml), [cgroup resource controls](https://raw.githubusercontent.com/systemd/systemd/v257/man/systemd.resource-control.xml), [Node child_process](https://raw.githubusercontent.com/nodejs/node/v22.23.1/doc/api/child_process.md).

## Локальный файловый слой фотографий

`createLocalMediaFileStore(rootDirectory)` из `src/lib/media-files.ts` — async factory с методами `write(record, bytes, attemptId?): Promise<void>` и `read(record): Promise<Buffer>`. `MediaFileRecord` содержит только `id`, `mimeType`, `width`, `height`, `size`, `sha256`; SQL-метаданные не дублируются в JSON/sidecar на диске. Factory и каждый вызов требуют Linux и `NODE_ENV=development|test`. HTTP, Nginx/public-раздачи, env-переключателя и production fallback нет. Это файловый примитив, **не проверка владельца**: запись получает record от guarded SQL reservation/claim (6e1 ниже), чтение — после разрешённого SQL lookup. UUID и digest сами по себе не дают пользователю права чтения.

Оператор заранее создаёт отдельный постоянный каталог **вне releases/public**: canonical absolute path, текущий UID, точный mode 0700, без symlink aliases. Factory не создаёт/не исправляет каталог и не выбирает fallback. Для каждой операции каталог открывается `O_DIRECTORY|O_NOFOLLOW`; проверяются UID/mode, исходные bigint dev/inode и resolved `/proc/self/fd/<fd>` path. Плоские leaves адресуются через удерживаемый descriptor, не через изменяемый строковый ancestor. Замена root между вызовами даёт отказ. Требуются доступный procfs и файловая система с POSIX hardlink/fsync; поддержка нестандартных/сетевых FS не заявлена. Иерархия должна управляться доверенным оператором: это не sandbox против root/других процессов того же UID, которые могут менять permissions, mount или inode contents.

Ключ — только canonical lowercase UUID v4 от будущей серверной reservation, не filename/URL клиента. Входные metadata/bytes копируются до первого await; проверяются MIME WebP, размеры 1..2048, bytes 12..2 МиБ, exact size, RIFF/WEBP shape и SHA-256 через существующий worker protocol. Файловый слой не загружает Sharp и не декодирует пиксели: проверка контейнера не заменяет предшествующую нормализацию в ограниченном worker.

Запись создаёт собственный `.pending-<random UUID>` с mode 0600 и `O_CREAT|O_EXCL|O_NOFOLLOW`, пишет bounded bytes и выполняет file sync. Только полный файл получает конечное имя `<record.id>.webp` через hardlink, который не перезаписывает существующий leaf; затем удаляется собственное временное имя и синхронизируется directory. Конкурирующие записи одного ID оставляют ровно один целый объект, проигравшая получает `MEDIA_FILE_EXISTS`; существующий файл/ссылка сохраняются. Не использовать обычный rename поверх существующего назначения или truncate.

Cleanup касается **только временного файла данного вызова**. Перед unlink сравниваются dev/inode с доказательством, прочитанным из исключительно созданного descriptor, тип/UID/mode и число ссылок. Путь ниже закреплённого root; отказ не расширяет область удаления. Подмена inode не удаляется. Непроверенная ownership/cleanup/close или ошибка после создания конечного имени блокируют экземпляр. Повторно создавать экземпляр без операторской сверки нельзя считать восстановлением: блокировка не глобальна и не сохраняется при рестарте. Generic ошибка без raw cause/path означает также **UNKNOWN**, если файл уже получил конечное имя: объект остаётся для будущего readback/reconciliation, а не удаляется как якобы неуспешный. Автоматических повторов нет.

Чтение требует полный record из доверенного backend; leaf открывается `O_NOFOLLOW|O_NONBLOCK`. До и после bounded read проверяются regular file, UID/0600, одна hardlink, exact size и стабильные bigint inode/mtime/ctime. Выделяется только ожидаемый размер + один byte для выявления роста; отсутствующие/FIFO/directory/symlink/hardlink, изменённые и повреждённые bytes дают `MEDIA_FILE_UNAVAILABLE`, не частичный результат. Нарушение record shape — `INVALID_MEDIA_FILE`. `MediaFileError` не сохраняет raw filesystem diagnostics. Методы list/delete/prune отсутствуют: они требуют отдельного контракта владельца и очистки.

Проверка: `node --experimental-strip-types --test tests/media-files.test.mjs`. TypeScript транспилируется как серверный модуль; все сценарии используют настоящую локальную FS и синтетический WebP. Дополнительно fault adapters подменяют отдельные I/O вызовы (partial write, sync/stat/unlink failure, inode/root substitution, growth), а не всю FS. Проверены restart, конкуренция, отсутствие final name до sync, traversal, existing ancestor aliases, чужой UID, mode, FIFO, hardlinks, generic errors и disabled latch. Это не HTTP/browser/SQL integration, не crash/power-loss durability proof и не испытание диска VPS.

PG-метаданные/сессия/ownership и атомарный учёт reservations реализованы локально в 6d; постоянный однократный write journal — в 6e1 ниже. **Перед upload остаются обязательными:** ограничение количества/параллельности jobs, OS writer fencing/crash-safe reconciliation и доказуемая очистка после рестарта, TTL/удаление/export и независимая копия в РФ, HTTP/приватная выдача, production worker sandbox/установка на VPS. Низкоуровневый FS-примитив сам не ограничивает суммарный объём и не решает сироты после kill/power loss; этап 6 и его checklist остаются открытыми. Ни серверы, ни рабочая БД, ни действующая загрузка не менялись.

Основание файловых API/флагов: [Node.js 22 fs](https://raw.githubusercontent.com/nodejs/node/v22.23.1/doc/api/fs.md).

## Фотографии: локальные SQL-метаданные и резерв квоты (6d)

`MediaMetadataRepository` из `src/lib/media-metadata.ts` связывает уже существующий файловый reader с PostgreSQL. Constructor и каждый вызов разрешены только в `development|test`, без browser, HTTP, нового env-переключателя, внешних запросов или подключения к действующему upload. БД и файловый reader передаются доверенным серверным кодом; raw input изображения здесь не декодируется.

- `reserve(token,intentId,imageMetadata)` принимает только MIME/width/height/size/SHA-256 нормализованного WebP и UUIDv4 intent; owner/ID/state/path/лишние поля запрещены. Владелец берётся из guarded app identity; ID генерируется в БД. Snapshot до await. Возвращает `pending`; тот же pending intent даёт `MEDIA_IN_PROGRESS`, изменённые metadata — `MEDIA_INTENT_CONFLICT`, ready повтор возвращает тот же объект.
- `getByIntent(token,intentId)` — owner-scoped readback при неизвестном исходе записи; no retry. `null` не является разрешением немедленно запускать ещё один FS writer: reservation не заменяет fencing/claim.
- `complete(token,id)` блокирует owned record, читает и проверяет конечный файл через FS layer, затем переводит pending в ready. Ошибка FS оставляет pending. Повтор ready также проверяет файл; окончательная проверка срока сессии после работы может откатить изменение.
- `readOwned(token,id)` выдаёт проверенные bytes только для owned ready внутри той же live-session transaction. Чужой/неизвестный/pending ID даёт null без обращения к FS; роль admin не обходит owner filter. Expiry после чтения не возвращает bytes вызывающему коду.

`0006-media-reservations.sql` добавляет две пустые таблицы: `app.media_objects` с immutable owner/intent/metadata и `app.media_storage_budget`. Общий атомарный SQL-лимит — 5 000 000 000 байтов + 10 000 объектов; все pending/ready, в том числе старые и с неизвестным исходом, занимают место. После успешного INSERT AFTER-trigger делает условный UPDATE одной budget-строки. Конкуренция разных процессов/владельцев сериализуется в PostgreSQL; пропущенный ON CONFLICT не учитывается повторно. Это **учёт SQL reservations**, не уже подключённый контроль всего диска VPS или всех временных файлов. Прямой вызов файлового write остаётся внутренним примитивом, ещё не upload workflow.

Budget-trigger — единственный SECURITY DEFINER в новом манифесте, fixed `pg_catalog,pg_temp` и fully-qualified table; PUBLIC execute/table privileges отозваны. Runtime не получает budget UPDATE/DELETE/TRUNCATE/DDL или владение схемой/функциями. Ограниченная тестовая роль имеет только нужные SELECT/INSERT/UPDATE столбцы; identity FOR UPDATE требует UPDATE authority, в fixture используется monotonic `users.auth_version`, а не разрешение менять role/password/id. Тест проверяет trigger с non-superuser owner и чужим search_path/temp shadow table. Это серверный доверенный SQL runtime, **не RLS для пользовательских SQL-подключений**.

Owner FK RESTRICT сохраняет доказательство при попытке удаления аккаунта; DELETE media запрещён даже оператору обычным DML до отдельного cleanup-контракта. TTL, освобождение квоты, list/delete/export, writer lease, temp-file journal/fencing и crash reconciliation **не реализованы этим этапом**. До их проверки нельзя подключать повторяемый HTTP upload. Обоснование — [ADR-003](decisions/0003-media-reservations.md).

Проверки: `tests/media-metadata.test.mjs` (границы/ошибки/local guard), `tests/media-metadata-integration.mjs` вызывается только существующим opt-in `tests/bootstrap-postgres-integration.mjs`. Настоящие PostgreSQL 18.6 и private FS с синтетическим WebP: owner/admin isolation, reserve→file→ready→read/restart, pending/ready повторы, unknown COMMIT, quota races/object limit/old pending, stale/expired/revoked sessions, expiry after FS, column grants, immutable records, guarded down и конкурентный INSERT во время down. Подмена только потерянного ответа и role boundary; expiry устанавливается собственным fixture SQL после настоящей FS-проверки, без коротких таймеров. SQL-движок и bytes файлов настоящие. Контейнер/root проверяются по ownership перед очисткой; удалённая БД не используется.

План удалённого применения 0006–0007 (пока не выполнялся):

1. Зафиксировать совместимый commit, остановить только будущий media writer, сделать и проверить независимую копию БД. READ ONLY сверить TLS, цель и журнал 0001–0005; 0006–0007 не должны быть внесены вручную или существовать вне журнала.
2. Проверить `--plan`, migration credentials и функцию budget-owner (не HTTP credentials). Явный `--apply HOST:DATABASE` установит отсутствующие 0006–0007 в порядке манифеста при совпадающем прежнем журнале и не перезапишет справочники.
3. READ ONLY сверить SHA-256, три пустые таблицы/нулевой budget, ограничения и отсутствие PUBLIC прав. Отдельной runtime-роли дать только проверенные grants; не переносить владельца/широкие операторские полномочия в приложение.
4. Upload и production guards остаются выключенными. Для rollback вернуть совместимое приложение; down допустим только после остановки writers и доказанной пустоты обоих хранилищ, в порядке 0007 → 0006. Down берёт ACCESS EXCLUSIVE **до** проверки; recorded attempts, заполненные reservations/ненулевой budget отклоняются. Не удалять данные и журнал, чтобы добиться «успешного» отката. Изолированный fixture вправе очищать свои синтетические строки, рабочая БД — нет.

## Фотографии: однократный writer и постоянный attempt journal (6e1)

`0007-media-write-attempts.sql` добавляет `app.media_write_attempts`, неизменный UUID/time и UNIQUE(media_id)/FK RESTRICT. Trigger под parent row lock допускает только pending reservation, запрещает UPDATE/DELETE; PUBLIC права отозваны, новых SECURITY DEFINER нет. Runtime достаточно SELECT/INSERT(media_id), без ID/time/reset/delete/DDL. Новая таблица не расходует file budget повторно: его уже занял media reservation.

`MediaMetadataRepository.claimWrite(token,fileId,imageMetadata)` в одной guarded owner transaction сравнивает все metadata, блокирует pending media и делает INSERT ON CONFLICT DO NOTHING. Только первый успешный COMMIT возвращает `{attemptId,record}`; missing/foreign — MEDIA_NOT_FOUND, changed metadata — MEDIA_INTENT_CONFLICT, ready/claimed — MEDIA_IN_PROGRESS. `getWriteAttempt(token,fileId)` даёт owned `{attemptId,claimedAt}`/null для наблюдения, **не повторное разрешение записи**. Нет TTL/reassignment или сброса по возрасту. Если ответ COMMIT потерян, FS не запускается, а попытка остаётся для безопасной будущей сверки.

`LocalMediaWriter` из `media-write.ts` — локальный Linux development/test orchestrator `write(token,fileId,normalizedImage)`. Строгий DTO нормализованного WebP, snapshot bytes до await, ≤2 МиБ и RIFF/WEBP/SHA-256 проверены без повторного native decode. Порядок: committed claim → private FS write с attempt ID → guarded complete. Неизвестный исход не вызывает retry/удаление/reset; ошибки finite/generic без raw cause. Изменение/удаление metadata/готовность остаются в SQL owner/session boundary; файловая запись не держит SQL-транзакцию открытой и может закончиться после отзыва сессии, но private read/ready требуют действующую сессию.

FS `write(record,bytes,attemptId)` выбирает строго `.pending-<attempt UUID>`; optional attempt разрешает старый random-temp low-level contract без изменения прежних tests. Writer всегда передаёт серверный claim UUID. В имени нет пользовательского пути, existing leaf не перезаписывается/не удаляется; inode proof собственной cleanup прежний. Теперь оба возможных имени после kill известны из SQL без listing directory. Достоверный inode/root и остановка writer всё ещё должны быть доказаны отдельно; имя/UUID/claim сами по себе не разрешают очистку.

Проверки: `tests/media-write.test.mjs`, дополненные FS/metadata tests; `tests/media-write-integration.mjs` внутри owned bootstrap fixture. Настоящие PG18/private FS: запись→ready→private read, две одновременные попытки, owner/admin/metadata denial, lost claim/FS/ready responses без replay, подтверждение сохранившегося конечного файла без перезаписи, restricted column grants и empty-only concurrent down. `media-write-crash-fixture.mjs` — собственный Node-child с clean env/без SQL и внешней сети: настоящий FS layer, fault adapter останавливает запись после file-sync первых 12 байт; тест делает SIGKILL точному собственному child и ждёт close. После kill partial leaf/claim/budget остаются, новая попытка отказана. Это process-crash test, не power-loss/полное production fencing.

Далее 6e2: отдельный файловый процесс с OS-backed serialization/fencing и доказуемая остановка, затем reconciliation/cleanup/release. Пока отсутствуют эти механизмы, попытки **не переиспользуются и не освобождаются**, HTTP/production выключены. [ADR-004](decisions/0004-media-write-attempts.md) фиксирует этот предел; автоматическую очистку по PID/TTL/DB timeout не добавлять.

## Аккаунты и сессии

`withAppSessionTransaction` — общий серверный transaction guard для admin/media: user → session → resource locks, live app scope и повторная проверка времени после работы. Владелец берётся из заблокированной DB identity, не из payload. Admin wrapper сохраняет прежнюю проверку роли до session work и прежний `AdminAccessError`; обычная app-сессия не становится admin authority. Policy — статический код вызывающего сервера, не HTTP-опция.

`src/lib/identity.ts` — внутренний серверный модуль, не публичный Auth API. Пароли хешируются встроенным async scrypt; новые значения 15–128 символов, пробелы не обрезаются. KDF допускает два одновременных вычисления на процесс; превышение выдаёт ошибку ёмкости, не «неверный пароль». Подробности и причины — [ADR-002](decisions/0002-server-sessions.md).

`IdentityStore.login(email, password, previousToken?)` создаёт сессию только после проверки пароля, подтверждения email, блокировки и повторной проверки credential hash/version под row lock. Переданная прежняя app-сессия отзывается в той же транзакции; ошибочный вход или сбой вставки сохраняют её. Отдельная data-subject сессия этой операцией не удаляется. Результат содержит plaintext токен **для серверного HttpOnly cookie-handler**, не для JSON/localStorage/логов. `resolveSession` читает актуальные роль/блокировку и проверяет SHA-256 токена, auth_version, 8-часовой абсолютный срок и 30-минутный простой. Обычная активность не продлевает абсолютный срок.

`revokeSession` — идемпотентный выход; `revokeAllSessions` отзывает все прежние сессии аккаунта через auth_version. Caller обязан проверять владельца перед передачей userId. Изменение пароля/email напрямую SQL тоже инвалидирует старые сессии. `pruneSessions` удаляет истёкшие, простаивающие и отозванные версии; до запуска пользователей его нужно включить в maintenance runner с ограниченными правами.

`loginForDataSubject` выдаёт только ограниченный scope для удаления/экспорта своих данных, включая заблокированный аккаунт без прежней сессии. `resolveDataSubjectSession` разрешён только соответствующим ownership-checked handlers. Он не заменяет обычный guard; такой токен никогда не даёт доступа к обычному API.

## Регистрация и подтверждение

`src/lib/registration.ts` предоставляет серверный `RegistrationStore`. Его вызывает только явно включаемый локальный HTTP-handler, описанный ниже. Он использует тот же scrypt и PostgreSQL-клиент, без нового провайдера/SDK.

- `register(input)` принимает ровно `email`, `password`, `acceptedAgreement: true`, `acknowledgedPrivacy: true`, `agreementVersion`, `privacyVersion`. Версии обязаны совпасть с `registration-legal.ts`; неизвестные поля (включая роль/время/подтверждение) отклоняются. Email приводится к lower/trim по существующему identity-контракту; provider-specific преобразований адреса нет. Пароль не изменяется.
- Один transaction создаёт неподтверждённого `user`, обе отметки документов и ссылку. Повторная регистрация возвращает внутренний `null`, не изменяя существующие данные. Локальный HTTP-ответ одинаков для нового/существующего адреса и не возвращает mail payload.
- `EmailConfirmation` содержит email, plaintext токен и срок **только для серверного почтового транспорта**; его запрещено писать в логи/API JSON. В PostgreSQL только SHA-256 случайного 256-битного токена, срок 1 час, email и credential version.
- `confirmEmail(token)` атомарно удаляет действительный токен и подтверждает аккаунт; 12 одновременных обращений дают одного победителя. Порядок блокировок — пользователь, затем токен. Проверка `clock_timestamp()` после user lock не допускает подтверждение ссылкой, истёкшей во время ожидания. Смена email/пароля, блокировка, другой purpose или replay отклоняются. Автоматического входа нет.
- `resendConfirmation(email, password)` требует исходный пароль неподтверждённого незаблокированного аккаунта; KDF вне transaction, затем повторная проверка credential version под lock. Старый токен заменяется атомарно; сбой сохраняет прежнюю ссылку и не меняет legal records. Забытый пароль не восстанавливается этой операцией.
- `pruneConfirmations()` удаляет неактивные токены. `prunePendingRegistrations()` делает пригодными к очистке неподтверждённые аккаунты старше 24 часов, до 100 за запуск, с каскадным удалением legal/token records. До запуска пользователей обязательны maintenance schedule, контроль backlog и описание срока с учётом интервала задачи; автоматического runner сейчас нет.

`0002-registration.sql` применяется после `0001`, транзакционно и однократно. `0002-registration.down.sql` отказывается удалять непустые добавленные таблицы, сохраняет identity и не использует CASCADE. Runtime grants должны давать INSERT/SELECT, но не UPDATE legal records; прямое редактирование отметок не является пользовательским сценарием. Public grants отозваны. Юридические отметки означают принятие соглашения и ознакомление с политикой, **не** согласие на рекламу/обмен ПД.

## Восстановление пароля: серверный модуль

`src/lib/password-recovery.ts` подключён только к явно включаемому локальному HTTP API, не к браузерной форме или рабочей БД. `0004-password-recovery.sql` — отдельная additive migration после identity/registration; не применяется при старте приложения. Down отказывается удалять непустую таблицу; аккаунты/сессии не удаляются откатом схемы.

- `requestRecovery(email)` выдаёт внутренний `{email,token,expiresAt}` или null только для подтверждённого адреса; блокировка не запрещает владельцу восстановить пароль, но остаётся после reset. Хранится только SHA-256 токена, одна ссылка на пользователя, срок 30 минут. Повторный запрос атомарно заменяет ссылку, не пароль. **Нельзя** раскрывать token/null или различие DB timing клиенту; HTTP-handler применяет shared limiter и одинаковый accepted response до поиска аккаунта/доставки.
- `resetPassword({token,password})` возвращает внутренний `{email}` для уведомления после commit или null при непригодной ссылке. Input shape ошибки — `RecoveryInputError`, password policy — прежний `hashPassword`, capacity/DB ошибки не маскируются успешным ответом. KDF вне транзакции; user → recovery-row lock → проверка актуальных email/version/confirmation/expiry → consume/password/version/delete all session scopes одним commit. Пароль не обрезается, роль/блокировка/подтверждение не повышаются, автоматического входа нет. После неизвестного commit reset не повторять автоматически: ссылка одноразовая.
- `pruneRecoveries()` удаляет до 1000 просроченных/устаревших хешей с SKIP LOCKED, не пользователей; периодический запуск ещё не включён. Удаление аккаунта каскадно удаляет recovery record. Перед production нужны отдельные runtime/migration credentials и минимальные grants, а не PUBLIC/широкие права.

Срок проверяется по реальному времени после **обеих** блокировок; одного volatile условия в DELETE недостаточно, если оно вычислено до ожидания tuple lock. Проверены повтор, конкуренция, чужой аккаунт, purpose, срок под user/token lock и rollback при insert/update/delete fault. Браузерная форма восстановления — следующий инкремент; ссылки и уведомления перехватываются локально, реальные письма не отправляются. Подробности решения — [ADR-002](decisions/0002-server-sessions.md).

## Локальный HTTP и перехват писем

Только `BLIZHNIY_AUTH_MODE=local` при development/test, явной loopback PostgreSQL и SSL disable. Origin — строго `http://127.0.0.1:<port>` или `https://127.0.0.1:<port>`; cookie-действия и recovery требуют **HTTPS**. Mail URL — строго `http://127.0.0.1:<port>/messages`, порт ≥1024. Секрет limiter — случайные 32+ символов вне Git. Пустой mode отключает маршруты (404), неверная/production-конфигурация отказывает (503) до создания пула. Пул/registry один на процесс, общий для registration/identity/recovery/limiter; менять конфигурацию или структуру runtime нужно перезапуском. Dev-сервер обязательно слушает **127.0.0.1**, не 0.0.0.0.

- `POST /api/account/register`: прежний strict registration input, только synthetic `*.invalid`; новый/существующий адрес получает одинаковый `202 {status:"accepted"}` без mail token/user id/email. Не считается безопасным повторением доставки письма: после неопределённого commit/недоставки используйте password-gated resend, не замену пароля через signup.
- `POST /api/account/resend`: ровно email/password, такой же 202 независимо от результата проверки аккаунта.
- `POST /api/account/confirm`: ровно `{token}`, 200 `{status:"confirmed"}` или 400 INVALID_CONFIRMATION; неверный shape — 422. Сессия/cookie не выдаётся. GET любого существующего действия — 405 без потребления токена; неизвестное действие — 404.
- `POST /api/account/login`: ровно email/password, только synthetic `.invalid`; успешный ответ `200 {status:"authenticated", user:{id,email,role,isBlocked}}`. Пароль, session token/hash/version не входят в JSON. Неподтверждённый/заблокированный/неизвестный аккаунт и неверный пароль получают одинаковый 401 INVALID_CREDENTIALS. Общий credential limiter применяется **до** KDF. Не повторяйте login автоматически после timeout: результат commit может быть неизвестен; после неопределённости проверьте `/session`.
- `POST /api/account/session`: ровно `{}`, 200 `{user:{id,email,role,isBlocked}}` или 401 UNAUTHENTICATED. Читает только одну корректную cookie `__Host-blizhniy_session`; query/body/Bearer, malformed и duplicate cookie не являются авторизацией. `requireAccountSession` — общий app-scope guard; resource handler дополнительно проверяет владельца/роль, а перед вызовом guard обязан применить HTTP/origin boundary. Блокировка/срок/версия и роль читаются из БД, не из клиентских полей. Cookie lifetime не продлевается.
- `POST /api/account/logout`: ровно `{}`, отзывает предъявленную сессию и удаляет cookie с теми же атрибутами. Без cookie идемпотентен и не открывает пул; заблокированный пользователь тоже может выйти. Сбой БД даёт 503 и **не** выдаёт ложный успешный logout/удаление cookie. Credential-attempt limiter не мешает lookup/logout; общие production ресурсные лимиты ещё нужны.
- `POST /api/account/recover`: ровно `{email}`, только synthetic `.invalid`. После общего/per-email limiter одинаковый `202 {status:"accepted"}` до поиска аккаунта и доставки; не обещает существование адреса или получение письма. Локальный процесс допускает два фоновых задания, без очереди; перегрузка — generic 503. Внутренний challenge/null отправляется только защищённому loopback capture; ссылка `${origin}/auth/local/reset#token=...`, TTL 30 минут. Новая просьба заменяет старую ссылку; доставки могут приходить в другом порядке, работает лишь последняя сохранённая ссылка.
- `POST /api/account/reset`: ровно `{token,password}`, общий limiter до bounded KDF. `200 {status:"password_reset"}` только после commit; 400 INVALID_RECOVERY при истёкшей/устаревшей/использованной ссылке, 422 INVALID_INPUT при неверном shape/password policy, generic 503 при недоступности/неизвестном результате commit. Уведомление о смене пароля после commit не содержит пароль/токен. Сбой уведомления логируется, но не откатывает пароль и не меняет успешный статус. Cookie не выдаётся и не очищается: в браузере может быть другой аккаунт. Прежние сессии владельца отозваны в БД; обычный вход с новым паролем выполняется отдельно. Автоматические повторные reset запрещены.

**Ограничение локальной доставки:** фоновые recover-задания не сохраняются и могут потеряться при перезапуске; после commit и недоставки нового письма прежняя ссылка уже заменена. Это не production queue/SMTP. Перед production обязателен отдельный durable delivery/outbox-инкремент, проверка восстановления и российских каналов доставки; in-process worker нельзя просто включить на сервере. Форма `/auth/local/reset` ещё не реализована.

Auth API и local auth-страницы имеют `Referrer-Policy: no-referrer` последним правилом Next config: общий header иначе перезаписывает route response. Development access logging исключает эти URL, включая отклонённые query credentials; остаются allowlisted JSON events. `local_auth_request` показывает status/code/duration, `local_auth_recovery_failed` — ошибку фоновой DB-работы, `local_auth_mail_failed` — сбой capture. `requestId` связывает ответ/работу/capture; `entryPoint` передаётся явно (`http` или `worker`). Ни один из них не обещает доставку; внешние proxy/access logs перед production также обязаны исключать чувствительные query/тела. Production-метрики/трейсы/alerts ещё не подключены.
- Login/session/logout/recover/reset на HTTP origin возвращают 503 HTTPS_REQUIRED до пула. Cookie всегда `__Host-blizhniy_session`, `Path=/; HttpOnly; Secure; SameSite=Lax`, без Domain, Max-Age не больше оставшегося абсолютного срока 8 ч; logout — Max-Age=0 и истёкший Expires. Не снимаем Secure ради localhost. На production этот локальный режим всё ещё запрещён.
- Все POST требуют точный Origin, фактический Host из конфигурации, `X-Blizhniy-Request: 1`, JSON, отсутствие query и cross-site Fetch Metadata. Не используем клиентские Forwarded headers для определения целевого Origin. **NextURL нормализует 127.0.0.1 в localhost**, поэтому именно Host + настроенный Origin, не внутренний URL.hostname, являются проверяемой границей. Body ≤4096 байт (считаем реальные байты, не только Content-Length), deadline 2 с. Ответы no-store/no-referrer/nosniff.
- Общий PostgreSQL limiter: фиксированное окно 15 минут, 60 запросов всего + 5 на canonical email, HMAC вместо plaintext. Счётчики не сбрасываются при рестарте; отказ БД — 503, лимит — 429/Retry-After 900. Это консервативная **локальная**, не production per-IP политика; production требует trusted proxy/per-IP и общих resource limits.
- Почтовый transport — только loopback capture HTTP, не SMTP. Ссылка `${origin}/auth/local/confirm#token=...`; фрагмент не попадает в access log/Referer. Письмо не уходит реальным получателям. Нулевой envelope при дубликате/неверном resend проходит тот же capture-вызов, чтобы не создавать раннюю ветку по наличию аккаунта. Capture authenticated HMAC-derived bearer, redirects запрещены, deadline 2 с, ожидается 204. Сбой логируется без payload, ответ остаётся 202; pending account можно подтвердить после password-gated resend.

Opt-in integration runner запускает свою PostgreSQL, свой Next.js **HTTPS** на динамическом loopback-порту, Chromium и свой in-memory capture без SMTP-forwarder/публичного inbox API. Генерирует собственный односуточный сертификат с SAN 127.0.0.1: Node проверяет CA/имя, Chromium допускает только этот SPKI, без глобального отключения проверки сертификатов. Ключи вне репозитория удаляются вместе с собственной fixture. `.env`/реальные SMTP ключи не читаются; данные синтетические, процессы и контейнер только собственные. Не используем legacy Supabase Mailpit. Нужен установленный Playwright Chromium; runner не скачивает браузер автоматически. Нельзя запускать одновременно с Next build: оба обновляют `.next`.

Форма `/auth/local` доступна только при той же проверенной локальной конфигурации; иначе 404. Старый `/auth` не изменён. `/auth/local/confirm` читает токен из fragment и удаляет его из URL; query token не принимается. Открытие ссылки не делает POST: подтверждение только по кнопке. Повторное открытие в той же вкладке не сохраняет прежний успех, токен не пишется в localStorage/sessionStorage. Письма доступны только внутри тестового capture, не в публичном inbox; это проверочный стенд, а не готовый почтовый сервис.

Наблюдаемость локального этапа: structured `local_auth_request` (requestId, entryPoint=http, allowlisted operation/status/code, durationMs) и `local_auth_mail_failed` с тем же ID; ID передаётся capture. Нет URL/body/email/IP/token/password в логах. Вопросы: какой guard отказывает, растёт ли 429/503, сработал ли capture, какова latency? Эти события дают request counts/error counts и распределение latency для локальной диагностики; полноценные production metrics/traces/alerts — ещё задача 11.

`/auth/local/login` — настоящая форма входа/смены аккаунта/выхода, доступная только на проверенном локальном **HTTPS** origin. Browser adapter не хранит токен или credentials, не следует HTTP redirects. После успешной мутации он отдельно проверяет cookie-сессию; при 503/timeout не показывает ложный успешный выход. При проверке/смене identity и поля очищаются; старый async-ответ не может вернуть прежнего пользователя. Другие вкладки получают только invalidation event, затем читают сервер; без BroadcastChannel проверка остаётся на focus/возврате видимости/bfcache. Роль на экране — лишь отображение, не полномочия для resource API. Сценарии с двумя аккаунтами, задержанным lookup, fault, блокировкой и мобильной/клавиатурной формой проверяются в Chromium, дополнительно к cookie probe. Legacy `/auth` и предметный кабинет пока не переключены. Следующий этап — одноразовое восстановление пароля с отзывом сессий. Нельзя включать этот локальный режим на публичном сервере вместо российского SMTP/production Auth.

Основания: [OWASP email verification](https://cheatsheetseries.owasp.org/cheatsheets/Email_Validation_and_Verification_Cheat_Sheet.html), [OWASP single-use tokens](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [PostgreSQL row locks](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE).

## Схема и откат

`database/migrations/0001-identity.sql` создаёт пустые `app.users`/`app.sessions`, ограничения и триггер, без Supabase Auth/Storage и без seed-аккаунтов. Все операции в одной транзакции с lock/statement timeout. Это одноразовая миграция: повторный запуск отказывает, не перезаписывая существующие таблицы. Общие PUBLIC-права отозваны; разделение migration/runtime ролей и точные grants обязательны перед production.

Migration credentials должны иметь CREATE на целевой БД для схемы `app` и права на её объекты; наличие CREATE на схеме `public` само по себе недостаточно. Эти права Timeweb нужно проверить отдельно перед применением, не повышая runtime-права автоматически.

`0001-identity.down.sql` блокирует обе таблицы и отказывается удалять непустые данные; без CASCADE. Для базы с аккаунтами rollback — возврат совместимого приложения или отдельная согласованная миграция, не сброс данных. На Timeweb 0001 установлена операторским bootstrap вместе с 0002–0005 (см. выше); down проверяется только на собственном локальном контейнере, на удалённой БД не запускался. Автомиграции при старте сайта нет.

Полная проверка: `npm run test:postgres:local` включает identity/registration, безопасный up/down, конкурентную смену пароля, одноразовое подтверждение/TTL после lock, права, ограниченные сессии и очистку; `node --experimental-strip-types --test tests/identity.test.mjs` проверяет примитивы и отказ при недоступности БД. Тесты только с синтетическими данными; никакие существующие аккаунты не переносятся. Не запускайте отдельный tsc параллельно Next build: сборка пересоздаёт `.next/types`; проверка типов выполняется после неё.

Старые `auth.users`, REST/RLS/Auth/Storage интеграции не переносятся слепо; см. [план](../tasks/plan.md) и [задачи](../tasks/todo.md). До достижения контрольных точек production остаётся неизменённым.

Основание: [параметры запросов](https://node-postgres.com/features/queries), [TLS](https://node-postgres.com/features/ssl), [транзакции](https://node-postgres.com/features/transactions), [подключение Timeweb](https://timeweb.cloud/docs/dbaas/postgresql/connect-to-database).
