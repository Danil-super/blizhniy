# F02: автоматическое обнаружение оснований компенсации

Локальная private TEST0050 поверх0049. Новый `worker.sweep()` объединяет обнаружение кандидатов, существующий intake0043/0045, очередь0049 и один финансовый tick0048. Ручного создания case больше не требуется в этом изолированном pipeline. Прежний `worker.tick()` по-прежнему обслуживает только готовую очередь и не требует схемы0050; его контракт не менялся.

## Ограниченный повторный обход

Cursor каждого TEST-магазина хранит нижний `(created_at,id)`, фиксированную верхнюю границу текущего прохода и время следующего. Один page посещает до25 исходных payment intents, штатный sweep10. LIMIT применяется до проверок оплаты/case; partial index `(merchant_shop_id,created_at,id)` охватывает только TEST application intents. Неоплаченные или уже рассмотренные записи также продвигают cursor, поэтому большие старые истории не превращаются в неограниченный anti-join.

Верхняя граница фиксируется при начале прохода, новые поступления не могут бесконечно отодвигать повтор старых записей. После конца cursor сбрасывается; новый цикл начинается не раньше чем через60s, с новой верхней границей. Так повторно рассматриваются waiting, временно busy/недоступные источники, поздняя capture/selection/closure и намерения, чей COMMIT пришёл позади cursor. Это не обещание возврата ровно в120h: задержка зависит от размера обхода, частоты вызова consumer и провайдера.

Timestamp microseconds сохраняются целиком внутри PostgreSQL, без преобразования cursor в JavaScript Date. Выбор page/CAS cursor — отдельная короткая READ COMMITTED транзакция с SKIP LOCKED; при неизвестном COMMIT список ID не передаётся intake. Пропущенная из-за сбоя порция возвращается в следующем цикле, без создания нового финансового ключа.

## Единственный источник права на выплату

SQL discovery выдаёт только ID кандидатов с локально подтверждённым capture без уже сохранённого case. Это не право вернуть деньги и не проверка непросмотра. Каждый ID проходит существующий `PostgresApplicationCompensationStore.claim`: payer/intent/order/work/application locks, оригинальные metadata/receipt/сумма/merchant и достоверные события просмотра, выбора и закрытия. Новая реализация политики, возрастной SQL-фильтр или вывод о непросмотре из отсутствия карточки не добавлялись.

Выход discovery содержит только счётчики scanned/skipped/claimed/waiting/ineligible/unavailable. Ошибка одного источника не запускает его SQL заново и не задерживает последующие ID; она учитывается как unavailable. Legacy_unknown также учитывается как unavailable для ручной сверки, а не как доказанный просмотр или обычный отказ в праве. Потеря intake COMMIT ACK может оставить уже принятый case и его атомарную задачу: финансовый worker сверяет именно эту сохранённую запись, а не ошибочный ответ intake. `claimed` означает подтверждённый case, включая параллельный идемпотентный повтор; это не счётчик перечисленных денег.

Unknown page COMMIT останавливает весь sweep до финансовой стадии. Ошибки отдельных source claims видны в результате sweep; consumer должен учитывать unavailable при наблюдении. Прямого DML cursor для worker нет, только фиксированный definer SELECT-function. Ни новых контактов/сумм из браузера, ни внешней передачи данных нет.
