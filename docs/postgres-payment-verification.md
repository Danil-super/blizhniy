# Сохранение подтверждённого состояния оплаты

Локальный этап L17 после [GET-reader](primary-yookassa-reader.md) и подготовки
заказа. Рабочая БД/роли/сайт не переключены. Реальные merchant запросы не
выполнялись. Ручное внешнее ревью, отложенное владельцем, не считается пройденным.

## Контракт и решение

`PostgresPaymentVerificationStore` — только доверенный серверный финансовый
компонент. Не HTTP API и не проверка прав пользователя: публичный маршрут не
должен принимать ID и вызывать его без отдельной авторизации. Для владельца
будет использоваться отдельный session-scoped order DTO. Constructor принимает
конфигурацию магазина; ID, сумма и metadata для сверки берутся из immutable intent,
а не из браузера или webhook. Сам webhook позже сможет инициировать authoritative
GET, но не подтвердить оплату своим payload.

`reconcile(id)` сначала короткой транзакцией проверяет исходный snapshot/hash и
наличие известного provider ID. Затем выполняет проверенный GET **вне SQL
транзакции**. В новой транзакции повторно читает те же привязки и блокирует
intent → order; обновляет verification и финансовый status заказа атомарно.
Другие финансовые writers должны соблюдать этот порядок. Ни POST, ни новый
ключ, ни публикация/исполнение, ни срок размещения здесь не создаются.

Одна строка `app.payment_verifications` относится к одному заказу и его точному
provider ID через два FK. Храним только status, необязательное исходное
captured_at и DB-время первого/последнего изменения. Это сводка, не полный журнал
всех ответов. Не добавляются карточные данные, контакты, полный payload либо
описание провайдера. UUID/состояние/времена относятся к финансовым данным уже
существующего намерения; назначение — сверка и последующее однократное исполнение.

Ожидание/блокировка средств дают order pending, только succeeded даёт финансовый
успех. Авторитетный canceled даёт failed и не выдаёт услугу. Задержанный pending
не отменяет succeeded/canceled и не понижает waiting_for_capture. Противоречащие
терминальные ответы или другое время списания — ошибка сверки без перезаписи
истории; нужен последующий операторский разбор, не новое автоматическое списание.
Существующий refunded не превращается обратно в succeeded; обработчик/доказательство
возврата пока не реализованы.

captured_at хранится **текстом** с исходной точностью до9 дробных знаков: SQL
timestamptz и JavaScript Date теряют часть точности. Отсутствующее время остаётся
NULL даже при финансовом успехе. Поздний проверенный ответ может заполнить его
один раз; повтор без времени не очищает его. Эквивалентные `.123Z` и `.123000000Z`
не переписывают первоначальные bytes, различие даже в1ns отклоняется.
Будущий fulfillment обязан отдельно проверить этот anchor и исходный срок;
NULL или старый capture не разрешают начать новый период от времени сверки.

Повтор с неизменным состоянием не переписывает verified_at/updated_at. UNKNOWN
COMMIT не объявляется успехом и не повторяется внутри метода: `read(id)` позволяет
прочитать committed результат без запроса провайдеру. Повторный reconcile безопасен
как GET той же оплаты, но readback не создаёт новый платёж.

## Миграция и выпуск

0021 добавляет таблицу, точный UNIQUE/FK provider binding и monotonic trigger;
первые20 SQL sources не меняются. Только opt-in `includePaymentVerification:true`,
без нового CLI apply, startup/deploy hook или grants. Down проверяется на пустой
таблице и отказывается удалять непустую историю. Операционный rollback — прежний
код с сохранением данных. Trigger не доказывает подлинность провайдера и не
защищает от SQL-owner: authoritative boundary выполняется доверенным компонентом.

Изолированная fixture-роль может сверять и менять только финансовый status,
но не пользователей/публикацию. Production роль и права требуют отдельного допуска.
До выпуска остаются retention/export/erasure и резервные копии финансовых ПД;
не выдумывается правовой срок и не включается произвольная очистка истории.
Также нужны fulfillment, dispatch/recovery UNKNOWN, webhook, UI/история/возвраты,
наблюдение и согласованный sandbox E2E. Полный перенос ещё не завершён.

## Проверки

Новые direct-import и PostgreSQL18 tests используют синтетический fetch и
собственный loopback container, не production/staging данные. Проверяются wrong
binding/merchant, missing provider link,404, pending/hold/canceled/succeeded,
missing/поздний/exact capture, конкуренция, отсутствие SQL lock при GET, rollback
обоих состояний, lost COMMIT/readback, FK/immutability/точечные права/down.
Инверсия проверки терминального конфликта сломала оба профильных теста; условие
восстановлено. Контрольная точка: native1546/1546 и PostgreSQL283/283, без
пропусков; whole lint0errors с одним прежним предупреждением. Отдельный статический
разбор не нашёл конкретного дефекта записи/конкуренции, но выявил недостающий
refunded regression и проверку дедлайна после каждой итерации barrier; оба
исправления включены в итоговый SQL-прогон. Это не заменяет внешнее ревью.
Production build завершён с exit0; staged Gitleaks не обнаружил секретов.

Общий прогон выявил старую timing-ошибку теста бюджета: остатки вычитали разные
консервативные round trips. Минимальное воспроизведение при неизменном anchor:
4918ms →4958ms; это не продление самого DB-дедлайна. После независимого разбора
добавлен bounded DB-clock barrier против **исходного** anchor, а все assertions
и пороги сохранены; дополнительно проверяется exact anchor после последнего
вызова. Окно POST и production authorizer не изменены.

Команды: `node --experimental-strip-types --test tests/bootstrap-postgres-integration.mjs`,
`npm test -- --test-concurrency=2`, `npm run check:types`, `npm run lint`,
`npm run build`, `npm run check:floor -- --base origin/main`, staged Gitleaks.
SQL-lock/точность сверены с PostgreSQL18 через Context7; статусы/captured_at — с
официальным контрактом ЮKassa. Runtime proof здесь — actual-source + локальная
настоящая БД, не пройденный merchant E2E и не production выпуск.
