# F02: очередь исполнения сохранённых компенсаций

Локальная0049 поверх0048. Это private TEST очередь для уже принятых неизменяемых оснований; не новое правило выплаты. Ручная БД сохраняет39 записей, production0033 не меняется. Worker/HTTP/системные службы и реальные provider-запросы не включаются.

## Обработка и восстановление

AFTER INSERT существующего case атомарно создаёт одну задачу с тем же ID оплаты и магазином. Старые cases обходятся по `(created_at,payment_intent_id)` с отдельным cursor каждого магазина и индексом; один batch читает не более100 записей, штатный tick50. Cursor продвигается и через уже существующие/завершённые задачи. Cases, чей COMMIT пришёл позади cursor, не теряются: их задача вставляется тем же AFTER-trigger внутри исходной транзакции. Исторические уже применённые0048 effects сразу получают completed, не забивая очередь.

Один explicit tick обслуживает не более одной задачи. Claim использует [FOR UPDATE SKIP LOCKED](https://www.postgresql.org/docs/18/sql-select.html), проверяет время БД и выдаёт новый nonce через gen_random_uuid на5 минут. Сетевых вызовов при удержании queue/financial locks нет. Неизвестный результат COMMIT enqueue/claim прекращает tick; автоматического SQL-повтора нет. После истечения lease другой worker получает новый nonce, прежний больше не может подтвердить задачу.

Перед началом обработки и возможным POST проверяется владение задачей. Дополнительный transaction-aware gate выполняется после прежних финансовых блокировок и до INSERT send attempt, затем аналогично до INSERT финансового effect. Он блокирует queue row и сверяет nonce/время в той же транзакции, поэтому ожидание user/intent/order locks не превращает старую lease в разрешение отправки. Ранний queue-only check завершается до финансовой транзакции; обратного queue→financial порядка нет. Валидный поздний ответ провайдера может сохранить прежний candidate/GET proof, но новый effect требует актуального допуска.

Исполнение использует0048 processor без смены request bytes/key, merchant или исходного окна23h55m. Повтор после неизвестного POST сохраняет единственную операцию. Pending откладывается с30s exponential backoff до1h; canceled блокирует задачу. Ошибка сохраняет только фиксированный processing_unavailable, без payload/контактов/секретов. Двенадцать processing claims — предел автоматического исполнения; отдельный заключительный read-only claim проверяет уже применённый effect прежде, чем выставить attempts_exhausted. Он не увеличивает счётчик и не обращается к провайдеру. Исходный финансовый предел12 send attempts не изменён.

Этот последний шаг важен при потере COMMIT ACK финансового эффекта именно на попытке12: деньги и уведомление могли уже сохраниться, хотя processor вернул ошибку. Нельзя оставлять такую задачу навсегда blocked. После сохранённого effect восстановление завершается без нового provider HTTP и без повторного уведомления. Finish использует CAS nonce/lease; его неизвестный COMMIT тоже не повторяется автоматически.

## Права и проверки

Queue/cursor таблицы закрыты для PUBLIC и прямого DML worker. Новый worker получает только EXECUTE фиксированных definer-функций; их тестовые grants существуют лишь в disposable fixture. Завершение completed требует сохранённого0048 effect. Scope фиксируется при создании TEST processor, IDs/лимиты/результаты проверяются также в TypeScript. Рабочие роли и guard-схемы не расширены.

RED подтвердил отсутствие очереди; отдельный RED воспроизвёл потерю финального effect ACK. Реальные PostgreSQL-сценарии проверяют оба lock-wait race, SKIP LOCKED, смену nonce, потерю claim/finish/effect ACK, pending/canceled, backoff/cap, поздний COMMIT позади cursor, scoped права и terminal-effect recovery. Мутация удаления transactional admission обнаружена, source восстановлен побайтно. Native input tests импортируют настоящий worker в поддерживаемом Node22. Независимое инженерное ревью завершено; дополнительную модель владелец пропустил.
