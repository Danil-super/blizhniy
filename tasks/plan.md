## Контракты и требования

1. Браузер вызывает только same-origin `/api/*`; секреты БД и пароли не попадают в bundle. Подключение PostgreSQL — через параметризованные запросы, небольшой пул, проверку цепочки CA и имени сервера. Без скрытого fallback к Supabase, PG* окружению или demo-данным.
2. Авторизация — серверные сессии с HttpOnly/Secure/SameSite cookies; проверки origin/CSRF для изменений, ограничение попыток, подтверждение email и одноразовое восстановление. Используем проверенные криптографические примитивы, не собственные алгоритмы. Администратор назначается вне клиентского ввода.
3. Владелец/роль проверяются на каждом защищённом запросе. Публичный ответ не содержит скрытых контактов, точного приватного адреса, токенов или хешей. Ограниченные runtime-права и защита БД дополняют API; клиент не может подключаться к PostgreSQL напрямую.
4. Файл: проверка типа/байтов/размера, случайное имя, привязка к владельцу, отсутствие исполнения и перечисления каталогов. Приватные файлы не доступны по публичной ссылке; необратимые удаления только по проверенным ID и принадлежности.
5. Оплата: цена/срок фиксируются на сервере до обращения к провайдеру; успех подтверждается провайдером, исполнение атомарное и идемпотентное. Никаких реальных списаний в разработке. Не теряем уже проверенные инварианты SQL-лаборатории.
6. Переход: сначала локальные отрицательные/положительные тесты, затем российская БД и стенд, резервирование и восстановление, затем переключение. Старый зарубежный backend нельзя включать автоматическим rollback после открытия нового контура.

- Node.js 22 (как в CI). На этой машине проверенный бинарник: `/home/danil/.cache/blizhniy-node22-pxyRwP/node`; npm 10.9.9 из существующего кэша. Это локальные инструменты, не пути production.
- Полные тесты: `node --experimental-strip-types --test tests/*.test.mjs tests/*.test.cjs scripts/test-*.mjs`.
- Типы: `node node_modules/typescript/bin/tsc --noEmit`; lint: `npm run lint`; build: `npm run build`.
- SQL-интеграции новой схемы: отдельная opt-in команда с локальной БД, явным подтверждением цели и собственной очисткой. Обычный тестовый запуск не читает production .env и не обращается к удалённым БД.
- Стиль: TypeScript, явные типы/ошибки; например `await db.query('select id from app.users where id = $1', [userId])`. Имена таблиц/колонок не конструируются из пользовательского ввода.

## Границы полномочий

Всегда: тест сначала, неизменённые бизнес-инварианты, проверка секретов перед коммитом, короткие проверенные этапы. Не добавляем новую инфраструктуру/платные сервисы без отдельного согласования; не повышаем runtime-права и не меняем рабочие секреты автоматически. 10.10 владелец явно разрешил использовать прежний пароль для подготовки БД в разработке; он не сохраняется в Git/журналах и меняется до пользовательского production. Это не препятствует разработке, но не заменяет разделение migration/runtime credentials.

Не делаем: удаление старых данных, массовый reset, отключение TLS/RLS/ownership ради запуска, удаление чужих контейнеров, пуш незавершённого cutover в main с автоматическим деплоем.

## Риски и контрольные точки

- Удаление Auth/REST/Storage — полноценная миграция, не замена URL. Проверяем каждый предметный сценарий и все прямые браузерные вызовы.
- БД проверена на 18.6, прежние локальные тесты — на 17. Схема и права проходят тесты на целевой major-версии до cutover.
- Пул и хеширование паролей могут исчерпать 2 ГБ VPS: ограничиваем параллелизм, измеряем, сборку не совмещаем с нагрузкой.
- Фотографии и БД резервируются отдельно; SQL dump не содержит файлы. Одна копия на том же VPS не считается независимым резервом.
- VPS сейчас не подключён к приватной сети БД. До её настройки TLS + allowlist; не считать адрес 192.168.0.4 достижимым без проверки сети.
- SMTP, CAPTCHA, карты и мониторинг проверяются отдельно на передачу/хранение персональных данных. Размещение в РФ само по себе не является юридическим заключением.

Контрольные точки: соединение/транзакции → идентификация двух пользователей → каталог/фото/черновик → платежи/права → полная сборка/восстановление/российский стенд → согласованный cutover.

Статический Code Graph использован для инвентаризации и поиска payment-компонентов. Его отрицательные результаты **не считаются доказательством отсутствия зависимостей**: `payment-store.ts` показан без consumers, хотя прямые импорты есть в provider, confirm, кабинетных и admin API. Связи через `@/` и helper-вызовы дополнительно проверяются исходниками и runtime network trace. В этой работе не проводились полноценный пентест, новый UX-аудит браузером или нагрузочный тест.

### Очерёдность и результаты этапов

1. **Основа релиза (L01–L04, L21):** согласовать перечень функций первой версии и критерии; подготовить изолированный российский staging, ограниченную роль БД, секреты и сеть; измерить текущие показатели; убрать сборку с рабочего VPS. Пока все существующие публичные разделы входят в объём запуска. Уменьшение объёма/скрытие разделов — только по решению владельца, не молча.
2. **Рабочая авторизация и первый пользовательский сценарий (L05–L10):** production SMTP с подтверждением/восстановлением, durable delivery, новые cookie sessions и кабинет; закрыть необходимые media/recovery/cleanup задачи этапа 6; подключить фото, каталог и обычные объявления. Контрольная точка: два настоящих тестовых пользователя на российском staging, чужие данные недоступны, черновик и фото переживают restart/deploy.
3. **Остальные разделы (L11–L16):** вакансии, заказы, специалисты, ярмарка, реклама; затем отклики, бронирования, уведомления и рабочая админка. Каждый тип отдельно проходит весь путь schema → API → UI → права. Неработающий платёж специалистов не объявлять готовой функцией. Публичные вакансии/заказы не содержат скрытых контактов ни в HTML/RSC, ни в JSON, метаданных и кеше.
4. **Деньги и сроки услуги (L17–L20):** перенести проверенные payment invariants в plain PG; фиксировать цену/срок на сервере, подтверждать провайдера, исполнять один раз, восстанавливать неизвестные результаты; проверить отмену/возврат/чек, истечение размещения и фоновые задания. Контрольная точка: реальный sandbox провайдера, без списаний и без production entitlement.
5. **Безопасность, приватность и эксплуатация (L22–L25):** полный обзор нового контура, независимые негативные тесты и безопасный DAST на staging; реальные backup/restore БД и файлов, privacy export/deletion, журнал действий и оповещения. Эти проверки проектируются с начала работ, не добавляются только в конце.
6. **Удобство и скорость (L26–L28):** браузерная матрица всех критических путей, мобильные устройства, доступность, понятные статусы/ошибки/стоимость, отсутствие потери черновика и повторной оплаты; нагрузочные замеры; проверка поиска/SEO без индексации приватных страниц. Исправления отдельными небольшими задачами с воспроизводимым тестом.
7. **Переключение и запуск (L29–L30):** российский staging проходит допуск; backend переключается по runbook, обращения к Supabase прекращаются, старые secrets/preview закрываются без удаления исторических доказательств. Затем ограниченная группа пользователей и 48–72 часа наблюдения; только после прохождения критериев — продвижение и массовый доступ. Процентные canary для несовместимых БД не смешивают два хранилища: бета использует только новый российский контур.

Операционная подготовка, юридическая проверка документов и дизайн сценариев могут выполняться независимо от предметных repositories. Миграции, общий auth contract и переключение должны быть последовательны. Это описание зависимостей, не запуск параллельных агентов.

### Предлагаемые критерии допуска

Числа ниже — **цели**, не уже достигнутые метрики или включённые CI gates. L01 формализует их в `CONSTRAINTS.md`, указывая реальные команды, владельца и место запуска; отсутствующий инструмент сначала подключается, а не объявляется проверкой. Покрытие проекта сейчас не измерено: 997 тестов не равно проценту покрытия.

- Нет открытых P0/P1: утечек, потери данных, неверных списаний/сроков, обходов прав и блокировки основных сценариев. P2 с влиянием на права/деньги тоже блокирует запуск. Остальные P2 имеют владельца, срок и согласованный остаточный риск.
- Все критические E2E сценарии проходят на **новом** российском backend, включая два аккаунта, администратора, restart, медленную сеть, потерю ответа и повтор webhook. Native, PG18 integrations, browser, types/lint/build и scans зелёные; тесты/защиты не отключаются для получения зелёного результата. Прежнее lint warning разобрать, не подавлять.
- Нет неисправленных эксплуатируемых Critical/High в runtime, build или deploy. Полный dependency audit рассматривается отдельно от production-only; подтверждённые false positives/обходные меры имеют доказательство и дату пересмотра, а не просто ignore. Coverage изменённой логики — предлагаемая цель ≥80%; финансовые/ownership/TTL ветки дополнительно имеют негативные и конкурентные тесты. Измерение и guard от ослабления checks — L01/L23.
- Нет обращения сайта к Supabase Auth/REST/Storage или неутверждённому получателю ПД; нет privileged секретов в browser bundle, Git, CI artifacts или логах. Ограниченный runtime не делает DDL, не назначает роли и не меняет бюджет напрямую.
- На критических страницах нет serious/critical axe findings; вручную проверены клавиатура, focus, labels, экранный диктор, 200% zoom. Целевая доступность — [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/); автоматический axe сам по себе не доказывает соответствие.
- Цели производительности: LCP ≤2.5 с, INP ≤200 мс, CLS ≤0.1 на p75 отдельно для mobile/desktop ([Web Vitals](https://web.dev/articles/vitals)). До появления field data — воспроизводимые lab/interaction замеры на staging; Lighthouse не измеряет настоящий field INP. После беты — RUM в РФ, без ПД. Bundle baseline фиксируется и не растёт без объяснения.
- Предварительный профиль нагрузки — 100 одновременно активных пользователей, не 100 RPS; 30 минут устойчивой смеси просмотра/поиска/кабинета/записи, затем всплеск и отдельно auth/upload limits. Ожидаемые 4xx/429 учитываются отдельно от 5xx. Предлагаемые пределы: неожиданные 5xx <0.5%, p95 обычных read API ≤800 мс, write API ≤1.5 с, auth ≤2 с без времени SMTP/провайдера; нет OOM, роста RSS/очередей, исчерпания пула и потери данных. Профиль и пределы согласовать после baseline, не понижать ради прохождения. Платежи не нагрузочно тестируются реальными деньгами.
- Проверенное независимое восстановление БД **и** файлов. Предлагаемые RPO ≤1 час, RTO ≤4 часа — подтвердить возможностями тарифа и замером; сбой/восстановление финансовой записи требует сверки с провайдером, не слепого restore поверх новых платежей. Снимки согласованы с метаданными, сроки хранения и повторное удаление после restore документированы.
- Российские backups/logs/mail/staging и внешние интеграции проверены; TLS/site/DB expiry, availability, память/диск/пул, pending payments и delivery backlog имеют оповещения и ответственного. Независимое оповещение при отказе самого VPS. После cutover rollback не возвращает зарубежный backend.
- На бете 48–72 часа нет P0/P1; обращения обработаны, critical flows проверены, доступность ≥99.9% за окно по выбранной частоте probe. Это пробный допуск, не доказанный месячный SLA. Для эксплуатации предлагается SLO 99.9% за 30 дней и политика error budget.

### Персональные данные и юридические решения

До запуска подтвердить у провайдера регион основной БД, реплик, снапшотов и резервов, а не только IP/город VPS. Составить реестр полей/целей/доступа/сроков и получателей: SMTP, CAPTCHA (сейчас Turnstile), карты, аналитика, мониторинг, платёжный провайдер. Требование российских серверов не отменяет отдельной оценки внешних передач. Новые платные сервисы и замена интеграций не подключаются без согласования.

Владелец и профильный специалист утверждают оператора/реквизиты, политику, согласия и их версии, оферту/условия размещения, обработку жалоб, privacy export/deletion/retention, применимость уведомлений регулятору, чеков/кассы/НДС и возвратов. Размещение на двух российских серверах не является юридическим заключением. Прежний экран заявки на удаление не заменяет фактическую обработку данных. Маркетинговые согласия не объединяются автоматически с необходимыми документами регистрации.

### Как сократить время без снижения проверок

- Выполнять законченные вертикальные сценарии; после каждого отчёт из четырёх фактов: commit, что работает, где проверено (local/staging/VPS/DB), что блокирует следующий шаг. Не считать количество новых модулей прогрессом запуска.
- Существующие реализации/регрессии переиспользовать; дополнительную абстракцию вводить только под проверенный сценарий. L01 утверждает объём первой версии; несогласованное расширение backlog не делает запуск ближе.
- Сборка и тяжёлые scans в CI, на VPS — совместимый проверенный artifact и короткие smoke checks. Не передавать ПД/DB secrets в GitHub build; проверить native Sharp/Node/Linux ABI и равенство runtime/build config. Если артефакт несовместим, не обходить checks: выбрать совместимый builder.
- Короткие проверки изменённого пути выполняются при разработке, полный suite/SQL/E2E — на контрольной точке и перед релизом. Не повторять один полный suite только для уже измеренного coverage. Нет blanket skip/ignore, force audit fix и destructive reset.
- Инженерная оценка срока появляется после L01–L04 и первого полного сценария L05–L10: нынешний локальный прогресс не даёт честного календарного срока всего запуска.

Ближайший результат реализации после согласования: российский staging, production-safe авторизация и работающий путь «регистрация → подтверждение → кабинет → фото → черновик объявления», затем sandbox checkout. Текущий запрос завершает **планирование**, а не эти работы.
