# План: БЛИЖНИЙ без Supabase

## Условия и статус

Архитектура одобрена владельцем 09.10.2026; этим же запросом разрешено составить план и начать реализацию. Работа ведётся в существующей папке проекта, без новых worktree и копий репозитория. Задачи и доказательства выполнения — в [todo.md](todo.md).

- Два российских сервиса: VPS сайта и управляемая PostgreSQL Timeweb. Supabase не используется в целевом приложении: ни облако, ни self-hosted стек, ни SDK.
- VPS `217.149.30.35`: проверены 2 vCPU, 1967 МБ RAM, диск 40 ГБ, около 17 ГБ свободно. Есть другие процессы; их не останавливаем и не удаляем.
- БД `37.252.20.119`, `default_db`: проверены PostgreSQL 18.6, пустая база, TLS verify-full. Тариф, регион копий и настройки резервирования ещё требуют подтверждения в панели провайдера.
- Чистый старт: справочники и тарифы из проверенного источника; старые аккаунты, публикации, платежи и фото не переносим. Старую БД не удаляем.
- До готовности замены действующий сайт не переключаем; новые PostgreSQL-модули пока не подключаем к production-маршрутам. Наличие старого кода на промежуточном этапе не означает, что отказ от Supabase завершён.

## Модули и порядок

`database → identity → catalog → media → publications → payments → operations → cutover`.

Все модули работают в одном Next.js backend на VPS. В PostgreSQL хранятся аккаунты, хеши паролей, хеши сессионных/одноразовых токенов, профили, контакты, согласия, справочники, публикации, отклики, бронирования, платежи и метаданные файлов. Файлы находятся в постоянном каталоге VPS вне релизов; стартовая квота 5 ГБ, независимые копии в РФ. Карточные реквизиты не собираем.

## Контракты и требования

1. Браузер вызывает только same-origin `/api/*`; секреты БД и пароли не попадают в bundle. Подключение PostgreSQL — через параметризованные запросы, небольшой пул, проверку цепочки CA и имени сервера. Без скрытого fallback к Supabase, PG* окружению или demo-данным.
2. Авторизация — серверные сессии с HttpOnly/Secure/SameSite cookies; проверки origin/CSRF для изменений, ограничение попыток, подтверждение email и одноразовое восстановление. Используем проверенные криптографические примитивы, не собственные алгоритмы. Администратор назначается вне клиентского ввода.
3. Владелец/роль проверяются на каждом защищённом запросе. Публичный ответ не содержит скрытых контактов, точного приватного адреса, токенов или хешей. Ограниченные runtime-права и защита БД дополняют API; клиент не может подключаться к PostgreSQL напрямую.
4. Файл: проверка типа/байтов/размера, случайное имя, привязка к владельцу, отсутствие исполнения и перечисления каталогов. Приватные файлы не доступны по публичной ссылке; необратимые удаления только по проверенным ID и принадлежности.
5. Оплата: цена/срок фиксируются на сервере до обращения к провайдеру; успех подтверждается провайдером, исполнение атомарное и идемпотентное. Никаких реальных списаний в разработке. Не теряем уже проверенные инварианты SQL-лаборатории.
6. Переход: сначала локальные отрицательные/положительные тесты, затем российская БД и стенд, резервирование и восстановление, затем переключение. Старый зарубежный backend нельзя включать автоматическим rollback после открытия нового контура.

## Структура и команды

- `src/lib/`: PostgreSQL, серверная идентификация и предметные репозитории; `src/app/api/`: HTTP-граница; `tests/`: native node:test; `scripts/`: явные диагностика/миграции; `database/`: новая проверенная plain-PostgreSQL схема, без слепого повтора старых Supabase SQL.
- Node.js 22 (как в CI). На этой машине проверенный бинарник: `/home/danil/.cache/blizhniy-node22-pxyRwP/node`; npm 10.9.9 из существующего кэша. Это локальные инструменты, не пути production.
- Полные тесты: `node --experimental-strip-types --test tests/*.test.mjs tests/*.test.cjs scripts/test-*.mjs`.
- Типы: `node node_modules/typescript/bin/tsc --noEmit`; lint: `npm run lint`; build: `npm run build`.
- SQL-интеграции новой схемы: отдельная opt-in команда с локальной БД, явным подтверждением цели и собственной очисткой. Обычный тестовый запуск не читает production .env и не обращается к удалённым БД.
- Стиль: TypeScript, явные типы/ошибки; например `await db.query('select id from app.users where id = $1', [userId])`. Имена таблиц/колонок не конструируются из пользовательского ввода.

## Границы полномочий

Всегда: тест сначала, неизменённые бизнес-инварианты, проверка секретов перед коммитом, короткие проверенные этапы. Не добавляем новую инфраструктуру/платные сервисы без отдельного согласования; не повышаем runtime-права и не меняем рабочие секреты автоматически. Пароль БД, опубликованный в чате, должен быть заменён до production; новый передаётся вне чата/Git.

Не делаем: удаление старых данных, массовый reset, отключение TLS/RLS/ownership ради запуска, удаление чужих контейнеров, пуш незавершённого cutover в main с автоматическим деплоем.

## Риски и контрольные точки

- Удаление Auth/REST/Storage — полноценная миграция, не замена URL. Проверяем каждый предметный сценарий и все прямые браузерные вызовы.
- БД проверена на 18.6, прежние локальные тесты — на 17. Схема и права проходят тесты на целевой major-версии до cutover.
- Пул и хеширование паролей могут исчерпать 2 ГБ VPS: ограничиваем параллелизм, измеряем, сборку не совмещаем с нагрузкой.
- Фотографии и БД резервируются отдельно; SQL dump не содержит файлы. Одна копия на том же VPS не считается независимым резервом.
- VPS сейчас не подключён к приватной сети БД. До её настройки TLS + allowlist; не считать адрес 192.168.0.4 достижимым без проверки сети.
- SMTP, CAPTCHA, карты и мониторинг проверяются отдельно на передачу/хранение персональных данных. Размещение в РФ само по себе не является юридическим заключением.

Контрольные точки: соединение/транзакции → идентификация двух пользователей → каталог/фото/черновик → платежи/права → полная сборка/восстановление/российский стенд → согласованный cutover.
