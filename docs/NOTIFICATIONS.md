# Уведомления БЛИЖНИЙ

## Принципы

- In-app уведомления в колокольчике являются базовым каналом для всех пользователей кабинета.
- Email используется для важных транзакционных событий: вход/восстановление доступа, оплата, публикация, модерация, ответы по заявкам.
- Push включается только после явного действия пользователя в настройках. Автоматический browser prompt при входе на сайт не показываем.
- SMS оставляем только для подтверждения телефона и критичных сценариев, потому что это дорогой канал.
- Маркетинговые рассылки отделяем от транзакционных уведомлений и включаем только после отдельного согласия.

## Гость

Гость не получает персональные серверные уведомления. В шапке показываем:

- приглашение войти или зарегистрироваться;
- пояснение, что личные события по оплатам, публикациям и заявкам привязываются к аккаунту;
- локальные демо-события только в текущем браузере, пока сайт работает без production-БД.

События, которые требуют личной истории, должны сначала вести на авторизацию: оплата, публикация, кабинет, отклики, заявки.

## Авторизованный пользователь

Пользователь получает уведомления по категориям:

- `payment`: платеж создан, ожидает подтверждения, успешно прошел, не прошел;
- `publication`: опубликовано после оплаты, снято с публикации, возвращено без повторной оплаты, удалено, продано;
- `booking`: новая бронь, ответ владельца, подтверждение или отказ;
- `message`: будущие сообщения между пользователями;
- `system`: настройки профиля, технические события кабинета;
- `security`: вход, смена email, восстановление пароля, смена телефона.

В кабинете пользователь управляет категориями и будущими каналами:

- брони и заказы;
- сообщения;
- оплаты;
- статусы публикаций;
- системные события;
- email-уведомления;
- push-уведомления после отдельного разрешения браузера.

## Админ

Админу нужны отдельные уведомления:

- новая оплаченная публикация;
- платеж не найден при webhook ЮKassa;
- ошибка оплаты или отмена;
- жалоба на объявление;
- новая заявка на ярмарку;
- ручная смена статуса публикации.

После подключения БД админские уведомления должны храниться отдельно от пользовательских и проверяться ролью `admin`.

## Production-схема БД

Минимальный набор таблиц для Supabase:

- `notifications`: `id`, `user_id`, `category`, `title`, `message`, `tone`, `action_href`, `read_at`, `created_at`, `dedupe_key`, `metadata`.
- `notification_preferences`: `user_id`, `category`, `in_app_enabled`, `email_enabled`, `push_enabled`.
- `push_subscriptions`: `id`, `user_id`, `endpoint`, `p256dh`, `auth`, `user_agent`, `created_at`, `revoked_at`.
- `notification_deliveries`: `id`, `notification_id`, `channel`, `status`, `provider_id`, `error`, `sent_at`.

Для RLS:

- пользователь видит только свои уведомления;
- пользователь меняет только свои настройки;
- push subscriptions доступны только владельцу;
- админские уведомления доступны только роли `admin`.

## Email

Перед включением email на домене нужно настроить SPF, DKIM и DMARC. Для транзакционных писем можно использовать Resend через Supabase Edge Functions или серверный API на VPS.

Обязательные письма:

- подтверждение email;
- восстановление пароля;
- платеж создан или ожидает подтверждения;
- оплата прошла и публикация включена;
- платеж отменен или не прошел;
- публикация снята/восстановлена;
- ответ по заявке или брони.

Маркетинговые письма и дайджесты должны иметь отдельную настройку согласия и отписку.

## Web Push

Push требует HTTPS, service worker, VAPID keys и отдельную подписку браузера. Permission prompt показываем только по клику в настройках, когда пользователь понимает ценность уведомлений.

Поток:

1. Пользователь включает `Push` в кабинете.
2. Клиент проверяет поддержку `Notification`, `serviceWorker`, `PushManager`.
3. После клика регистрируется service worker и запрашивается разрешение.
4. Подписка сохраняется в `push_subscriptions`.
5. Сервер отправляет push только по включенным категориям.
6. Если push endpoint возвращает ошибку удаления, подписка помечается `revoked_at`.

## Что реализовано сейчас

- Единый локальный реестр in-app уведомлений: `src/lib/site-notifications.ts`.
- Колокольчик показывает гостевое состояние, in-app уведомления, старые локальные брони и настройки каналов.
- Платежный flow создает уведомления по созданию и подтверждению платежа.
- Личный кабинет создает уведомления по снятию/возврату публикации, продаже, удалению и сохранению настроек.
- Настройки профиля расширены категориями уведомлений и флагами email/push.
