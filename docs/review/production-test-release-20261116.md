## TEST-приёмка после внедрения

Сначала проверить режим и допуск существующего TEST-магазина/аккаунта без
печати секретов. Автоматизация не использует сохранённый production пароль
пользователя и не создаёт фиктивные публикации для индексации.

Пользовательский путь для существующего разрешённого аккаунта: подтверждённый
телефон → заполнение объявления/сохранение фотографий → одна подготовка оплаты
→ ЮKassa TEST → success/return → серверное подтверждение → статус в кабинете.
В действующем production TEST тестовая покупка не равна публичной платной
публикации; проверяем фактическое поведение включённого режима.

Проверить отмену, reload/back/повтор return, задержку статуса и неизменность
суммы/срока/истории. Перед новым платежом при неизвестном результате сначала
сверить старый. Для чтения чужого объекта должен быть отказ. Ручной ввод
тестовой карты пользователем допустим, итог принимается по серверному статусу,
а не только по сообщению браузера.

Вакансии/заказы/отклики/продления/возвраты, зависящие от пока локального
runtime, не выдаём за проверенные на production. Их включение требует точного
следующего rollout-плана: поддерживаемая схема, минимальные права, service
admission, TEST-owner gate и обратимость. Локальный simulator в prod не переносим.

Основание отдельных решений: CONSTRAINTS.md запрещает новые исключения без
согласования владельца и доказательства риска; сам guard уже ранее просмотрен.
Этот документ не объявляет весь аудит, реальную TEST/fiscal приёмку,
нагрузку или эксплуатационные проверки двух российских серверов завершёнными.
