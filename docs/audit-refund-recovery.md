## Контракт

- Только уже подготовленный полный TEST-возврат с anchor и хотя бы одной сохранённой попыткой отправки. Одна подготовка без попытки не даёт полномочия присоединить сторонний возврат.
- Для размещения обязательно исходное неизменяемое решение0042; для отклика — решение0043/0045 с фискальным режимом исходной оплаты. Другой действующий администратор может сверить старое решение.
- До сети сохраняется неизменяемая запись `requested`. Один UUID действия связан с одним оператором, причиной, операцией и кандидатом. Отдельные `pending/succeeded/canceled` фазы дописываются по проверенному журналу, исходная запись не заменяется.
- Повторно используется существующий GET reader/journal. Проверяются исходная оплата, TEST-магазин, metadata, полная сумма, время, receipt schema и отсутствие конфликтующего candidate/link. Dispatcher не вызывается: новых POST, ключей, reservation, anchor и send attempts нет.
- GET разрешён после истечения исходных23h55m, но окно и лимит12 попыток сохраняются. Противоречивый результат, missing proof, неверный магазин или metadata требуют отдельного разбора и не объявляются успехом.
- Успех применяет существующий0040/0048 effect ровно один раз. Финальный effect, результат аудита и завершение compensation job находятся в одной транзакции. Отмена возврата сохраняет исходную оплату; pending не сбрасывает очередь/лимиты.
- Завершённый повтор того же действия читает локальный terminal proof и audit: временная недоступность API не скрывает уже выполненный результат. Потеря ACK не запускает автоматический SQL retry и не создаёт другую операцию.

## Блокировки и полномочия

Каждая транзакция авторизует администратора заново, включая запись GET-доказательства после сети. Порядок: admin user/session → payer NOWAIT → intent/order → очередь. NOWAIT на втором пользователе предотвращает встречное ожидание двух администраторов-плательщиков. Сеть не удерживает транзакцию.

SQL самостоятельно выводит actor/source/time, запрещает изменение/удаление/truncate и проверяет сессию после financial lock wait и после queue lock wait. Вызов через factory дополнительно делает финальную проверку сессии перед COMMIT. Narrow fixture operator не может создавать отправки, изменять сумму/статус оплаты, сбрасывать очередь или подставлять исход результата. Существующие worker-права и старые миграции не изменены.
