# Настоящий TEST-магазин: закрытая техническая проверка

20.10.2026 владелец разрешил TEST-запросы в ЮKassa на синтетических данных,
без реальных списаний. Это не разрешение LIVE или публичного TEST-checkout.

## Граница инструмента

`createPrimaryTestPaymentProbe` — явный операторский инструмент, не HTTP API,
не пользовательский checkout и не автоматический daemon. В web routes он не
импортируется. Новых DDL, grants, зависимостей и изменений Auth/SSH нет.
Оператор использует существующие доверенные полномочия разово; credentials
оператора не передаются веб-процессу и не записываются в артефакт.

Четыре заранее сохранённых UUID связывают точный order/owner/listing/creationKey.
Перед сетью проверяются канонический TEST-магазин, immutable binding, текущая
approved revision, неоплаченный draft без дат/исполнения, заблокированный
синтетический владелец с точным техническим email и без каких-либо сессий.
Подмена любого из этих условий отказывает до создания anchor и merchant I/O.
Заблокированный владелец здесь — намеренная изоляция технической записи:
этот инструмент нельзя использовать как замену session/owner admission.

Чек содержит только технический адрес `checkout-<UUID>@example.com`, одну
исходную позицию и TEST vat_code=1. Реальные адреса/телефоны/ФИО не отправляются.
Это не выбор НДС/кассовой схемы для LIVE. Точная return_url ведёт на исходный
номер заказа своего сайта; receipt и исходные байты после сохранения не меняются.

Диспетчер сохраняет исходное окно/key, проверяет ответ провайдера и связывает
один provider ID. Повтор после известного ID делает только GET; отдельный
`reconcile` никогда не создаёт платёж. Авторитетная GET-сверка обновляет
финансовый журнал. **Fulfillment, очередь, публикация и выдача услуги не
вызываются**, даже если TEST-платёж станет succeeded.

## Проверка настоящего магазина

С российского VPS выполнен authenticated GET магазина с существующим TEST-ключом.
Рабочая конфигурация сайта осталась prepare-only/test; постоянный worker,
новый webhook и LIVE не включались.

Реальный API выявил требования, которых не доказывали локальные fixtures:
заказ без чека получил400 `receipt`, два технических адреса были отвергнуты400
`receipt.customer.email`. Исходные заказы/bytes сохранены, ошибки не выданы за
успешную оплату. Для исправленных технических данных создавались **новые
закрытые targets**, а не новый ключ того же неизвестного платежа или изменение
immutable history. Документация API указывает Email maxLength254; отказ на
конкретных технических адресах не выдаётся за доказанный общий лимит64.

В08:34:12UTC создан один настоящий TEST-платёж199.00RUB: POST → строгая проверка
shop/test/amount/metadata/confirmation → immutable link → независимый GET →
pending в рабочем журнале. В08:34:40UTC повтор операторского dispatch выполнил
только GET/GET того же provider ID, без POST или второго платежа.
Provider URL/UUID, ключи и исходные ответы не записываются в Git/CI/аудит.
Private fixtures/proofs остаются вне репозитория, резервные операторские
свидетельства — на российском VPS в root-only каталогах.

В изолированном Chromium открыта проверенная hosted confirmation URL. Страница
явно показывала TEST; использована официальная синтетическая карта без3DS,
автосписания/дополнительная квитанция не включались, реальных карт и личного
профиля браузера не было. ЮKassa показала успешную оплату. В08:37:31UTC отдельный
GET через настоящий verifier подтвердил succeeded и сохранил его в рабочем
журнале. Закрытый draft, blocked owner и отсутствие fulfillment/queue сохранились.
Это проверка provider checkout, а не пользовательского возврата/сессии сайта.

## Проверки и оставшееся

Native tests проверяют отказ LIVE, чужой/активный/изменённый/исполненный target,
синтетический receipt, URL и GET-only replay. Owned PostgreSQL18.6 проверяет
настоящие joins/сессии/immutable store/verification, terminal replay и отсутствие
публикации/queue. Удаление проверки blocked owner поймано mutation-тестом;
исходное условие восстановлено. Runtime40-column policy не расширяется.
Итог: native1610/1610, PostgreSQL330/330, без skips; types/lint без ошибок,
одно прежнее lint warning. Build успешен. Production-only audit0; полный
audit по-прежнему9(7high/2moderate) в build/dev, без нового исключения или
изменения зависимостей. Проверки GitHub и конкретный deploy фиксируются отдельно.

Это ещё **не сквозная пользовательская оплата сайта**. Отдельно остаются
защищённый dispatch admission/API и кнопка, безопасное TEST/LIVE разделение
исполнения, webhook/worker supervision, остальные услуги, возвраты и LIVE
фискализация. Полный перенос/L17–L20 не отмечаются завершёнными.

Основания: [API](https://yookassa.ru/developers/api),
[тестирование и официальные тестовые карты](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing).
