Patch применён к runtime/tests/guard; точные байты и SHA сверены.

## Проблема и предлагаемый результат

При всплеске25 одновременных поисков действующий runtime допускает два,
остальным немедленно отказывает. Кандидат оставляет ровно два физических
reader и существующий pool max5, но добавляет FIFO максимум32 ожидающих.
Ожидание не дольше750ms и входит в общий бюджет5000ms. Переполнение/истечение
по-прежнему возвращает ошибку; пустая выдача не подменяет отказ.

Самостоятельно исправленная часть — исходный абсолютный monotonic deadline
передаётся runtime → search store → readTransaction. Прежняя относительная
передача незаметно запускала новый отсчёт после преобразования входа.
Перед новым SQL проверяется оставшийся срок; уже истёкший дедлайн не начинает
checkout. Допуск занят до фактического завершения initializer/read scope,
даже если HTTP-ответ уже завершился ошибкой; повтор cleanup не освобождает
чужой слот. Обычные write-транзакции и вызовы без абсолютного deadline не
получают нового поведения. Node timers не обещают точного времени доставки
ответа при заблокированном event loop — обещания «ответ всегда ровно до5s» нет.

## Объём решения владельца

Patch заменяет только:

1. `src/lib/production-search-runtime.ts` — проверенный кандидат очереди.
2. `tests/public-search-contract.test.mjs` — шесть ожиданий немедленного
   отказа в четырёх тестах заменяются проверкой ожидания и отказа через750ms.
   Новая проверка явно подтверждает, что до истечения ожидания нет результата.
   Все прежние проверки two-reader, SQL/config calls, invalid input,
   duplicate cleanup, позднего initializer и общего срока сохраняются.
3. `scripts/check-quality-floor.mjs` — одна точная пара SHA256 всего
   указанного тестового файла в существующем механизме reviewed artifacts.
   Ни алгоритм guard, ни другие исключения не изменяются.
