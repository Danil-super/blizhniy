## Поведение

Анкета сохраняется в существующей таблице. Текущую версию проверяет модератор,
затем сервер предлагает сумму/срок действующего тарифа specialist-publication.
Перед новой оплатой проверяются владелец, сессия, телефон, профиль, город,
действующая профессия и одобрение именно этой revision. Переиспользованы
существующие checkout, immutable intent, dispatch, capture и журнал fulfillment.

Отдельная таблица specialist_checkout_terms фиксирует допуск нового локального
заказа. Старые покупки и metadata account-test-v1 не переинтерпретируются.
SQL BEFORE fulfillment проверяет capture/привязки и назначает даты;
AFTER fulfillment публикует анкету. Прямое опубликованное INSERT/UPDATE требует
настоящую совпадающую запись fulfillment. Параллельные вызовы дают один период.

После правки оплаченной анкеты требуется новая revision и новая модерация.
Каталог не показывает неодобренную revision. Прежняя оплата и даты сохраняются;
повтор старого fulfillment не продлевает срок. Новая покупка/продление для
оплаченной анкеты этим кандидатом не добавляются.

Клиент ведёт оплату по type=specialist, восстанавливает исходный заказ,
возвращает в /cabinet/specialist после подтверждения размещения. История
остаётся читаемой после отключения режима; новые dispatch/capture/fulfillment
тогда запрещены. Отмена у провайдера проверяется через локальный симулятор;
отдельная отмена ещё не отправленного заказа не показывается для анкеты.

## Границы

- Только BLIZHNIY_SPECIALIST_CHECKOUT=local-v1 в прежнем owned-local окружении
  https://127.0.0.1:3045 и shop local-fixture-shop; банковских запросов нет.
- Fair/2ГИС и существующие production-режимы не включаются этим флагом.
- Кандидат0060 не заменяет существующие SQL-функции. Прежние metadata guards,
  миграции и финансовые права не расширены.
- SQL применён только в уничтожаемых синтетических контейнерах. Постоянный
  стенд, production, установленные handlers/roles, LIVE и GitHub не изменены.
- Функции/таблица создаются с закрытым PUBLIC-доступом; GRANT в кандидате нет.
  В тестовой БД роли web/worker не superuser: web не может менять финансовый
  статус или вставлять fulfillment. Их SELECT специально шире будущего
  production-плана; это проверка разделения записи, не готовый пакет прав.

## Перед постоянной установкой

Сначала подготовить совместимость установленных финансовых guards и packages
с новым точным журналом/каталогом: local58+0060 даёт 59 записей, это не полный
префикс0001–0060. Прежние guards этот журнал правильно отклоняют. Нужны точные
структурные снимки, минимальные права, отрицательные проверки неизвестной
схемы и пакет установки с закрытой копией/откатом. Затем человеческий review
по [CONSTRAINTS.md:47](../../CONSTRAINTS.md): «Изменения самого guard/workflows
… обязательно проверяются человеком». До такого допуска этот SQL остаётся
предложением. Этот документ не разрешает установку или production-активацию.
