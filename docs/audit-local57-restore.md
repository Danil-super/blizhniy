# Локальная проверка восстановления — 14.11.2026

Область: существующий синтетический стенд local57, закрытая копия БД/фото
и отдельный одноразовый PostgreSQL18.6. Production, два российских сервера,
настоящий провайдер, миграция58 и новые права постоянного стенда не затронуты.

## Найденный отказ и исправление процедуры

Обычный custom `pg_dump` восстанавливает данные, но повторный SQL parse
меняет группировку шести CHECK, первоначально написанных через BETWEEN и AND.
Меняется только constraint-группа fingerprint; точный допуск финансовых
обработчиков отказывает. Это воспроизведено на свежей БД и на закрытой копии
ручного стенда. Исходные миграции и действующий schema guard не изменялись.

Добавлена отдельная не подключённая к приложению процедура:

- [guarded helper](../scripts/restore-local-primary57-checks.mjs);
- [единственный SQL payload](../database/restore/local-primary57-checks.sql);
- [отпечаток именно восстановленной57](../database/refund-schema-local-primary-restored-0057.json);
- [повторяемый PG-тест](../tests/logical-backup-restore-postgres.mjs).

Helper предназначен только для теста восстановления на свежем, проверенном
по ownership одноразовом контейнере без работающего приложения. Он не открывает
соединения, не является CLI и не вызывается launcher/deploy. Caller обязан
сначала доказать физическую принадлежность временной цели; одного имени БД
для этого недостаточно. Helper разрешён только в test runtime с postgres
и БД blizhniy_prod: полный journal/SHA256 и точный известный post-restore
fingerprint проверяются до DDL. SQL дополнительно проверяет хеш всего журнала.
Шесть исходных определений пересоздаются с полной проверкой существующих
строк в одной транзакции; перед COMMIT требуется прежний исходный fingerprint57.
Никаких новых допусков в финансовые обработчики и новых GRANT нет.

Первая версия проверки count/max не обнаруживала подмену ранней миграции;
замечание инженерного ревью исправлено. Тесты сохраняют count/max при подмене
имени/хеша и отдельно меняют другую часть схемы: отказ происходит до DDL.
Повторное статическое ревью существенных замечаний не нашло.

## Фактическая копия ручного стенда

Источник проверен по fixed state, Docker ID/label/image, loopback и pinned DB TLS.
При создании копии принадлежащий стенду launcher был остановлен, его клиенты
БД завершились; удерживался прежний OS writer fence. `pg_dump` получил
экспортированный read-only Repeatable Read snapshot. Копия media сохранила
полные байты и существующие hardlink-группы; проверены owner/mode/type и
неизменность файлов. До/после дампа совпали содержимое таблиц и последовательности.

Восстановление выполнено в новом закрытом loopback PG18 контейнере с тем же
закреплённым образом, без host mounts и прав источника. Его ID отличался от
источника; после проверки контейнер удалён только после повторной сверки
ownership. Пароли финансовых ролей в этой одноразовой цели были синтетическими;
их атрибуты/ACL и доступы восстановлены из копии. Исходные пароли не выгружались.
