## Поведение

Формы вакансии, заказа и анкеты получают действующие профессии через `GET /api/reference/professions`. Это публичная проекция `{id,slug,name,parent,active:true}`, без закрытых данных. Чтение ограничено 1000 строками; превышение лимита и сбой БД возвращают ошибку, без подстановки `data.ts`. В ответах — `no-store`. Браузер проверяет DTO, время, размер и число частей ответа; отменяет устаревший запрос при повторной загрузке и размонтировании.

В выпадающем списке можно искать и выбирать клавиатурой. Категория и slug различают одинаковые названия. UUID назначается явным выбором; изменение текста очищает его. Сохранённая ссылка восстанавливается по ID, в том числе после переименования. Если ранее сохранённая профессия отключена, черновик можно оставить с ней; новое размещение и отклик требуют действующую. Вновь выбранная, но ещё не сохранённая отключённая ссылка такого исключения не получает. Сбой загрузки не стирает остальные поля; предусмотрен явный повтор.

Сервер разрешает новую ссылку по UUID и записывает каноническое имя из БД. Старые name-only запросы поддержаны при однозначном имени; при редактировании собственной записи прежний FK имеет приоритет перед поиском по переиспользованному старому названию. Повтор уже выполненного создания возвращает ту же запись до нового поиска по справочнику. Владение, сессия, revision CAS и принадлежность фото не меняются.

Приватные и публичные чтения подставляют текущее имя по FK, не переписывая JSON, revision, даты и оплату. Сохранение/readback допускает расхождение только подписи профессии при том же валидном выбранном UUID; остальные поля сравниваются целиком. Лимит подписи 200 символов соответствует схеме.

Новые клиенты отправляют `X-Blizhniy-Profession-Refs: 1`. Четыре private publication/moderation API включают metadata UUID только при этом точном значении; старые вкладки сохраняют прежний набор JSON-ключей. Заголовок не предоставляет полномочий. Совместимость относится к форме DTO; обновлённый клиент нужен для новых возможностей выбора и лимита 200 символов.

Поиск, страницы профессий и sitemap читают тот же активный справочник. Primary-страница профессии фильтрует в SQL по UUID с ограниченной пагинацией; она не сканирует все анкеты и не примешивает demo-анкеты. Полный поиск публикаций пока остаётся отдельным F12.

Новые отклики получают название профессии из текущего FK. Уже отправленный snapshot неизменяем: переименование и отключение не переписывают прошлые сообщения. Проверки актуальной активности сохранены, сравнение устаревающих подписей в разных SQL statements устранено.

## Воспроизведение

Node 22.23.1; команды запускаются из корня проекта. Общий PostgreSQL/browser runner выполняется отдельно от тяжёлых native/build проверок; лимиты тестов не увеличиваются.

```sh
npm test
node --experimental-strip-types --test tests/profession-catalog-postgres-integration.mjs
node --experimental-strip-types --test tests/postgres-integration.mjs
node --experimental-strip-types --test tests/bootstrap-postgres-integration.mjs
npm run check:types
npm run lint
npm run check:floor -- --base 55a072b
npm run build
node --experimental-strip-types scripts/check-local-profession-catalog.mjs
```

Последний сценарий проверяет только подтверждённый собственный loopback-стенд: создаёт случайные синтетические аккаунт и профессии, проходит реальные API/Chromium, очищает только эти записи. Существующие ручные данные не сбрасываются. Он проверяет UUID при одинаковых названиях, обновление списка, сохранение, отключённый старый FK, ошибку/повтор без потери текста, размеры 320/768/1024/1440 и публичные поиск/sitemap/страницу профессии.

53 проверки нового изолированного PG18.6 runner покрывают также повторное создание, переиспользование старого имени другой строкой, границы прав и 1000 записей, имя 200 символов, SQL-пагинацию и snapshots откликов. Детерминированная проверка переименования между двумя statements воспроизводит найденную ревью гонку.
