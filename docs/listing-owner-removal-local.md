# Удаление заблокированного объявления из локального кабинета

Область: только локальный Postgres-стенд с явно включённым `postmoderation`.
Рабочий сайт, платёжные права, реальная оплата и прежний режим не меняются.

## Контракт

- Владелец может редактировать заблокированное объявление в единой форме. Правка
  не снимает блокировку, не продлевает срок и не меняет оплату.
- «Удалить» после подтверждения убирает только уже заблокированное объявление из
  кабинета владельца. Восстановление через пользовательский API не предусмотрено.
- Это не удаление персональных данных по запросу субъекта. Исходная запись,
  фотографии, причина блокировки, уведомления и финансовая история сохраняются;
  администратор продолжает видеть карточку. Отдельный процесс удаления аккаунта
  по-прежнему удаляет связанные персональные записи согласно своим правилам.

`POST /api/account/listing-removal` принимает ровно `action: read | remove`,
`expectedOwnerId`, `listingId`, `expectedRevision`. Cookie, Origin/Host, ingress,
лимит запросов и реальное владение проверяются сервером. Ответ содержит только
`id`, исходную `revision` и `removed`.

Один intent — пара listingId + expectedRevision. После неизвестного ответа
клиент не повторяет запись: доступно явное чтение того же intent. Совпавшая
отметка подтверждает удаление даже если административно менялась текущая версия;
другая removedRevision даёт конфликт. Дубликат не создаёт новую отметку.

## Хранение и минимальные права

Добавочная локальная миграция 0029 создаёт `app.listing_owner_removals`: listing_id,
owner_id, removed_revision, removed_at. INSERT-trigger берёт блокировку объявления
и проверяет автора, текущую версию и существующую блокировку. UPDATE запрещён,
DELETE недоступен веб-роли; каскад процедуры удаления аккаунта выполняется
операторской ролью. Текст объявления и новые контактные данные не дублируются.

Веб-роли нужны только SELECT и INSERT(listing_id,owner_id,removed_revision) новой
таблицы. Возможности UPDATE/DELETE старых таблиц, оплаты, сроков и блокировок не
выдаются. Старый режим не читает новую таблицу. Владелец после удаления не может
открыть старую ссылку редактора или изменить ресурс через API. Админская проверка
и финансовые обработчики не используют owner-фильтр.

## Проверки и применение

1. `scripts/check-local-listing-removals.mjs` проверяет настоящую PostgreSQL 18 в
   отдельной scratch-БД внутри валидированного локального контейнера. Удаляет
   только созданную scratch-БД; базу стенда не меняет.
2. `scripts/apply-local-listing-removals.mjs --plan` показывает подтверждённый
   loopback-target, точный hash и два GRANT без применения.
3. `--apply-local` запускается только после проверки diff и отдельного сигнала
   оператора. Проверяет точный журнал 0001–0028 или уже установленную 0029;
   неизвестный исход COMMIT автоматически не повторяется.
4. `scripts/check-local-blocked-owner-ui.mjs` на общей проверенной сборке
   воспроизводит редактирование blocked, скролл, чужой доступ, потерянный ответ,
   явное чтение результата, скрытие в кабинете и сохранённую админскую карточку.

Откат миграции допустим только пока таблица пуста. При наличии решения пользователя
down-миграция останавливается, чтобы не вернуть удалённое объявление в кабинет.
