## Выполнено: законченная SQL-сверка локального стенда

Команда `node --experimental-strip-types scripts/check-local-media-retention.mjs`
не принимает аргументов, remote URL, пути, режима apply или параметра удаления.
До подключения она проверяет точную identity owned Docker-контейнера,
loopback-порт и origin3045. Операторский доступ нужен только для чтения
закрытого budget и истории; веб-роли новые права не выдаются.

На одном соединении и одном bounded REPEATABLE READ READ ONLY snapshot
проверяются полный журнал57/hash, fingerprint установленной схемы и четыре
известных внешних ключа к media. Три таблицы связей фотографий учитываются
отдельно от `media_write_attempts`: наличие попытки не доказывает остановку
загрузчика. Известные JSON формы/профиль/booking и снимки откликов/броней,
тела исходных оплат/возвратов проверяются на буквальные UUID, включая
вложенные, повторные, embedded и uppercase значения. JSON Unicode escapes
нормализуются PostgreSQL до поиска; request_body разбирается как JSON.

Предел — 10000 metadata-строк,32 МБ документов,5 секунд на весь snapshot,
с SQL/client deadlines существующего PostgresDatabase. Неизвестный FK,
неполный/изменённый schema57, неверные строки, превышение бюджета или
несовпадение storage counters завершаются отказом, без успешного частичного
отчёта. В JSON попадают только выбранные metadata/ID/типы ссылок и счётчики;
телефоны, email, исходные документы, токены, хеши и пути файлов не выводятся.
Отчёт создаётся после успешного завершения snapshot через exclusive create
0600 в проверенном0700 каталоге вне Git. Stdout содержит сводку и путь отчёта;
ошибки содержат только фиксированный код/этап, без SQL/данных соединения.

Фактический результат на постоянном synthetic local57: **156 объектов,
3909920 байт,149 с известными текущими ссылками и7 без них**. Все156 ready,
pending0; owner caps не превышены, charged bytes/objects совпали. SQL-сверка
не является замером диска: временные файлы, hardlinks, физическое наличие
и безопасность содержимого не проверялись. Внешние документы вне app57 и
утраченные версии прежних связей не проверены; границы включены в сам JSON.

Все строки имеют `action=retain`, `unlinkedSince=null`, а весь отчёт —
`cleanupAuthorized=false`. Семь строк без текущих связей **не названы безопасными
к удалению**. Возраст metadata, дата публикации и время начала транзакции
не подменяют дату снятия последней связи. Отчёт не выдаёт capability на
unlink, DELETE, повтор записи или освобождение квоты.

## 14.11: журнал-кандидат и устранение разрыва claim → filesystem fence

Подготовлен `database/candidates/0058-media-reference-journal.sql`, **вне активных
миграций**. Он проверяется только на новой временной PostgreSQL18.6 с полными
0001–0057. Постоянный ручной стенд остаётся57; установленным handlers/workers
не расширяли допуск, роли и GRANT не меняли.

Журнал хранит media/source/resource ID, тип события и время, без копирования
форм, контактов, тела платежа или хешей. Записываются reserve/ready, присоединение
и снятие трёх photo-связей, UUID в текущих формах/профиле/booking и буквальные
UUID исторических снимков/тел запросов оплаты и возврата. Историческое
наблюдение не исчезает при изменении исходного документа. UPDATE/DELETE/TRUNCATE
журнала запрещены, веб-роли не получают доступ к нему или identity sequence;
SECURITY DEFINER trigger выполняет запись с фиксированным search_path.

События source-таблиц создаются AFTER фактического изменения: пропущенный
`ON CONFLICT DO NOTHING` не создаёт вымышленную ссылку. Общая media identity
блокируется в порядке ID через FOR NO KEY UPDATE: это совместимо с FK KEY SHARE,
но сериализует журнал между загрузчиками связей. Время берётся после ожидания
блокировки. Реальные переходы требуют READ COMMITTED; старые файлы получают
событие наблюдения при активации, без выдуманного unlink time в прошлом.
Это журнал доказательств, **не разрешение удалять**: финансовые связи target →
фото, не содержащие буквальный media ID в сохранённом документе, и утраченные
исторические версии ещё требуют отдельного консервативного удержания.

Общий путь `LocalMediaWriter` теперь получает SQL claim **после** READY от
дочернего процесса, уже доказавшего kernel flock. Только после успешного claim
в тот же процесс отправляется существующий ограниченный BFW1 frame. Отказ или
неопределённый результат COMMIT → пустой EOF, без файловой записи; исходная
ошибка возвращается после проверенного ответа и фактического close. Busy
сохраняет публичный MEDIA_IN_PROGRESS без создания SQL attempt. Нормализованные
байты копируются до первого ожидания, complete вызывается после закрытия child.
Прямой низкоуровневый write остаётся для явных файловых fixtures; штатные local/
production compositions используют обязательный writeClaimed без fallback.

Пятисекундный предел child теперь включает получение claim. Если до отправки
кадра child действительно закрылся, следующий независимый запрос разрешён;
поздний результат SQL никогда не отправляется в старый или новый child. Это
**не отмена SQL-транзакции**: поздний COMMIT может оставить pending attempt,
история и начисление сохраняются. После отправки любых файловых байтов UNKNOWN
по-прежнему блокирует supervisor; отсутствие подтверждённого close также
блокирует его. Ни отказ, ни timeout не освобождают квоту и не дают replay.

Проверки: PostgreSQL-кандидат9/9 (включая конфликт-no-op, реальный lock wait,
двух клиентов с FK KEY SHARE, rollback, reserve→ready и успешную запись роли
без доступа к журналу); bootstrap PostgreSQL364/364 с настоящими HTTP/socket/
файлами и новым поздним COMMIT после отмены child. Итоговая native2737/2737
прошла после последнего дополнительного сценария latch после BFW1;
supervisor22/22 прошёл отдельно. Целевые writer/supervisor/реальные

Ошибки воспроизведены RED, затем исправлены.
Два независимых инженерных ревью учтены; дополнительную проверку другой моделью

## Оставшийся пакет реализации очистки

1. **История связей.** Добавочный журнал переходов для трёх photo-таблиц,
   соответствующих form/snapshot операций и финансовых bindings. Общая media
   identity блокируется и добавлением ссылки, и retirement. Последняя ссылка
   исчезла → `clock_timestamp()` после ожидания блокировки, а не `now()` начала
   транзакции. Повторное присоединение сбрасывает отсчёт. Для старых неизвестных
   unlink нет задней даты: начало наблюдения явно записывается после активации;
   неразрешённые исторические/финансовые связи удерживают файл.
2. **Терминальная запись.** Immutable media и `(owner_id,intent_id)` сохраняются
   как защита replay; retired-файл нельзя прикрепить, дописать, заново прочитать
   как ready или восстановить старым intent. Quota admission должен считать
   активные начисления с учётом единственного завершённого retirement. Удалить
   metadata и забыть intent либо лишь добавить retirement без изменения суммы
   квоты — оба варианта некорректны.
3. **Retirement под общим filesystem fence.** Разрыв claim до flock устранён
   порядком READY → claim → frame, но будущий claim дополнительно должен
   отвергать terminal retirement под общей media identity. Pending с попыткой
   не признаётся остановленным по возрасту.
   Retire/file removal/fsync/единственное освобождение начисления требуют
   устойчивых фаз и reconcile; UNKNOWN сохраняет начисление.
4. **Пакет допуска.** Новые права, SQL guards и расширение схемы готовятся
   изолированно, с проверками attach-vs-retire, delayed writer, replay, рестарт,
   lost ACK и session/lock expiry. Локальные handlers/operators/workers57
   сверяют полный fingerprint: установка58 без согласованной совместимости
   остановит их. Установка на ручной стенд и изменение этих guard проходят
   одним конкретным пакетом review; текущие57-проверки не обходятся.

Такой порядок следует найденным гонкам, а не разрешает удаление семи строк
из сегодняшнего отчёта. F08 и весь этап3 остаются открытыми. Этот инкремент
не устанавливает миграций/GRANT, не меняет установленные workers и не удаляет файлы.
Production, два российских сервера, push/deploy и настоящие платежи не тронуты.

Источник условий snapshot: [PostgreSQL18, Repeatable Read](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-REPEATABLE-READ).
Завершение child подтверждается по [Node22, close](https://github.com/nodejs/node/blob/v22.23.4/doc/api/child_process.md#event-close), а не только exit или отправке сигнала.
