# Запросы на удаление аккаунта: внедрение и ручная обработка

## Что делает интерфейс

Авторизованный пользователь может отправить запрос через `/cabinet/udalit-akkaunt` и увидеть его номер и состояние. Пока один запрос открыт, повторная отправка возвращает тот же номер; после закрытия пользователь может обратиться снова, предыдущая запись остаётся в истории. Подтверждение сервера означает **только регистрацию запроса**, а не удаление данных. Заблокированный аккаунт с действительной сессией тоже может подать запрос; без доступа к аккаунту остаётся адрес `prostova04@yandex.ru`.

API принимает идентификатор пользователя только из проверенного Supabase Auth токена, игнорирует тело запроса, создаёт запись идемпотентно и позволяет читать только своё заявление. Администратор видит всю очередь по страницам (50 записей) по адресу `/admin/account-deletion`, может перевести заявление в `in_review` и только после фактического ручного рассмотрения отметить исход `resolved` с номером дела в защищённом журнале. Удаление пользователя, публикаций, файлов или платежей в приложении **не реализовано**. Административное закрытие заявки само по себе ничего не удаляет.

## Порядок внедрения

1. На подключённой БД уже применены миграции `20260927080926_account_deletion_request_intake_20260927.sql` и `20260927083242_account_deletion_requests_detach_deleted_user_20260927.sql`. Перед новой выкладкой сверить их с историей миграций. Проверить `relrowsecurity`, отсутствие прав `SELECT/INSERT/UPDATE` у `anon` и `authenticated`, права `service_role`; из anon/JWT проверить прямой Data API, затем `GET`/`POST` через Next.js от пользователей А и Б и администратора.
2. Проверить вход и выход между двумя пользователями в одном браузере: чужой номер заявки не остаётся на экране и не доступен через API. Повторный `POST` и два одновременных `POST` создают одну запись. Ошибка БД показывает ошибку, а не успешное сообщение.
3. Подтвердить, кто из сотрудников ежедневно проверяет очередь и через какой безопасный канал отвечает владельцу аккаунта. **До** запуска пользовательского UI применить миграцию в рабочей БД; затем выложить код и выполнить проверку с тестовыми пользователями.

## Ручная проверка каждого заявления

- Записать номер заявки и время поступления, подтвердить полномочия заявителя. Не использовать email из произвольного тела запроса и не пересылать копии паспорта без утверждённой процедуры.
- Проверить действующие платные размещения, платежи/возвраты и споры. До удаления скрыть или закрыть публичные публикации и связанные контакты, затем проверить поиск, карты, кеш и индексируемые страницы.
- Сверить **все** внешние ключи к `auth.users`, связанные `profiles`, `organization_profiles`, анкеты, заявки, изображения и Storage. После удаления Auth пользователя таблица заявлений сохраняет дело с `user_id = NULL` (`ON DELETE SET NULL`), не блокируя его удаление; автоматического `CASCADE` для финансовых записей нет. Составить отдельный план изменения/обезличивания и только после утверждения исполнить транзакцию с резервной копией, проверкой последствий и записью операции в защищённом журнале.
- Отделить данные, которые больше не нужны для целей обработки, от сведений, сохранение которых обосновано отдельным законом, договором или текущим спором. Платёж и бухгалтерский первичный документ могут иметь иной срок, чем контакт в публичном объявлении. Проверить серверные логи, письма, файлы и резервные копии; назначить ограничение доступа и срок уничтожения для каждой категории.
- Зафиксировать принятое решение и сообщить заявителю, какие данные удалены, какие временно сохранены и по какому основанию. Только после фактических действий в очереди выбрать «удалено», «частично сохранено» или «отказ», указать короткий неперсональный номер дела (`CASE-2026-0001`) и подтвердить ручные действия. Сайт запишет исход `resolved`, но не исполнит удаление. Перед удалением аккаунта зафиксировать ответ и безопасный канал связи в защищённом журнале: после удаления `auth.users` заявление остаётся без `user_id`, а email из профиля больше не показывается в очереди. Удалять запись заявления для этого не нужно.

## Нормативные рамки, которые нужно утвердить

Юристу оператора нужно утвердить сроки по категориям, сценарий прекращения обработки и ответ на заявление с учётом [152-ФЗ, статья 21](https://ips.pravo.gov.ru/api/ips/legislation/document?baseid=None&hash=98490812b3409e2a8d78a11ca9010f434ea3d9250a11dbbdb78690cd5551bdd6). Сроки в статье зависят от вида обращения и исключений: для требования прекратить обработку установлен ориентир в **10 рабочих дней** с возможным мотивированным продлением до **5 рабочих дней**; для отзыва согласия при отсутствии другого основания на хранение применяется отдельный срок уничтожения. Оператор должен зарегистрировать дату поступления и не ждать утверждения политики, прежде чем выполнять действующие требования закона. [402-ФЗ, статья 29](https://ips.pravo.gov.ru/api/ips/legislation/document?baseid=None&hash=2cd1c64de5d2c2f028fbd68e725846eeae60fdd78e4a90d57b1f9e110477ba36) задаёт срок хранения первичных бухгалтерских документов **не менее пяти лет после отчётного года**, но не делает все поля пользователя бессрочно нужными. Текущая политика `/legal/privacy` говорит о «разумном периоде»; оператор должен заменить эту формулировку конкретной матрицей сроков и механизмом удаления. Интерфейс не придумывает универсальный срок завершения удаления.

Это только входящая очередь для реальных заявлений. Пока нет назначенного ответственного и проверенного процесса, не считать проблему полного удаления данных закрытой.

Проверка метаданных действующей БД на 25.09.2026 показала: `auth.users → profiles` имеет `ON DELETE CASCADE`, но `profiles → payments`, `listings`, `vacancies`, `work_requests`, `specialist_profiles` и `fair_applications` имеют `NO ACTION`; `profiles → applications`, `booking_requests`, `organization_profiles`, `user_roles` и ряд других записей имеют `CASCADE`. Поэтому удаление `auth.users` без предварительного разбора зависимостей либо прервётся по FK, либо удалит часть неочевидных дочерних записей. Повторно проверить метаданные перед любой ручной операцией.
