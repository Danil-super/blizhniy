# Сверка статуса публикаций по сроку оплаты

Скрипт `supabase/maintenance/reconcile-expired-publications.sql` переводит оплаченные и неоплаченные строки `listings` и `vacancies` из `published` в `expired`, когда их `expires_at` наступило. Он не меняет `is_paid` (история оплаты), `published_at` или `expires_at`. Заархивированные, проданные, отклонённые, ожидающие оплаты, записи с пустым сроком и новые оплаченные публикации остаются без изменений. Публичные выборки независимо фильтруют срок, поэтому запуск скрипта нужен для правильного статуса в кабинете и админке.

Отдельное действие «вернуть вакансию из архива» меняет `published_at` на момент восстановления для порядка выдачи, но сохраняет исходный `expires_at`. Дата возврата не означает новую оплату и не продлевает размещение. Архивную вакансию с истёкшим сроком вернуть этим действием нельзя; новый срок потребует отдельного проверенного сценария оплаты и исполнения.

На 25.09.2026 метаданные живой БД подтвердили наличие срока у объявлений и вакансий, но пока не у `specialist_profiles` и `work_requests`. После добавления сроков для этих двух типов потребуется отдельное расширение скрипта и проверка их сценариев публикации. Для `fair_applications` срок не задан: участия без фиксированной даты окончания скрипт не затрагивает.

## Проверка и ввод в эксплуатацию

1. На отдельном стенде исполнить тест на временных таблицах: `psql -X -v ON_ERROR_STOP=1 -d "$STAGING_DATABASE_URL" -f tests/reconcile-expired-publications.sql`. Он проверяет границу `expires_at = now()`, действующие и архивные строки, сохранность истории оплаты и повторный запуск. Тест заканчивается `ROLLBACK`; в production не запускать его вместо основного скрипта.
2. Снять резервную копию стенда и агрегатно подсчитать будущие изменения: `select count(*) from public.listings where status = 'published' and expires_at <= now();` и аналогично для `public.vacancies`. Проверить, что есть право на оба `UPDATE`, а тип статуса принимает `expired`.
3. На стенде выполнить `psql -X -v ON_ERROR_STOP=1 --single-transaction -d "$STAGING_DATABASE_URL" -f supabase/maintenance/reconcile-expired-publications.sql`. Повторить запросы: оба счётчика должны стать нулём; убедиться в правильном статусе в кабинете, админке, отсутствии в выдаче и в том, что оплата не изменилась. Проверить публикацию новой оплаченной вакансии: действующая запись остаётся `published`.
4. Только после этого планировать production: согласовать время, сделать backup, записать агрегатные счётчики до запуска, исполнить тот же файл с production URL и сверить числа `expired_count`. Не включать таймер до успешного одиночного прогона и проверки сайта.

## Постоянный запуск на Timeweb

Релизный архив теперь включает `supabase/maintenance/reconcile-expired-publications.sql`. Локальный скрипт `scripts/reconcile-expired-publications.sh` запускает `psql` в одной транзакции и завершает службу с ошибкой, если SQL не исполнился или после него остались просроченные `published` строки. Публичного HTTP-обработчика и секрета для вызова через интернет нет.

Шаблоны `ops/systemd/blizhniy-expiry.service` и `ops/systemd/blizhniy-expiry.timer` рассчитаны на app VPS с релизным симлинком `/var/www/blizhniy`. Таймер запускает сервис каждые 15 минут; systemd не запускает вторую копию активного oneshot-сервиса. Включать его **только после** успешной выкладки этого кода, переноса БД и одиночной проверки подключения.

1. На сервере установить клиент PostgreSQL (`psql`) и создать отдельного системного пользователя `blizhniy-expiry` без входа в shell. SQL-сервису нужен только доступ к БД и на чтение файлов текущего релиза. Если база на отдельном Timeweb VPS, указать её приватный адрес и проверить сетевое соединение между серверами.
2. Создать отдельную роль PostgreSQL `blizhniy_expiry` с правами `SELECT(id,status,expires_at)` и `UPDATE(status)` **только** для `public.listings` и `public.vacancies`. Поскольку на этих таблицах включена RLS, дать роли `BYPASSRLS` лишь после проверки прочих унаследованных прав либо создать две узкие политики SELECT/UPDATE для этой роли. Пароль назначить интерактивно через `psql \\password blizhniy_expiry`, не помещать его в SQL-файл и историю shell.
3. В `/etc/blizhniy/pg_service.conf` создать секцию `[blizhniy_expiry]` с `host`, `port`, `dbname`, `user=blizhniy_expiry` и подходящим режимом TLS. В `/etc/blizhniy/pgpass` записать `host:port:dbname:blizhniy_expiry:password`; файл должен принадлежать `blizhniy-expiry` и иметь права `0600`. Каталог `/etc/blizhniy` и service-файл разрешить только root и группе `blizhniy-expiry`. Пароль не передавать в `ExecStart`, переменной `PGPASSWORD` или URL командной строки.
4. Установить оба unit-файла из текущего релиза в `/etc/systemd/system`, выполнить `systemctl daemon-reload`. **Таймер пока не включать.** Сначала выполнить `systemctl start blizhniy-expiry.service`; проверить `systemctl show -p Result blizhniy-expiry.service` и `journalctl -u blizhniy-expiry.service -n 30 --no-pager`. Результат должен быть `success`, оба счётчика в логе, а агрегатные счётчики просроченных `published` строк — ноль.
5. После проверки сайта включить `systemctl enable --now blizhniy-expiry.timer` и проверить `systemctl list-timers blizhniy-expiry.timer`. Отслеживать ненулевой код сервиса через журнал и мониторинг сервера; не считать ошибку SQL успешным запуском. При переносе релиза systemd продолжит обращаться к `/var/www/blizhniy`, то есть к текущему симлинку.

До появления Timeweb сервера и работающего GitHub Actions Deploy эти команды не запускались. Само слияние PR **не включает** таймер. В промежутке между запусками кабинет и админка показывают эффективный статус `expired` по времени; SQL-сверка приводит в соответствие саму БД.
